## How to use this file

1. **Pick the next item** from [Order and dependencies](#order-and-dependencies) whose dependencies are `done` and whose gate matches the current release target.
2. **Claim before branching:** mark the item `Status: in progress — claimed: <handle>, branch <branch-name>` (and later `— in PR #n`) in a small claim commit or PR, and read [`AGENTS.md`](../AGENTS.md), [`pitfalls.md`](pitfalls.md), and [`extending.md`](extending.md) before writing code.
3. **One item per PR:** keep pull requests scoped to a single `R<m>.<n>` item, use branch prefixes `feature/`, `bugfix/`, `hotfix/`, `refactor/`, `docs/`, `test/`, `chore/`, or `audit/` with the roadmap ID, and end squash PR titles with `(R<m>.<n>)`.
4. **Metadata & checkboxes:**
   - Every item header has the form `### R<m>.<n> <title>` followed by `Owner: maintainers|open · Status: todo|in progress|blocked (why)|done|merged into R<m>.<n> (<date>)|dropped (<date>, why) · Was: <old IDs / notes>`.
   - `- [ ]` lines track concrete pending sub-tasks (surfaced by `cargo xtask pending` under `R0.4`). Mark them `- [x]` only after verification passes.
   - After marking an item `done`, move it to its milestone file in [Roadmap History](history/roadmap.md) and add a direct link in the [archive index](#completed-roadmap-items). Preserve its ID and verification evidence, and update links to the item.
   - When items are merged or dropped, move each to its milestone file in [Roadmap History](history/roadmap.md) with the matching status. Keep its `[x]` lines and decisions, delete its open `[ ]` lines (they now live in the new item, tagged `(from R<old>)`), and list it in the [archive index](#completed-roadmap-items) with the suffix *(merged)* or *(dropped)*.
   - Hour estimates are single-agent implementation estimates (notes only, excluding human review).
5. **Unique table keys:** every Markdown table in `docs/ROADMAP.md` and `docs/STATUS.md` MUST have unique values in Column 1 (`cargo xtask status` enforces this to catch silent merge-conflict duplicates).

## Architecture rules for new work

- **Headless first:** domain logic (`L0`–`L5`) never depends on UI toolkits or OS windowing; UI panels (`L6`) act strictly through engine commands (`crates/engine`) or documented `UI_COMMANDS`.
- **Extend through seams:** register commands, formats (`Importer`/`Exporter`), fit equations (`ParametricModel`), and error codes through typed tables and traits rather than closed string `match` chains.
- **Data over code:** parameter schemas, command descriptors, shortcut metadata, and cursor tables live in declarative structs/TOML that generate docs and schemas rather than hand-synced prose counts.
- **Structured results:** propagate typed errors (`EngineError` / `ErrorCode`) and typed assumption diagnostics (`ChecklistItem::remediation`) — never silently coerce invalid domains or keyword-match UI strings.
- **Versioned files & safe I/O:** persist structured files with explicit format versions and forward-upgrade steps (`versioned.rs`), refuse to overwrite newer file versions, and route external subprocesses and atomic writes through `curvebook-platform` (`L0`).

A 2026-11-15 audit of the rendered desktop window (`apps/curvebook`) and web canvas (`apps/curvebook-web`) found that **`0` of `50`** reference GUI workflows can be completed end to end by a person, although the engine and most dialog state machines behind them exist and pass the agent-harness suite. This milestone closes that gap and brings the GUI to full visual and interactive alignment with no external branding. Systemic blockers:

| Blocker | Summary | Items |
|---|---|---|
| `B1` | Modal dialogs and the Power wizard render as ≤6 static uppercase text lines (12 of the 26 dialogs show only a placeholder); no buttons, tabs, inputs, or selectors; overlay not hit-tested; `Enter` does not confirm | `R10.1`, `R10.16`, `R10.3` |
| `B2` | No reachable New Data Table / Welcome picker; menu and shortcut create a default 12×2 `XY` table only. `WelcomeWizardState`, `TableCreationDraft`, and built-in sample fixtures exist in `workspace_nav.rs` but are never rendered | `R10.4` |
| `B3` | Result sheets show ≤4 tabs × 6 rows × column 0 with no scrolling; sub-tabs not hit-tested; `Cmd+T` on a result sheet creates a blank table (the parameter-dialog intercept exists only in `gui_actions.rs`) | `R10.5` |
| `B4` | Desktop engine menu items dispatch `Value::Null` params and fail on required fields; the web host has no menu bar | `R10.6`, `R10.7` |
| `B5` | Toolbar, inspector, formula bar, column headers / role badges, and context menus are drawn but not interactive; the wheel zooms the canvas instead of scrolling the grid past ~30 rows; arrows and `Delete` do not navigate or clear | `R10.6`, `R10.8`, `R10.17`, `R10.18` |

**Root cause.** The interface is split three ways: `inspect.rs` invents virtual control coordinates, `compositor.rs` paints uppercase 5×7 bitmap wireframes, and `interaction.rs` hit-tests only a handful of regions. None of the three reads the others' geometry.

**Binding rules for every `R10` item:**

1. **Human-operable:** a step counts only when it is performed with raw pointer, wheel, keyboard, or IME events against widgets drawn in the frame the user sees, located by pixel coordinates or by an accessibility tree produced from the same layout pass that drew them. Structured params through `ui.invoke_menu`, field patches through `ui.answer_dialog`, and `inspect.rs` nodes without drawn counterparts do not count.
2. **Single retained layout & widget pass:** each frame computes one shared layout tree. Every toolbar button, navigator row, grid header and cell, scrollbar, result sub-tab, inspector control, and modal widget gets its geometry once, and pixel rendering, physical hit-testing, and `ui.inspect` all read that tree.
3. **Deterministic layout per host:** layout and rendering stay pure and deterministic for a given text-measurement source. Desktop and the headless screenshot/workflow runner share `curvebook-text` shaping with system fonts, so they produce identical visuals and hit-boxes for the same font set. The web host measures and draws text with the browser's own canvas text rendering and fonts (decided 2026-11-15), so web text may differ from desktop pixel for pixel; widget structure, layout rules, and hit-box parity within the web frame still hold. No network access and no OS-widget divergence on any host.
4. **Clean-room & no external branding:** reference material may inform functional structure, visual hierarchy, and workflow ergonomics only. All wording, vector icons, schematic diagrams, and styling are original; no reference frames, icons, or copy enter the repository. CurveBook's own branding is permitted everywhere; no external product, suite, or vendor branding (such as that visible in the reference video frames) appears on any visible or metadata UI surface (`R10.14`).

[Completed R10 work and the original phase plan](history/roadmap/r10.md#r10-human-operable-gui--50-workflow-human-completion) are in the history.

## R11 Usable browser app

**Why this milestone exists.** A 2026-11-17 code audit of `apps/curvebook-web` (code reading only, no browser run) found that the browser evidence behind [`R8.4`](history/roadmap/r8.md#r84-live-wasm32-unknown-unknown-trunk-webgpuwebgl2-browser-hosting), [`R10.7`](history/roadmap/r10.md#r107-web-menu-bar-toolbar--chrome-parity-b4-web), and the web part of [`R10.13`](#r1013-human-operable-50-workflow-acceptance--manual-qa) consists of **native** tests of the Rust host logic. No test executes on `wasm32` or in a real browser, `cargo xtask wasm` is a `cargo check`, and no recorded computer-use or manual browser walkthrough exists. This milestone makes the browser build usable by a person and proves it in a browser. `R10` remains the shared desktop/web GUI milestone: its desktop walkthrough is required for **Beta** and its browser walkthrough for the `1.0` full release. The browser app is not a Beta requirement (see the browser decision in the archived [`R0.28`](history/roadmap/r0.md#r028-rein-in-the-number-of-release-install-files)).

**Runtime architecture today.** Inline JavaScript in `apps/curvebook-web/index.html` owns every DOM listener and sends JSON events to `WebBridgeSession::handle_event` (`apps/curvebook-web/src/host_adapters.rs`). Rust rasterises a full RGBA frame per event, base64-encodes it into the JSON reply, and JavaScript uploads it as a WebGL2 texture. There is no `requestAnimationFrame` loop and no worker, so analyses and fits run on the main thread.

| Gap area | Finding (2026-11-17) | Item |
|---|---|---|
| Browser evidence | No `wasm-bindgen-test`, browser automation, or browser QA; the web bundle size budget is checked only when a zip already exists locally (`check_web_bundle_readiness` in `xtask/src/web_fonts.rs`), not in CI or `release.yml` | `R11.1`, `R11.10` |
| Host glue | Event wiring, presenter, pickers, locks, and autosave live in inline JavaScript rather than Rust, outside every Rust test | `R11.2` |
| Text layout | `WebChromeBridge::build_layout_tree` (`apps/curvebook-web/src/chrome_bridge.rs`) measures with `DesktopTextMeasurer`, while the browser draws with its own fonts; browser `measureText` only adjusts baselines after layout (binding rule 3 of `R10`) | `R11.3` |
| Text entry & input | No focused editable element, so composition (IME) events and soft keyboards cannot work; `Tab` is always swallowed; mouse events only, without pointer capture; no cut; touch inertia (`CoastStep`) is never driven | `R11.4` |
| Document lifecycle | No save-in-place (every save downloads or asks "Save as"); export does not mark the document clean; opened `.curvebook.d/` folders are never written back (no `SyncDirectory` sender); one shared `"default"` autosave slot with silent restore and no stale-snapshot clearing; wasm timestamps read `unix:0` | `R11.5` |

## R12 User documentation

**Why this milestone exists.** The user-facing documentation is currently a beginner MCP guide ([`mcp-for-beginners.md`](mcp-for-beginners.md)), the MCP server overview ([`mcp.md`](mcp.md)), the generated engine command catalog ([`commands.md`](commands.md)), and implementation notes written for contributors. The GitHub Pages site ([`index.html`](index.html), [publication notes](release/github-pages.md)) is a single landing page that links out to Markdown on GitHub. No document describes every user-facing capability, and no document describes every MCP tool, toolset, resource, and prompt.

**Scope decisions (maintainer, 2026-11-18).**

- **Full reference, no examples.** `R12.1`, `R12.4`, and `R12.5` publish the reference documentation on GitHub Pages before **Beta**: an entry for every registry item, the automation reference, and the getting-started, files, settings, and support pages. `R12.3` adds the hand-written methods content section by section, before or after Beta. Reference pages may show the syntax of a single call (one request/response per MCP tool, one command line per CLI form) but no scenario walkthroughs, example use cases, or example workflows; those belong to `R12.2` after **Beta**.
- **Interface-neutral until the GUI is accepted.** Beta documentation describes what CurveBook does and how to drive it through MCP, the CLI, the control protocol, and batch files. A GUI user guide is a separate item (`R12.7`), unlocked by human GUI acceptance (`R10.13` for desktop, `R11.10` for the browser app), so the site never presents an unaccepted GUI path as working ([pitfalls §6](pitfalls.md#6-treating-semantic-agent-harness-tests-as-proof-of-human-gui-parity)).
- **Generated static HTML.** A `cargo xtask docs-site` step renders the hand-written Markdown and the typed registries into static HTML/CSS under `docs/`. Pages stays buildless and script-free with no external requests, so navigation uses section indexes, per-page contents, and an A–Z index instead of search.
- **Audience.** Users first. Contributor guides are not rendered on Pages; the **Contribute** section links to their Markdown on `main`, where contributors work. Rust API docs (`cargo doc`) are not published, because rustdoc pages need scripts.
- **Versioning.** Pages shows the documentation of the latest release, frozen at its tag, and keeps earlier release snapshots under `/vX.Y/`. Documentation for unreleased work on `main` is previewed locally only.

**Site map (Beta).** Get started · Concepts · Data tables & formulas · Analyses · Curve fitting · Graphs & Page Layouts · Calculators & quality-of-life tools · Files, import & export · Automation (MCP, CLI, control protocol, batch) · Settings & languages · Privacy, licences & security · Troubleshooting & known issues · Glossary & A–Z index · Contribute (links to GitHub). A **Using the app** section joins with `R12.7`.

### Release Gates

**Alpha policy (2026-11-16):** Alpha means full MCP functionality for the currently implemented engine scope, launched as **CurveBook**. Through the actual MCP transport, users must be able to discover and run the supported data, analysis, fitting, graph/layout, persistence, preview/export, batch, resource, and prompt workflows, with the documented modes and structured failures. `R7.3` supplies the recorded functional acceptance evidence; rerun that acceptance and the `R7.4` beginner setup under the final renamed binaries before launch. Deferred features and future engine additions are outside the current Alpha scope.

**Known bugs are acceptable for Alpha**, including documented audit findings. Alpha does not promise production reliability, a stable interface, or completion of `R0.19`; keep failures, limitations, and scientific caveats visible in the known-issues record and report only checks actually run. This milestone definition does not waive the project's scientific, clean-room, or engineering rules. In particular, prohibited branding/naming or asset references are launch blockers, not acceptable known-bug exceptions.

**Strict branding and asset-provenance clearance (`R0.21`) is also required for Alpha launch.** No reference-suite product/vendor branding or naming in any casing, and no mentions or use of its proprietary assets, may remain in the reviewed source, UI/MCP/documentation/export surfaces or launch artefacts. Only `.pzfx` / `.prism` file handling and its indispensable parser/exporter tokens are excepted at the format boundary. Require strict automated checks plus original-asset and rendered-output review on the final launch revision; ordinary guard passes with unchecked exclusions do not establish clearance. Known bugs do not waive this gate, and it does not depend on future GUI readiness.

**The full CurveBook rename (`R0.20`) is required for Alpha launch.** MCP functionality under the old identity alone does not complete the launch gate. Human GUI readiness (`R10`), full signed cross-OS distribution, and target-hardware/browser release QA remain separate later milestones; neither a visible window nor human-completable GUI workflows is required for Alpha. Existing presenter and agent-harness achievements retain their evidence, independently of the pending Alpha launch.
