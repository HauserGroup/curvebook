# Known Pitfalls (LumenCraft Incidents & Rules)

Every item below records a real issue encountered in the LumenCraft codebase and the mandatory engineering rule adopted to prevent it from recurring.

---

## 1. Documenting a `CommandSpec` Registry That Did Not Exist

- **What happened:** Documentation described a unified `CommandSpec` registry at `crates/engine/src/cmd/mod.rs` as though it already existed, whereas shipped engine commands were split across `COMMANDS: &[CommandDescriptor]` in `crates/engine/src/catalog.rs`, `is_read_only_command` in `crates/engine/src/lib.rs`, and string `match` arms across `crates/engine/src/{lib.rs,cmd_data.rs,cmd_sci.rs}`. Contributors looked for non-existent types and updated catalog entries without updating dispatch or read-only lists in sync.
- **Rule:** Never document unimplemented target abstractions as present fact. Explicitly mark target-architecture seams (such as `CommandSpec` and `UiCommandSpec` slated for `R0.8`) as **target** while citing the live files that implement behaviour today. When adding or modifying a command, update its descriptor, handler, read-only metadata, and sweep tests in one PR—and route everything through one typed registry once consolidated.

---

## 2. Hardcoded Headline Counts Going Stale

- **What happened:** Static prose in top-level contributor documentation hardcoded exact feature totals—for example claiming `75` engine commands when `crates/engine/src/catalog.rs` had grown to `90`, and `17` UI commands when `crates/ui-egui/src/menus/ui_commands.rs` had grown to `29`. As soon as subsequent PRs landed, those numbers became wrong and misled readers.
- **Rule:** Never hardcode mutable counts (engine commands, UI commands, tests, analyses, models, crates, or lines of code) inside hand-written prose. Live numbers belong only in generated or gate-checked documents ([docs/STATUS.md](STATUS.md) checked by `cargo xtask status`, `docs/commands.md` generated by `cargo xtask commands`, `crates/mcp/src/ui_catalog.rs` generated by `cargo xtask ui-commands`, or runtime output from `cargo xtask stats --exact`).

## 3. Growing `UI_COMMANDS` Without Regenerating `crates/mcp/src/ui_catalog.rs`

- **What happened:** New menu and dialog actions were appended to `UI_COMMANDS` in `crates/ui-egui/src/menus/ui_commands.rs`, but `cargo xtask ui-commands` was not run afterwards to update `crates/mcp/src/ui_catalog.rs`. The desktop UI menu and the MCP server's generated UI command list silently fell out of sync.
- **Rule:** Whenever you change a source registry (`UI_COMMANDS`, engine `COMMANDS` / `CommandSpec`, persisted schemas, or `cursors.toml`), regenerate every derived file (`cargo xtask ui-commands`, `cargo xtask commands`, `cargo xtask schemas`) in the same commit and always run `--check` (`cargo xtask ui-commands --check`, `cargo xtask commands --check`, `cargo xtask schemas --check`) before finishing.

## 4. Positional Tuple Destructuring Scrambling `UI_COMMANDS` Fields in MCP

- **What happened:** `UI_COMMANDS` in `crates/ui-egui/src/menus/ui_commands.rs` stored 4-tuples `(id, label, shortcut, params_doc)`. Because all four elements had the identical type `&'static str`, `crates/mcp/src/tools.rs` destructured `&(id, label, menu_path, shortcut) in UI_COMMANDS`, silently reporting `shortcut` strings as `"menu_path"` and JSON `params_doc` strings as `"shortcut"` (while hardcoding `"params_doc": "{}"`) with zero compiler warnings.
- **Rule:** Never define shared cross-crate lookup tables as homogeneous positional tuples (`(&str, &str, ...)`). Always use named struct fields (`UiCommandSpec`, `CommandSpec`) so Rust enforces field identity at compile time. Until tuple tables are retired, downstream consumers must use generated accessors or named catalog structs rather than unpacking raw tuples positionally.

---

## 5. Non-Atomic `.lumencraft` Saves Risking Truncation on Crash

- **What happened:** `save_project_file` and `save_template_file` in `crates/format/src/archive.rs` wrote `.lumencraft` and `.lctemplate` archives directly using `std::fs::write(path, bytes)?`. If the process crashed, received a signal, or encountered an I/O failure partway through writing over an existing project file, the user's file on disk could be left truncated or empty.
- **Rule:** Never overwrite persisted user projects, templates, preferences, or critical state files with direct in-place `std::fs::write`. Perform all persistent saves atomically (write sibling temp file -> flush & sync -> atomic rename over target) via the shared helpers in `lumencraft-platform` (`crates/platform`, introduced in `R0.10`), keeping recovery journals intact until replacement completes.
