# Known Pitfalls (CurveBook Incidents & Rules)

Every item below records a real issue encountered in the CurveBook codebase and the mandatory engineering rule adopted to prevent it from recurring.

---

## 1. Documenting a `CommandSpec` Registry That Did Not Exist

- **What happened:** Early documentation described a unified `CommandSpec` registry at `crates/engine/src/cmd/mod.rs` before it existed, whereas shipped engine commands were split across `COMMANDS: &[CommandDescriptor]` in a legacy `catalog.rs` file, `is_read_only_command` in `crates/engine/src/lib.rs`, and string `match` arms across `crates/engine/src/{lib.rs,cmd_data.rs,cmd_sci.rs}`. Contributors looked for non-existent types and risked updating catalog entries without updating dispatch or read-only lists in sync.
- **Resolution & Rule:** `R0.8` replaced `catalog.rs` with typed [`CommandSpec`](../crates/engine/src/cmd/mod.rs) dispatch (`cmd::registry()`, typed params via `serde_path_to_error`, `Effects`, and JSON Schemas). Keep the underlying discipline permanent: never document unimplemented target abstractions as present fact; distinguish **target** seams from live files, and whenever adding or modifying a command, update its `CommandSpec` entry, handler, schema, and sweep tests together (`cargo xtask commands --check`, `cargo xtask schemas --check`).

---

## 2. Hardcoded Headline Counts Going Stale

- **What happened:** Static prose in top-level contributor documentation hardcoded exact feature totals—for example claiming stale engine or UI command totals while `CommandSpec` grew to `90` engine commands and `UiCommandSpec` grew from `17` -> `29` -> `30` UI commands. As subsequent PRs landed, prose numbers became wrong and misled readers.
- **Rule:** Never hardcode mutable counts (engine commands, UI commands, tests, analyses, models, crates, or lines of code) inside hand-written prose. Live numbers belong only in generated or gate-checked documents ([docs/STATUS.md](STATUS.md) checked by `cargo xtask status`, `docs/commands.md` generated by `cargo xtask commands`, `crates/mcp/src/ui_catalog.rs` generated by `cargo xtask ui-commands`, or runtime output from `cargo xtask stats --exact`).

## 3. Growing `UI_COMMANDS` Without Regenerating `crates/mcp/src/ui_catalog.rs`

- **What happened:** New menu and dialog actions were appended to `UI_COMMANDS` in `crates/ui-egui/src/menus/ui_commands.rs`, but `cargo xtask ui-commands` was not run afterwards to update `crates/mcp/src/ui_catalog.rs`. The desktop UI menu and the MCP server's generated UI command list silently fell out of sync.
- **Rule:** Whenever you change a source registry (`UI_COMMANDS`, `cmd::registry()`, persisted schemas, i18n keys, or `cursors.toml`), regenerate every derived file (`cargo xtask ui-commands`, `cargo xtask commands`, `cargo xtask schemas`) in the same commit and always run `--check` gates (`ui-commands --check`, `commands --check`, `schemas --check`, `telemetry`, `screenshots --check`) before finishing.

## 4. Positional Tuple Destructuring Scrambling `UI_COMMANDS` Fields in MCP

- **What happened:** Historically `UI_COMMANDS` in `crates/ui-egui/src/menus/ui_commands.rs` stored 4-tuples `(id, label, shortcut, params_doc)`. Because all four elements had `&'static str`, `crates/mcp/src/tools.rs` mis-destructured `&(id, label, menu_path, shortcut)`, silently reporting `shortcut` strings as `"menu_path"` and JSON `params_doc` strings as `"shortcut"` (while hardcoding `"params_doc": "{}"`) with zero compiler warnings.
- **Resolution & Rule:** Resolved in `R0.8`: `UI_COMMANDS` now uses named [`UiCommandSpec`](../crates/ui-egui/src/menus/ui_commands.rs) fields synced via codegen into [`crates/mcp/src/ui_catalog.rs`](../crates/mcp/src/ui_catalog.rs). Never define shared cross-crate lookup tables as homogeneous positional tuples (`(&str, &str, ...)`). Always use named struct fields (`UiCommandSpec`, `CommandSpec`) so Rust enforces field identity at compile time.

## 5. Non-Atomic `.curvebook` Saves Risking Truncation on Crash

- **What happened:** `save_project_file` and `save_template_file` in `crates/format/src/archive.rs` wrote `.curvebook` and `.cbtemplate` archives directly using `std::fs::write(path, bytes)?`. If the process crashed, received a signal, or encountered an I/O failure partway through writing over an existing project file, the user's file on disk could be left truncated or empty.
- **Resolution & Rule:** Resolved in `R0.10`: `crates/format/src/archive.rs` now saves through `curvebook_platform::fs::write_atomic`. Never overwrite persisted user projects, templates, preferences, or critical state files with direct in-place `std::fs::write`. Perform all persistent saves atomically (write sibling temp file -> flush & sync -> atomic rename over target) via the shared helpers in `curvebook-platform` (`crates/platform`, introduced in `R0.10`), keeping recovery journals intact until replacement completes.

## 6. Treating Semantic Agent-Harness Tests as Proof of Human GUI Parity

- **What happened:** The semantic agent harness (`--gui-only` MCP/control tools, `--control`, `--event-script`, and headless `dispatch_gui_action` suites covering `WF-01`–`WF-49`) ran cleanly without opening or operating visible controls in the rendered `egui`/`eframe` GUI. Because those harness runs were mistaken for proof of human GUI parity, UI checklist items were marked `[x]` done while `0 / 50` reference workflows could be completed by a person through the rendered GUI.
- **Resolution & Rule:** Resolved in `R0.15`: every `[x]` claim in `docs/ui-parity.md` (excluding rows explicitly tagged `*(agent harness)*`) and every non-zero entry in the `Human path` column of `docs/gui-workflows.md` §6.2 must cite a passing human-path/unit test name or a recorded computer-use (mouse and screen) or manual human walkthrough. Semantic agent-harness tests and flags (`--control`, `--event-script`, `dispatch_gui_action`, `gui_wf_*`, `gui_only_workflows`, `gui_w22b_qol_and_r9`, `gui_only_surface`, `mcp_gui_only_parity`, `gui_only_wiring`, `ui.invoke_menu`, `ui.answer_dialog`) never count as evidence for GUI/human-operable claims, and `cargo xtask status` fails CI if any `[x]` or human-path claim lacks qualifying proof.
