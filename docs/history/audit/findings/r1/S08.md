### R1-S08-01 · S1 · Log-axis tick generator overflows and allocates without bound when a data value is near `f64::MAX` or the smallest subnormal

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/xy.rs:1198-1221` (`generate_log_ticks`), domain source `crates/chart/src/xy.rs:233-235` and `xy.rs:260-262` (`auto_domain_min`/`auto_domain_max`), callers `xy.rs:1068`, `xy.rs:1108`; axis built for XY at `xy.rs:1542-1547` and Column/Grouped at `crates/chart/src/column_grouped.rs:96-101`
- **Category:** no-panic / resources
- **Defect:** On a Log10/Log2/Ln axis the auto domain is `base^ceil(log(max·(1+headroom)))` and `base^floor(log(min))`, which become `+inf` for data above about `1e308` (`9.5e307` on Y with the 5 % headroom) and `0.0` for data below about `1e-323`; `generate_log_ticks` then casts `inf`/`-inf` exponents to `i32::MAX`/`i32::MIN` and does unchecked `i32` arithmetic (`hi_exp - lo_exp` at `xy.rs:1201`, `k += stride` at `xy.rs:1218`) in a `while k <= hi_exp` loop that pushes a tick (`inf` or `0.0`) on most iterations.
- **Failure scenario:** An XY table (CSV paste, `.pzfx`/`.prism` import, or `table.setCell`) with Y values `1.0` and `1.5e308`, graphed with a Log10 Y axis. Debug builds panic (`attempt to add with overflow`, `xy.rs:1218`). Release builds wrap `k` back to a negative value, so the loop never terminates and the `majors` vector grows until the process aborts on allocation failure (wasm aborts sooner). With Y values `0.01` and `1.5e308`, or `1.0` and `5e-324`, `hi_exp - lo_exp` itself overflows (`xy.rs:1201`). No cell-magnitude cap exists in `Cell::number` (`crates/doc/src/cell.rs:64-66`), and the same `SegmentedAxis` builds Column and Grouped Y axes. Every compile of that graph (open, redraw, export) hangs.
- **Evidence:** Probe `xy_doc(Single, [(1,1.0),(2,1.5e308)])`, Y scale `Log10`, `compile_graph`:
  ```
  debug:   panicked at crates/chart/src/xy.rs:1218:9: attempt to add with overflow
  release: PROBE: live heap exceeded 512 MiB cap -> aborting (unbounded allocation)   (after ~2 s)
  ```
  Y values `(0.01, 1.5e308)` and `(1.0, 5e-324)`: debug `panicked at xy.rs:1201:20: attempt to subtract with overflow`; release hits the 512 MiB cap.
  ```rust
  let lo_exp = seg.min.log(base).floor() as i32;            // xy.rs:1199
  let hi_exp = seg.max.log(base).ceil() as i32;             // xy.rs:1200
  let stride = (((hi_exp - lo_exp).max(1) as f64) / 7.0)... // xy.rs:1201
  while k <= hi_exp { ... majors.push(major); ... k += stride; }  // xy.rs:1205-1218
  ```
- **Suggested fix:** Reject non-finite or zero segment bounds after domain resolution (fall back to the scale default with a warning), compute exponents in `f64` and cap the tick count as `scales.rs:1247-1255` already does with `MAX_TICKS_PER_SEGMENT`, and use checked arithmetic for `k`.
- **Related:** R1-S08-09 (the guarded tick engine in `scales.rs` is not the one `compile_graph` runs); `X1`.

### R1-S08-02 · S1 · Y-axis title placement panics in `f64::clamp` on canvases narrower than about 40 pt

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/survival_cat.rs:630` (`emit_y_title`), plot rect from `survival_cat.rs:343` (`update_plot_rect_for_labels`); canvas check `crates/chart/src/lib.rs:44`
- **Category:** no-panic
- **Defect:** `emit_y_title` computes `(r.x - max_y_label_w - 14.0).clamp(11.0, r.x - 8.0)`, and `f64::clamp` panics when `min > max`, which happens whenever the plot left edge `r.x < 19`; `update_plot_rect_for_labels` sets `r.x = min(left_base + extra, 0.48 · width_pt)`, so any canvas narrower than about 39.6 pt with a non-empty Y title panics.
- **Failure scenario:** `graph.setSpec` with `{"canvas_size_pt": {"width": 30, "height": 200}}` (or a project file carrying that size; `compile_graph` only rejects non-positive and non-finite sizes, `lib.rs:44`) on a Contingency graph whose Y axis title is `"Count"`. Rendering, export or thumbnailing panics. The same `draw_cartesian_frame` → `draw_y_numeric_ticks` → `emit_y_title` path serves Survival, Contingency, Multiple Variables, Volcano, Bland–Altman, ROC, Forest and Residual graphs (`survival_cat.rs:1269`, `1722`; `multivariate_layout.rs:198`, `530`, `1372`, `1612`, `1830`, `2022`). Release builds panic too (the `clamp` assertion is unconditional); wasm aborts.
- **Evidence:** Probe: 2×2 `ContingencyTable` with counts, `GraphSheet::new_uninitialized_for_data`, `y_axis.title = "Count"`, `canvas_size_pt = 30×200`:
  ```
  kind=Contingency
  panicked at .../core/src/num/f64.rs:1585:9:
  min > max, or either was NaN. min = 11.0, max = 6.399999999999999
  ```
  (same in debug and release).
- **Suggested fix:** Compute `hi = (r.x - 8.0).max(11.0)` before clamping (or use `max`/`min` instead of `clamp`), and enforce a minimum canvas size in `compile_graph`/`GraphSpec::validate`.
- **Related:** `S07` (`graph.setSpec` accepts any positive canvas size), `X1`.

### R1-S08-03 · S2 · Default replicate beeswarm is quadratic: a 16,000-value column takes 8 s per render, a 100,000-value column several minutes

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/column_grouped.rs:1176-1213` (`deterministic_beeswarm_offsets`), called from `column_grouped.rs:761`, `784`, `901`, `1027`; default overlay `crates/doc/src/graph.rs:687`
- **Category:** resources
- **Defect:** For each point the beeswarm tries up to `2·max_steps+1` offsets and scans every already-placed point for each (`placed.iter().any(...)`, `column_grouped.rs:1197`), so cost is O(n²·steps) with no cap on `n`, and `BarWithReplicates { replicate_overlay: Some(DeterministicBeeswarm) }` is the default GDO for Column, Grouped and Nested graphs (`graph.rs:687`).
- **Failure scenario:** A Column table with one data set of N replicates (rows are allowed up to `MAX_ROWS = 1_000_000`) and its auto-created graph. Opening, redrawing or exporting the graph blocks the engine thread: measured 0.12 s at N = 2,000, 2.1 s at 8,000, 8.4 s at 16,000 (release); quadratic extrapolation gives about 5 min at 100,000 and hours at 1,000,000. The desktop UI and MCP/control requests that compile the scene stall for that long.
- **Evidence:** Probe `swarm N`: `ColumnTable::new(UnpairedReplicates, 1, N)`, values `100 + 10·(frac(r·0.618…) − 0.5)`, default graph, release build:
  ```
  n=2000  compile_graph took 115.8ms
  n=8000  compile_graph took 2.143s
  n=16000 compile_graph took 8.371s
  ```
- **Suggested fix:** Bin points by Y (only compare against placed points within `min_dist` in Y, for example with a sorted sweep), and cap the number of individually drawn replicate markers (falling back to a density strip or aligned column above a threshold).
- **Related:** `X1`.

### R1-S08-04 · S2 · XY/Column auto ranges on probit, logit and reciprocal axes exclude valid data, and the omitted points raise no warning

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/xy.rs:236-244` (`auto_domain_min`), `xy.rs:263-271` (`auto_domain_max`), omission at `xy.rs:1773-1794` and `xy.rs:1866-1879`, warning predicate `xy.rs:1892-1894`
- **Category:** wrong-result
- **Defect:** The automatic domain clamps Probit/Logit-percent to `[min(max(raw_min·0.5, 0.1), 10), clamp(raw_max, 90, 99.9)]` (Proportion: `[0.001…0.1, 0.9…0.999]`), so valid data below 0.1 % or above 99.9 % falls outside the axis, and on a Reciprocal axis with mixed-sign data the domain `[raw_min·1.15, raw_max·1.15]` straddles zero so no point maps; `map_strict` then drops these points, and the only warning (`is_out_of_axis_domain`) fires when the scale transform fails, not when a valid value lies outside the resolved domain.
- **Failure scenario:** XY data Y = `0.05, 20, 50, 80, 99.95` (percent) on a Probit or Logit-percent Y axis with automatic range: 3 of 5 points are drawn, `scene.warnings` is empty, and the axis reads 0.1…99.9 as if it covered all data. Y = `-2, -1, 1, 5` on a Reciprocal axis: 0 of 4 points drawn, no warning (the `scales.rs` resolver rejects such a domain with `invalid_axis_domain`, `scales.rs:859-869`, but that code is not on this path).
- **Evidence:** Probe, default ScatterAndLine series, counting filled marker paths:
  ```
  probit:      5 data points, filled markers drawn = 3   warnings=[]
  logitpct:    5 data points, filled markers drawn = 3   warnings=[]
  recip_mixed: 4 data points, filled markers drawn = 0   warnings=[]
  ```
- **Suggested fix:** Derive the auto probit/logit range from the finite in-domain data (for example the next candidate tick outside `[min, max]`), reject sign-straddling reciprocal domains, and emit a warning counting every point not drawn because it lies outside the resolved segments.
- **Related:** R1-S08-05, R1-S08-09.

### R1-S08-05 · S2 · An explicit reversed axis range (`min > max`) is silently replaced, hiding data

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/xy.rs:212-214` (`resolve_segment_domain`), `xy.rs:285-290` (`expand_degenerate_domain`)
- **Category:** wrong-result
- **Defect:** When both bounds are set and `min >= max`, the XY/Column resolver discards both and substitutes `center ± max(|min|,1)·0.5` around the user's `min`, with no warning, whereas `scales.rs` treats a reversed domain as valid (`scales.rs:384-386`, `416-419`).
- **Failure scenario:** An inverted Y axis (common for depth or rank plots), set via `graph.setAxes` with `{"y": {"min": 100, "max": 0}}` (accepted by `apply_segment_updates`, `crates/engine/src/cmd_sci.rs:1557-1563`), Y data `10, 30, 60, 90`. The axis is drawn 50…150, only 2 of 4 points are plotted, and `scene.warnings` is empty.
- **Evidence:** Probe `reversed`:
  ```
  4 data points, filled markers drawn = 2
  y tick labels: [... "60", "80", "100", "120", "140" ...]
  warnings=[]
  ```
- **Suggested fix:** Either support reversed segments (map with `g_min > g_max` as `scales.rs` does) or reject them in `apply_segment_updates`/`AxisSpec::validate`; never substitute a different range silently.
- **Related:** R1-S08-04, R1-S08-09.

### R1-S08-06 · S2 · Pre-summarized Mean/SD/N rows: a missing N draws ±SD for any requested metric, and a missing SD removes the mean even when no error bars are requested

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/xy.rs:449-496` (`summarize_pre_summarized`), fallback `crates/doc/src/cell.rs:222-228` (`explicit_bounds`); shared by Column/Grouped via `column_grouped.rs:283`, `446`
- **Category:** wrong-result
- **Defect:** `SummarizedPoint::reconstruct` runs before the error-bar spec is consulted (`xy.rs:457-461`); on `Err` (missing N, N < 1, missing spread) the code returns `explicit_bounds`, which for `MeanSdN`/`MeanSemN` is `mean ± column 2` and for `MeanCvN` is `mean ± CV·|mean|` regardless of the requested metric, and returns `None` (point dropped) when the spread cell is blank.
- **Failure scenario:** XY table in `MeanSdN` mode, error bars set to SEM. Row (50, 10, 100) draws 49…51 (correct). Row (60, 10, N blank) draws 50…70, the SD, under an SEM legend (with N = 100 the SEM would be 1). With error bars set to "none", row (70, SD blank, 100) disappears from the graph although only the mean is needed. The warnings say "missing sample size N" / "missing its SD/SEM/%CV spread value" but not that a different metric was drawn or that the point was removed.
- **Evidence:** Probe `meansdn`, Y axis 0…100, converting error-bar pixel ends back to data units:
  ```
  vertical error bar at x=87.1:  data 49.00 .. 51.00
  vertical error bar at x=242.9: data 50.00 .. 70.00
  no-error-bar graph: filled marker paths = 2 (3 rows with a mean)
  ```
- **Suggested fix:** When the metric cannot be computed, draw the mean without an error bar (and warn that the bar was omitted); only call `reconstruct` when an error bar that needs N or SD is requested.
- **Related:** `S05` (`SummarizedPoint` contract in `crates/doc`).

### R1-S08-07 · S2 · A significance bracket whose group is not drawn falls back to the slot at the same position and labels the wrong pair

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c

The bracket is drawn from Arm 2 to Arm 3 and labelled with the Arm 1 vs Arm 3 P value; no warning is raised. Expected: skip the bracket with a warning.

- **Related:** none.

### R1-S08-08 · S2 · User major-tick intervals: ticks silently stop after 65 intervals, and tiny intervals overflow `i64` arithmetic

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/xy.rs:1165-1196` (`generate_linear_ticks`); same cap pattern in `crates/chart/src/survival_cat.rs:259-285` (`linear_nice_ticks`, 32 ticks)
- **Category:** wrong-result / no-panic
- **Defect:** The tick count is `(end_k - start_k).clamp(0, 64)` counted from the low end, so any user interval giving more than 65 ticks draws ticks only over the first 64 intervals; `end_k - start_k` (`xy.rs:1174`) and `start_k + dk` with `dk = -1` (`xy.rs:1186`) are unchecked `i64` operations on values saturated from `f64` division, so a tiny interval over a range that includes negative values overflows.
- **Failure scenario:** (a) Y axis 0…1000 with `major_tick_interval = 10` (101 ticks): labels run 0…640 and the top third of the axis has no ticks or labels, with no warning. Survival/MV axes stop after 32 ticks. (b) Y axis −10…10 with `major_tick_interval = 1e-300`: debug builds panic (`attempt to subtract with overflow`, `xy.rs:1174`); release builds draw a single label `-9.223372037e-282`. `apply_segment_updates` accepts any finite interval (`crates/engine/src/cmd_sci.rs:1566-1571`).
- **Evidence:** Probe `interval10`: `numeric labels ... max=640.0`, `warnings=[]`. Probe `tinyinterval`: debug `panicked at crates/chart/src/xy.rs:1174:17: attempt to subtract with overflow`; release `texts=[..., "-9.223372037e-282", ...]`.
- **Suggested fix:** Raise the interval to `range / MAX_TICKS` when it would exceed the cap (as `scales.rs:1247-1248` does) and warn, compute the tick count in `f64` before any integer conversion, and use checked/saturating `i64` arithmetic.
- **Related:** R1-S08-01, R1-S08-09.

### R1-S08-09 · S3 · The guarded axis engine in `scales.rs` that the tests and parity checklist verify is not the one `compile_graph` runs

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/scales.rs:19-20`, `485-540` (`ResolvedAxis::resolve`), `987-1031` (`compute_axis_ticks`), `1919` (`resolve_axes_and_ticks`), `2949` (`render_graph_chrome`); shipped paths `crates/chart/src/xy.rs:102-151`, `1141-1221` (`SegmentedAxis`, its own tick generator) and `crates/chart/src/survival_cat.rs:195-285` (`resolve_axis_domain`, `nice_axis_ticks`); dispatch `crates/chart/src/lib.rs:50-58`
- **Category:** contract-drift
- **Defect:** Three independent axis implementations exist; only the `scales.rs` one has `MAX_TICKS_PER_SEGMENT`, the `min_step` interval floor, reversed-domain support, reciprocal sign checks, the 25 % gap cap (`scales.rs:501`) and `ScaleDiagnostics` warnings, but outside `scales.rs` nothing calls `ResolvedAxis`, `compute_axis_ticks` or `render_graph_chrome` (only `AxisMapping`, additional-tick helpers and `gridline_stroke` are shared), while `tests/scales_axes.rs` and `tests/ticks_and_diag_parity.rs` exercise exactly those unused functions.
- **Failure scenario:** `docs/evidence/graphing.md:18` and `:20` mark broken axes, tick cadences and log handling as verified, and the 11 `scales_axes` tests pass, yet the shipped XY/Column path has the defects in R1-S08-01, -04, -05 and -08 and an uncapped break gap (`xy.rs:112`, `gap_width_pt.max(2.0)`, so a 1e6 pt gap pushes later segments off the canvas). A fix made in `scales.rs` changes nothing the user sees.
- **Evidence:** `grep -rn "ResolvedAxis\|render_graph_chrome\|render_axes_and_frame\|compute_axis_ticks" crates apps` outside `scales.rs` matches only `crates/chart/tests/scales_axes.rs` and `crates/chart/tests/ticks_and_diag_parity.rs`.
- **Suggested fix:** Route `xy.rs`, `column_grouped.rs` and `survival_cat.rs` through `ResolvedAxis` and `compute_axis_ticks` (keeping their GDO code), delete `SegmentedAxis`'s domain and tick code and `survival_cat::nice_axis_ticks`, and make the tests compile real graphs.
- **Related:** R1-S08-01, -04, -05, -08.

### R1-S08-10 · S3 · `scales.rs` reciprocal error-bar clamp uses +1e-12 as the floor on a negative axis, producing coordinates near 1e14 pt

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/scales.rs:307-312` (`clamp_error_bound`, Reciprocal arm), `scales.rs:242-249` (`positive_floor`)
- **Category:** wrong-result (latent: public API, not on the `compile_graph` path today, see R1-S08-09)
- **Defect:** When a reciprocal error bound crosses zero, the bound is replaced by `±positive_floor()`, but on an all-negative domain `positive_floor()` falls back to `LOG_POSITIVE_FLOOR_DEFAULT = 1e-12`, so the bound becomes `-1e-12`, whose reciprocal is `-1e12`.
- **Failure scenario:** `AxisMapping { min: -10, max: -1, scale: Reciprocal }.map_error_bar(-5.0, -9.0, 1.0, 0.0, 300.0, …)` maps the upper whisker to about `3.3e14` pt instead of the domain end at `-1`; any renderer receiving that path draws a line to the edge of float range. Traced by hand, not run.
- **Evidence:** `let safe = if center > 0.0 { self.positive_floor() } else { -self.positive_floor() };` with `positive_floor` returning `1e-12` when neither bound is positive.
- **Suggested fix:** Clamp to the domain endpoint nearest zero with the centre's sign (`-min(|min|, |max|)` for a negative domain).
- **Related:** R1-S08-09.

### R1-S08-11 · S3 · Dendrogram node ids from a result tab are negated without overflow checks

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/multivariate_layout.rs:1251` (`l as isize`), `multivariate_layout.rs:1279` and `1307` (`((-node) - 1) as usize`)
- **Category:** no-panic (debug builds only)
- **Defect:** Merge ids are read from `ResultCell::Number` as `f64` and cast with `as isize`, which saturates `-1e300` to `isize::MIN`; `-node` then overflows.
- **Failure scenario:** A project file whose correlation-matrix result sheet has a `hierarchical-dendrogram` tab (`multivariate_layout.rs:1166`) containing a merge row `[-1e300, 0, 1, 2]`. Compiling the heatmap panics in debug builds (`attempt to negate with overflow`); release wraps and ignores the node. Traced, not run.
- **Evidence:** `merges.push(DendrogramMerge { left: l as isize, ... })` and `let leaf = ((-node) - 1) as usize;`.
- **Suggested fix:** Validate merge ids when extracting (`-(n_leaves as f64) <= l < merges.len()` and integral) and use `node.checked_neg()`.
- **Related:** `S06` (result sheets read from project files).

## Checked, no finding

- **Zero-span domains:** XY/Column expand degenerate auto domains (`crates/chart/src/xy.rs:203-205`, `212-214`); survival/MV `sanitize_range` pads equal bounds (`survival_cat.rs:182-193`); `scales.rs` pads in `nice_linear_bounds` (`scales.rs:891-894`) and rejects `|hi-lo| <= EPSILON` (`scales.rs:858`).
- **NaN/Inf data and bounds:** non-finite data excluded from domains (`xy.rs:192`); explicit bounds must be finite and in the scale domain (`xy.rs:194-201`); `AxisScale::transform` rejects non-finite input and output (`crates/math/src/lib.rs:93-96`, `142`); `RectPt::new` zeroes non-finite geometry (`scene.rs:37-43`); `ChartScene::new` and `compile_graph` reject non-finite canvas sizes (`scene.rs:264-265`, `lib.rs:44`).
- **Log of non-positive values:** excluded from the auto domain (`xy.rs:192`); points omitted with a `non_positive_on_log_axis` warning (`xy.rs:1773-1794`); lower whiskers clamp to the segment floor with `log_axis_floor_clip` (`xy.rs:67-88`, `577-585`); bars on log axes skip non-positive values with a warning (`column_grouped.rs:691-696`, `711-714`).
- **Segment counts:** more than 3 segments truncated (`xy.rs:111`, `scales.rs:795-801`) and rejected at the command layer (`crates/engine/src/cmd_sci.rs:1525-1527`, `AxisSpec::validate`); overlapping segments map a value to the first matching segment (`xy.rs:153-160`), no crash.
