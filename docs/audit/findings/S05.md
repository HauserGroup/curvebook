### R1-S05-01 · S1 · Ragged tables pass load validation; `row_count()` reads only the first column and consumers index the others → panic

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/doc/src/archetypes.rs:1002` (`MultipleVariablesTable::row_count`). The same pattern is at `archetypes.rs:174`, `:331`, `:433`, `:501`, `:690` and `:1065`.
- **Category:** no-panic
- **Defect:** Every archetype assumes its columns are rectangular: the same row count in every data set, variable or group, and the subcolumn width that the mode implies. Only the constructors enforce this. Nothing in `lumencraft-doc` re-checks it after `serde` deserialization, and the loader's `validate_project_document` checks each column only against `MAX_ROWS`/`MAX_SUBCOLUMNS` (`crates/format/src/archive.rs:565–574`, `:613–617`). So `row_count()`, which reads only the first column, can be smaller or larger than any other column.
- **Failure scenario:** Build a `.lumencraft` file whose `MultipleVariables` sheet has a response variable with 6 rows and a categorical factor variable with 3 rows. `open_project_bytes` accepts it. A Multifactor ANOVA on it (`run_factorial_anova`) loops `r in 0..mv.row_count()` and indexes `mv.variables[c_idx].cells[r]` (`crates/stats/src/anova.rs:2329–2334`). That panics, which aborts on wasm and goes through the engine's panic guard on native. `crates/stats/src/regression.rs:879–885` (GLM predictors) has the same pattern. For XY, a longer second data set loses its extra rows without any message: `x_value_at` returns `None` for `row >= row_count()` (`archetypes.rs:182–184`), so `active_xy_pairs` (`:245–248`) and CSV export skip them.
- **Evidence:** Probe: the crafted archive loaded, then `open OK: row_count=6, var1 len=3` and `panicked at crates/stats/src/anova.rs:2334:50: index out of bounds: the len is 3 but the index is 3`. A second probe loaded a ragged XY sheet with `data_sets[1].cells = [[1.0], [], [Empty, Empty]]` and reported `ragged XY open OK: row_count=1 ds1 rows=3`.
- **Suggested fix:** Add `TableArchetype::validate()` (and `DataSheet::validate()`) in `lumencraft-doc` that checks the same invariants as the constructors: equal row counts across columns, `x_cells`/`times`/`row_titles`, each row's width equal to the mode's subcolumn count, and the mode allowed for the kind. Call it from `validate_project_document`. Separately, the stats indexers should use `.get(r)`.
- **Related:** S02 (`anova.rs:2334`, `regression.rs:885`), S06 (`archive.rs` validator), R1-S05-03, R1-S05-05

### R1-S05-02 · S1 · `transpose_cell_grid` turns a ragged grid into a dense `max_cols × rows` grid with no cap, so a ~200 KB CSV can abort the app

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/doc/src/links.rs:337–353`
- **Category:** resources
- **Defect:** `transpose_cell_grid` allocates `vec![vec![Cell::empty(); grid.len()]; max_cols]`. For a ragged grid, the output size is (longest row) × (row count), which grows with the square of the input size. Neither it nor its caller in the import pipeline checks a cell budget first.
- **Failure scenario:** `table.importCsv` reads its text from `csv`/`text` or from a `path` (`crates/engine/src/cmd_data.rs:2104–2110`), with `sheet_id` naming an existing sheet and `transpose: true`. The CSV has one line of N fields followed by N lines of one field each. The text goes through `apply_import_link_pipeline` → `transpose_cell_grid` (`crates/transform/src/import.rs:160–161`) before any placement or budget check. With N = 50 000 (about 200 KB of text), the result has 2.5·10⁹ cells × 32 B ≈ 80 GB, so the allocation fails and the process aborts. On wasm it aborts much sooner. A linked external file is refreshed through the same path.
- **Evidence:** Probe through `Session::execute("table.importCsv", {transpose:true, ...})`: with 12 000 bytes of text the peak RSS was 300 MB; with 24 000 bytes it was 1 189 MB. Doubling the input quadrupled the memory, and both calls returned `Ok("imported CSV into data sheet")`. Calling `transpose_cell_grid` directly turned 6 000 input cells into a 3000×3001 grid (9 003 000 cells, 32 B each).
- **Suggested fix:** Make `transpose_cell_grid` fallible. Have it take a cell budget (for example `MAX_IMPORT_CELLS`), compute `max_cols.checked_mul(rows)` and return an error when the result is over the budget. Callers should also check the budget before transposing.
- **Related:** S04 (`transform/src/import.rs:160`), S07 (`cmd_data.rs:2141–2163`), X1

### R1-S05-03 · S1 · `XColumnMode::Numbers { subcolumn_mode: RawReplicates(n) }` is not bounded after load, so saving loops `n` times

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/doc/src/archetypes.rs:120–128` (`XColumnMode::subcolumn_count`). The only bound is in the constructor at `archetypes.rs:150–152`.
- **Category:** no-panic
- **Defect:** `XyTable::new_with_x_mode` checks the X subcolumn mode, but a deserialized `XyTable` is never re-checked. The loader validates `y_subcolumn_mode` (`crates/format/src/archive.rs:520`) and the actual `x_cells` row widths (`:521`), but not `x_mode`. So `x_mode.subcolumn_count()` can be any `usize`. Callers use it as a loop bound or an allocation size.
- **Failure scenario:** Open a `.lumencraft` file whose XY sheet has `"x_mode": {"Numbers": {"subcolumn_mode": {"RawReplicates": 18446744073709551615}}}`. `open_project_bytes` accepts it. The next save (`save_archive_bytes` → `export_datasheet_to_csv`, `crates/format/src/archive.rs:192`) runs `for s in 0..x_subs` and pushes one header string per iteration (`crates/format/src/csv.rs:436–437`). Memory grows until the process aborts, and every unsaved sheet in the session is lost. A paste into that sheet instead calls `vec![Cell::empty(); x_subs]` in `crates/transform/src/import.rs:490–493`, which panics with "capacity overflow".
- **Evidence:** Probe: the crafted archive gave `open_project_bytes OK; x_mode.subcolumn_count() = 18446744073709551615`. With bounded values, CSV export time and size grow linearly past `MAX_SUBCOLUMNS = 512`: 512 → 3 476 B in 83 µs; 200 000 → 1.9 MB in 21 ms; 2 000 000 → 20.9 MB in 231 ms.
- **Suggested fix:** The `validate()` from R1-S05-01 should also call `subcolumn_mode.validate()` for `XColumnMode::Numbers` and require each `x_cells` row to be exactly `x_mode.subcolumn_count()` wide.
- **Related:** S06 (`archive.rs:516–522`), S04, R1-S05-01

### R1-S05-04 · S2 · `clone_structure` with `override_replicates` turns `Mean/SD/N` cells into raw replicates

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/doc/src/links.rs:375–379` (XY), `:392–396` (Grouped), `:480–481` (`reset_data_sets`)
- **Category:** wrong-result
- **Defect:** `override_replicates: Some(n)` replaces the mode with `RawReplicates(n)` whatever the old mode was. Cells are cleared only when the width changes. When a pre-summarized mode (always 3 wide) becomes `RawReplicates(3)`, the cells stay and the Mean, SD/SEM and N values become three replicate observations. Two related problems: on `Column`, `Contingency`, `Survival`, `PartsOfWhole` and `MultipleVariables` sheets the override is ignored without an error (`:381–387`, `:398–435`), and when the width does change the Y values are cleared even if `clear_y_values` is `false` (`:480–481`, `:446–447`).
- **Failure scenario:** `sheet.clonePipeline {sheet_id, clear_y_values:false, override_replicates:3}` (`crates/engine/src/cmd_data.rs:956–966`, `:1012–1020`) on an XY `MeanSdN` sheet with row `[100, 5, 12]`. `clear_results` follows `clear_y_values`, so the cloned analyses and fits recompute on the replicates `(x, 100), (x, 5), (x, 12)` and show the results as normal. The only visible sign is that the subcolumn headers change from Mean/SD/N to Y1/Y2/Y3.
- **Evidence:** Probe: `clone mode RawReplicates(3), active_xy_pairs=[(1.0, 100.0), (1.0, 5.0), (1.0, 12.0)]`. On a `Column` sheet `override_replicates: Some(4)` gave `mode Single`, with no error.
- **Suggested fix:** When the source mode is pre-summarized and `override_replicates` is set, either require `clear_y_values` or return an error. Return `IncompatibleSubcolumnMode` for kinds that cannot take raw replicates, instead of ignoring the override.
- **Related:** S07 (`sheet.clonePipeline`)

### R1-S05-05 · S2 · A `Column` table's subcolumn mode is not checked against its kind after load; extra replicates are ignored without a message

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/doc/src/lib.rs:107–117` (`TableKind::allows_subcolumn_mode`, used only by the constructor at `crates/doc/src/archetypes.rs:310–313`). The consumer is `archetypes.rs:348–353`.
- **Category:** wrong-result
- **Defect:** `ColumnTable::new_with_subcolumns` rejects `RawReplicates(n)`, `MeanLowHigh` and the other modes not allowed for `Column`. A deserialized `ColumnTable` can carry any of them, because the loader checks only the subcolumn count (`crates/format/src/archive.rs:525–530`). Column-table readers assume one value per row and read `subs.first()`.
- **Failure scenario:** A `.lumencraft` file from a third-party writer or a hand edit has a `Column` sheet with `subcolumn_mode: RawReplicates(3)` and rows `[1, 2, 3]`. It opens without warning. `active_column_values` and `stats::common::extract_numeric_columns` (`crates/stats/src/common.rs:222–226`) use only `1`. Every *t*-test, ANOVA and descriptive analysis on that sheet then runs on a third of the data, with no warning.
- **Evidence:** Probe: `open OK: mode RawReplicates(3), allowed=false, active_column_values=[1.0]`.
- **Suggested fix:** The doc-level `validate()` from R1-S05-01 should reject any mode for which `kind.allows_subcolumn_mode(mode)` is false. This also covers `Grouped` + `Single`, which the constructor at `archetypes.rs:410` rejects.
- **Related:** S06, S02, R1-S05-01

### R1-S05-06 · S2 · `ordered_levels_with` is quadratic in the number of distinct levels

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/doc/src/archetypes.rs:880` (linear `entries.iter_mut().find` per cell) and `:906–916` (`Explicit` comparator calls `order_list.iter().position` twice per comparison)
- **Category:** resources
- **Defect:** Counting levels takes O(rows × distinct levels). An `Explicit` order takes O(L² log L) to sort. No cache or cap applies to either.
- **Failure scenario:** A `MultipleVariables` sheet at the documented `MAX_ROWS = 1 000 000` has a subject-ID text column, which is inferred as `Categorical`. Calls that reach `ordered_levels_with` each take about 17 minutes by extrapolation from the measured times, and the UI or CLI hangs: a Multifactor ANOVA or Kaplan–Meier grouping on it (`crates/stats/src/anova.rs:2321`, `survival.rs:1358`), the MV graph's categorical axis or colour (`crates/chart/src/multivariate_layout.rs:118`), or the Variables inspector (`crates/ui-egui/src/grid_view.rs:312`).
- **Evidence:** Probe with distinct `S0000000…` tokens: EntryOrder took 99 ms at 10k, 404 ms at 20k, 1.67 s at 40k and 6.42 s at 80k levels. Doubling the levels made it about 4× slower. Explicit order took 72 ms at 5k, 298 ms at 10k and 1.16 s at 20k.
- **Suggested fix:** Count with a `HashMap<String, usize>` from token to entry index. For `Explicit`, build a `HashMap` from level to rank once and sort by that key.
- **Related:** S02, S08

### R1-S05-07 · S3 · `SummarizedPoint::reconstruct` returns `Ok` for impossible moments

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/doc/src/cell.rs:298–310`
- **Category:** wrong-result
- **Defect:** The function checks only `n >= 1` and `spread >= 0`. It returns `Ok(Some(..))` in three cases where the moments are not valid:
  - `sd` or `ss_within` overflows to `+Inf`.
  - `N` is not a whole number, which gives a fractional `df_within`.
  - Under `MeanCvN` the mean is 0, so `SD = 0` whatever %CV was entered.
- **Failure scenario:**
  - `MeanSdN` row `[10, 1e155, 3]` gives `ss_within = inf`. `MeanSemN` row `[10, 1e200, 1e250]` gives `sd = inf`. The chart draws error bars of `±inf` with no `invalid_pre_summarized_point` warning (`crates/chart/src/xy.rs:457–486`).
  - `MeanSdN` row `[10, 2, 2.5]` (a typing error in N) gives `df_within = 1.5`. The CI error bar then uses a *t* quantile at 1.5 df.
  - `MeanCvN` row `[0, 20, 5]` gives `sd = 0`. The bar has zero width, as if the spread were exactly zero.
  - The fit's `1/SD²` weighting rejects non-finite or zero SD (`crates/fit/src/solver.rs:459–465`), so the fit shows a signal. The chart and AUC (`crates/transform/src/curve.rs:104–106`) do not.
- **Evidence:** Probe output:
  - `N=2.5 -> Ok(Some{sd: 2.0, n: 2.5, ss_within: 6.0, df_within: 1.5})`
  - `SD=1e155,N=3 -> Ok(Some{ss_within: inf, ..})`
  - `SEM=1e200,N=1e250 -> Ok(Some{sd: inf, ss_within: inf, ..})`
  - `CV=20,mean=0 -> Ok(Some{sd: 0.0, ss_within: 0.0, ..})`
- **Suggested fix:** Add `SummaryPointError` variants for a non-finite derived SD/SS, for a non-integer `N`, and for %CV with a zero mean. The guide (§2.1) already says invalid points are "flagged as invalid for parametric inference".
- **Related:** S08 (chart error bars), S03

## Checked, no finding

- **Exclusion masks stay aligned with cells.** The mask is a field of each `Cell` (`crates/doc/src/cell.rs:50–53`), so it moves with its value. No row/column insert or delete command exists at this base (the engine's `table.*` command ids have none). Paste growth pads whole columns (`crates/transform/src/import.rs:548–556`, `crates/format/src/csv.rs:1379–1383`).
- **Indexing from row/column/subcolumn coordinates in the doc crate** uses `.get`/`.get_mut` throughout: `archetypes.rs:70–76`, `:1144–1198`; `links.rs:196–252`, `:265–299` (clamped, with `usize::MAX` handled; `subcolumn_upper_index` caps at `MAX_SUBCOLUMNS`, `:363`); `reorder_vec` (`project.rs:290–308`).
- **Sheet ID uniqueness and caps in the API.** `ProjectDocument::ensure_can_insert` (`project.rs:101–113`) checks for an empty id, duplicates across all five sections, and `MAX_SHEETS_PER_PROJECT`. After load, `validate_project_document` checks the same things (`format/src/archive.rs:470–500`).
- **Dimension caps in constructors and growth helpers:** `validate_rows`/`validate_data_sets`/`validate_subcolumns` (`error.rs:39–63`) are called by every archetype constructor, by `DataSetColumn::ensure_rows` (`archetypes.rs:79–86`), by `clone_structure` (`links.rs:309–311`) and by `reset_data_sets` (`links.rs:475`).
- **Freeze guard on `DataSheet` mutators:** `set_title`, `set_cell`, `set_excluded`, `set_x_or_time_cell`, `set_x_or_time_excluded` and `add_linked_region` all call `ensure_mutable` (`links.rs:178–259`). The fields are `pub`, so whether the engine respects the guard is a question for S07.
- **Template hooks parser:** `extract_template_hooks` slices only at byte offsets returned by `find("{{")`/`find("}}")` (ASCII), so it cannot split a UTF-8 character (`ids.rs:169–184`).
- **Natural sort comparator** (`archetypes.rs:940–968`) is a total order: a digit run starts with `0`–`9`, and no non-digit character lies inside that range, so `sort_by` cannot see an inconsistent order.
- **Generated X sequences:** the geometric exponent is clamped to `i32::MAX` and the result is checked with `is_finite` (`archetypes.rs:189–195`).
- **`ConfidenceLevel` deserialization** rejects 0 and 100 (test at `lib.rs:721–722`). `NonlinearFitSpec::clamped_max_iters` caps iterations (`analysis.rs:624–626`).
- **`SummarizedPoint` with `N < 1`, missing `N`, or negative spread** returns explicit errors, as the guide (§2.1) requires (`cell.rs:294–301`).
- **Not traced to a failure, so not reported:** duplicate `LinkedDataRegion.id`, `NoteId`, `LayoutItem` ids and case-insensitive duplicate `InfoConstant` names are accepted on load and by `add_linked_region`. The engine handles regions by index (`engine/src/dag.rs:300–345`), and I found no consumer that misbehaves on a duplicate.

## Observations for other slices (not S05 findings)

- **S04/S07:** `transform/src/import.rs:488–493` grows XY `x_cells` with `resize_with(min_rows, …)` before `DataSetColumn::ensure_rows` validates `min_rows`. Here `min_rows = anchor.row + grid.len()` (`import.rs:452–453`), and `anchor.row` comes straight from `start_row` (`engine/src/cmd_data.rs:2876`). Probe: `table.importCsv {sheet_id: <xy>, text: "1\n", start_row: 1e12}` returned nothing within 60 s and was killed by `timeout` (exit 124).
- **S04:** `transform/src/import.rs:437–470` `place_grid` never adds columns and drops cells beyond the last existing column. In R1-S05-02's probe, a 3000-column result placed into a one-column `Column` sheet returned `Ok`.
- **S02:** `ContingencyTable::count_at` accepts any whole `f64` up to `2^64` (`doc/src/archetypes.rs:516`). `analyze_contingency` totals counts with an unchecked `u64` `sum()` (`stats/src/categorical.rs:805`), which wraps in release builds when two cells are each about `1e19`. This was traced by reading the code, not run.
