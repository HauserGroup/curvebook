### R2-S03-01 · S1 · `OneSiteCompetitionLigandDepletion` omits nonspecific bound radioligand from `eval`/`grad` (Swillens 1995)

- **Base:** fda1cc0106092834d97b53289ec2a99c1bf0439c
- **Location:** `crates/fit/src/library/pharma.rs:1773`, `crates/fit/src/library/pharma.rs:1844-1849`, `crates/fit/src/library/pharma.rs:1876-1878` (mirrored in `crates/fit/src/tex_format.rs:498-506`) at that base (introduced in `e832bc7` and `f145a16`)
- **Category:** wrong-result
- **Defect:** `OneSiteCompetitionLigandDepletion` returns only specific bound radioligand $B^*_{\text{sp}} = \frac{R}{K_{d,\text{nM}}(1+\text{NS}) + R} \cdot \text{HotNM}$ instead of total bound radioligand $Y = B^*_{\text{sp}} + B^*_{\text{ns}} = \frac{R + \text{NS} \cdot K_{d,\text{nM}}}{K_{d,\text{nM}}(1+\text{NS}) + R} \cdot \text{HotNM}$, making `KdNM` and `NS` algebraically collinear and driving $Y \to 0$ at saturating competitor even when `NS > 0`.
- **Failure scenario:** Under Swillens (1995, *Mol. Pharmacol.* 47(6):1197–1203), free radioligand satisfies $L^* = \text{HotNM} - B^*_{\text{sp}} - B^*_{\text{ns}}$ with $B^*_{\text{ns}} = \text{NS} \cdot L^*$ and $B^*_{\text{sp}} = \frac{R \cdot L^*}{K_{d,\text{nM}}}$, so $L^* = \frac{K_{d,\text{nM}}}{K_{d,\text{nM}}(1+\text{NS}) + R}\text{HotNM}$ and measured total bound radioligand is $B^*_{\text{tot}} = \frac{R + \text{NS} \cdot K_{d,\text{nM}}}{K_{d,\text{nM}}(1+\text{NS}) + R}\text{HotNM}$. Because `eval` omits the $+\text{NS}\cdot K_{d,\text{nM}}$ numerator term, at high competitor ($I \to \infty \implies R \to 0$) predicted binding collapses to `0` instead of the nonspecific plateau $\frac{\text{NS}}{1+\text{NS}}\text{HotNM}$; furthermore, `kd_nm` and `ns` enter `eval` exclusively through the product `kd = kd_nm * (1.0 + ns)`, so unfixed `KdNM`/`NS` Jacobian columns (`out[2]` and `out[4]`) are strictly linearly dependent (rank-deficient). Fitting noiseless Swillens data (`Rt = 5.0 nM`, `HotNM = 2.0 nM` fixed, `KdNM = 1.0 nM` fixed, `LogKi = -8.0` (`Ki = 10 nM`), `NS = 0.25` fixed) silently biases `Rt` to `5.75 nM` and `LogKi` to `-7.50` (`Ki = 31.62 nM`, a **3.16×** error in $K_i$).
- **Evidence:**
  ```rust
  let kd = kd_nm * (1.0 + ns);
  ...
  fn eval(&self, x: &[f64], params: &[f64], _dataset_index: usize) -> Option<f64> {
      let x0 = x.first().copied()?;
      let st = Self::solve_free_receptor(x0, params)?;
      let y = (st.r / (st.kd + st.r)) * st.hot_nm;
      y.is_finite().then_some(y)
  }
  ```
  Oracle (`Python 3.15.2` exact Swillens mass-balance + Gauss–Newton least squares on `X = [-12..-4]`):
  `True Swillens Y at X=-4 (100 uM competitor): 0.400001 nM; current model Y at X=-4: 0.000718 nM; fitted Rt = 5.7495 nM (true 5.0), fitted LogKi = -7.5000 / Ki = 31.62 nM (true -8.0 / 10.0 nM)`.
- **Suggested fix:** Compute total bound radioligand `let y = ((st.r + st.ns * st.kd_nm) / (st.kd + st.r)) * st.hot_nm;` in `eval`, update `out[0..5]` in `grad` using $\frac{\partial y}{\partial R} = \frac{\text{HotNM} \cdot K_{d,\text{nM}}}{d_d^2}$ plus explicit partial derivatives of $(R + \text{NS}\cdot K_{d,\text{nM}})/(K_{d,\text{nM}}(1+\text{NS}) + R)$ with respect to `KdNM` and `NS`, and update the TeX display formula in `crates/fit/src/tex_format.rs:498-506` to match.
- **Related:** none.

### R2-S03-02 · S1 · Unbounded recursion in `tex_format.rs` DSL parser, renderer, and `DslExpr` drop overflows thread stack on untrusted equations

- **Base:** fda1cc0106092834d97b53289ec2a99c1bf0439c
- **Location:** `crates/fit/src/tex_format.rs:1192-1199`, `crates/fit/src/tex_format.rs:1210-1306`, and `crates/fit/src/tex_format.rs:1308-1380` at that base (introduced in `f145a16`)
- **Category:** no-panic
- **Defect:** `tex_format.rs` introduces a second recursive-descent DSL parser (`parse_dsl_expr` / `parse_unary` / `parse_primary`), recursive renderer (`render_dsl_tex` / `render_dsl_bin`), and recursive heap-boxed `DslExpr` enum with default recursive `Drop`, with **no** token-length, AST-depth, or iterative drop guard.
- **Failure scenario:** Two concrete paths trigger process-aborting stack overflow from untrusted input:
  1. **Untrusted `.lumencraft` project open without running the solver:** In `crates/chart/src/equation_box.rs:127`, `resolve_model_equation` calls `format_model_equation_tex(&spec.equation_id, spec.custom_dsl.as_deref(), ...)` whenever a persisted `ModelEquation` annotation has `status` `UpToDate` or `Stale`. A `.lumencraft` document whose `custom_dsl` is `"Y = " + "(".repeat(20_000) + "X" + ")".repeat(20_000)` or `"Y = " + "-".repeat(20_000) + "X"` bypasses `crates/fit/src/dsl.rs` (`MAX_PARSE_DEPTH = 128`) completely and recurses 20,000 frames deep in `parse_primary` / `parse_unary`, aborting the process on project open or chart render.
  2. **Flat left-associative custom DSL chains that pass `dsl.rs` compilation:** `parse_add_sub` in `crates/fit/src/tex_format.rs:1214` parses `Y = X + X + ... + X` (e.g., 2,000 terms, well under `dsl.rs`'s `MAX_AST_NODES = 4_096` and at parse depth `1`) into a left-skewed `DslExpr::Bin` spine of depth 2,000, which then recurses 2,000 frames deep in `render_dsl_tex` and in compiler-generated `Drop::drop` for `Box<DslExpr>`, overflowing worker threads (default 2 MiB stack).
- **Evidence:**
  ```rust
  #[derive(Clone, Debug)]
  enum DslExpr {
      Num(String),
      Ident(String),
      Neg(Box<DslExpr>),
      Bin(DslBinOp, Box<DslExpr>, Box<DslExpr>),
      Call(String, Vec<DslExpr>),
  }
  ...
  Some(DslTok::Minus) => {
      *pos += 1;
      Some(DslExpr::Neg(Box::new(parse_unary(tokens, pos)?)))
  }
  ```
- **Suggested fix:** Enforce explicit node-count and recursion-depth budgets (e.g., `MAX_DSL_TEX_DEPTH = 64`, `MAX_DSL_TEX_TOKENS = 4_096`) across `parse_dsl_expr` and `render_dsl_tex` (falling back to `fallback_custom_dsl_tex` when exceeded), and either store `DslExpr` nodes in a flat `Vec` arena or implement an explicit iterative `Drop` for `DslExpr`.
- **Related:** `R1-S03-04`.

### R2-S03-05 · S1 · Four built-in curve TeX equations in `tex_format.rs` (`logarithmic_curve`, `lorentzian`, `probit_line`, `power_series`) contradict the actual fitted equations in `curves.rs`

- **Base:** fda1cc0106092834d97b53289ec2a99c1bf0439c
- **Location:** `crates/fit/src/tex_format.rs:816-821`, `crates/fit/src/tex_format.rs:903-904`, and `crates/fit/src/tex_format.rs:909` at that base (introduced in `f145a16`)
- **Category:** wrong-result
- **Defect:** `format_peak_curve_tex` and `format_line_poly_curve_tex` emit mathematically different equations (including swapped parameter roles, missing `0.5` FWHM scaling, missing `100 ×` percentage scaling, and a nonexistent parameter `c`) from what `crates/fit/src/library/curves.rs` actually fits.
- **Failure scenario:** When a user fits any of these four built-in models and places a `ModelEquation` annotation (symbolic or substituted) on a chart:
  1. **`logarithmic_curve` (`crates/fit/src/tex_format.rs:904` vs `crates/fit/src/library/curves.rs:1084`):** `curves.rs` fits `y = a * ln(x) + b` (`a` is the slope on `ln(X)`, `b` is the intercept). `tex_format.rs` renders `Y = a + b \cdot \ln(X)`, **swapping the fitted numeric values of `a` and `b`** in substituted mode (`a = 5, b = 1` renders as `Y = 5 + 1 \cdot \ln(X)` when the fitted curve is `Y = 5 \ln(X) + 1`).
  2. **`lorentzian` (`crates/fit/src/tex_format.rs:816-821` vs `crates/fit/src/library/curves.rs:743-744`):** `curves.rs` parameterizes `Width` as FWHM (`u = (x - center) / (0.5 * width)`, `y = amp / (1 + u^2)`), whereas `tex_format.rs` omits `0.5` (`((X - Center) / Width)^2`), misstating the fitted peak width by a factor of `2`.
  3. **`probit_line` (`crates/fit/src/tex_format.rs:909` vs `crates/fit/src/library/curves.rs:1354`):** `curves.rs` fits percentage response `y = 100.0 * normal_cdf(slope * x + intercept)`, whereas `tex_format.rs` renders `Y = \Phi(\text{Slope} \cdot X + \text{Intercept})`, off by a factor of `100×`.
  4. **`power_series` (`crates/fit/src/tex_format.rs:903` vs `crates/fit/src/library/curves.rs:1045-1052`):** `PowerSeries` only has 2 parameters `["a", "b"]` and fits `y = a * x^b`, whereas `tex_format.rs` appends `+ c`, leaving a literal dangling `+ c` in substituted equations (`Y = 2.5 \cdot X^{1.8} + c`).
- **Evidence:**
  ```rust
  "lorentzian" => format!(
      "Y = \\frac{{{}}}{{1 + (\\frac{{X - {}}}{{{}}})^{{2}}}}",
      ctx.val("Amplitude", "\\text{Amplitude}"),
      ctx.val("Center", "\\text{Center}"),
      ctx.val("Width", "\\text{Width}"),
  ),
  ...
  "power_series" => format!("Y = {} \\cdot X^{{{}}} + {}", ctx.val("a", "a"), ctx.val("b", "b"), ctx.val("c", "c"),),
  "logarithmic_curve" => format!("Y = {} + {} \\cdot \\ln(X)", ctx.val("a", "a"), ctx.val("b", "b")),
  ...
  "probit_line" => format!("Y = \\Phi({} \\cdot X + {})", ctx.val("Slope", "\\text{Slope}"), ctx.val("Intercept", "\\text{Intercept}")),
  ```
- **Suggested fix:** Align all four templates in `crates/fit/src/tex_format.rs` with `crates/fit/src/library/curves.rs`: `"logarithmic_curve"` -> `Y = {a} \cdot \ln(X) + {b}`, `"lorentzian"` -> `(X - {Center}) / (0.5 \cdot {Width})` (using `ctx.factor` for `Width`), `"probit_line"` -> `Y = 100 \cdot \Phi(...)`, and `"power_series"` -> `Y = {a} \cdot X^{{{b}}}` (removing `+ c`).
- **Related:** none.

### R2-S03-06 · S2 · Broken operator precedence / missing parentheses in substituted TeX equations (`sinc_wave`, scientific-notation divisors in scripts, and negated products)

- **Base:** fda1cc0106092834d97b53289ec2a99c1bf0439c

- **Suggested fix:** Use `ctx.denom("Width", "\\text{Width}")` in `sinc_wave`; in `DslExpr::Num` and `DslExpr::Ident`, parenthesize whenever `(parent_prec >= 3 && (s.starts_with('-') || s.contains("\\times"))) || (parent_prec >= 4 && s.contains("\\times"))`; and in `DslExpr::Neg`, check `pos_body.contains("\\times") || pos_body.contains("\\cdot") || pos_body.contains('/')` when `parent_prec >= 3`.
- **Related:** none.

### R2-S03-08 · S2 · `tex_ident` emits unescaped identifiers inside `\text{...}`, causing `_`, `^`, `{`, `}`, and `*` in parameter/variable names to corrupt TeX markup
