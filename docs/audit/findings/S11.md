### R1-S11-01 · S1 · The desktop app opens a crash-recovery journal but never records a command, so a crash loses all work since launch

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft/src/main.rs:171-193` (journal held in `startup.journal`, never passed on); `crates/ui-egui/src/lib.rs:126-127` (`UiApp::execute_command` calls `Session::execute`, not `execute_and_record`)
- **Category:** data-loss
- **Defect:** `launch_application` opens the WAL journal, then hands only the `Session` to `UiApp::from_session` (`main.rs:173`) and keeps the journal unused until `close_startup_recovery_cleanly` (`main.rs:193`), so no control or UI command is ever appended to `ops.journal`; the only write is the final snapshot on a clean `app.quit`.
- **Failure scenario:** Launch `lumencraft --portable-dir D --control 47391` (or with no `--portable-dir`, the standard data dir). Run `sheet.createData` over the control socket. The process is then killed (SIGKILL, OOM killer, power loss, a panic caught nowhere, Ctrl+C in a terminal). On the next launch, recovery restores the snapshot from the *previous* clean exit and the new sheet is gone. README/`docs/gaps.md` G2 advertise "WAL crash recovery". Launches that name files skip the journal entirely (`main.rs:217-219`), so those sessions have no protection either.
- **Evidence:** Probe output: after `sheet.createData` returned `ok`, the recovery directory contained only `lumencraft.lock` (`ops.journal` absent). After SIGKILL and removing the stale lock (see R1-S11-02), `doc.inspect` on relaunch did not contain the sheet. The engine provides `Session::execute_and_record` (`crates/engine/src/lib.rs:214-225`), but nothing in `apps/` or `crates/ui-egui` calls it (grep for `execute_and_record|journal` in `crates/ui-egui/src` finds only unrelated "journal preset" text).
- **Suggested fix:** Move the journal into `UiApp` (or the control loop) and route every mutating command through `execute_and_record`, with periodic `checkpoint_journal`; decide and document whether file-backed sessions are journaled too.
- **Related:** R1-S11-02, R1-S11-03, R1-S06-02 (checkpoint replay), S10 (control dispatch).

### R1-S11-02 · S2 · Any crash or startup error leaves `lumencraft.lock` behind, and the app then refuses to start for 5 minutes

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft/src/main.rs:171-193` (early `?` returns at `:174`, `:182`, `:184`, `:190` skip `close_startup_recovery_cleanly`); `apps/lumencraft/src/main.rs:20` (`RECOVERY_LOCK_TTL_MS = 300_000`); `crates/format/src/recovery.rs:437-443`
- **Category:** data-loss
- **Defect:** The lease is time-only (no owner-liveness check) and is released only by `close_cleanly`; every error path after the journal is opened at `main.rs:171` drops it unreleased (the journal has no `Drop` release), so the next launch fails with "journal lock … is actively held by `lumencraft-pid-N`" until the TTL expires, even though process N is dead.
- **Failure scenario:** (a) `--control 7979` while port 7979 is taken: the bind fails at `main.rs:190`, the process exits, and every relaunch within 5 minutes exits with code 1. (b) A `shortcuts.json` the app rejects (R1-S11-05): the error at `main.rs:174` leaves the lock, so after the user deletes the bad file the app still refuses to start. (c) Any crash or kill (R1-S11-01): the user restarts immediately and is refused. In every case the researcher cannot start the app to recover their session for 5 minutes. A transient `accept()` error in `serve_control_listener` (`crates/ui-egui/src/control_io.rs:293-294`) also ends the session through `main.rs:190` without writing the final snapshot.
- **Evidence:** Probe: binding a listener on 47393, then `lumencraft --portable-dir P --control 47393` → `rc 1 … Address already in use`; immediately `lumencraft --portable-dir P --headless-once` → `rc 1 … journal lock lumencraft.lock is actively held by lumencraft-pid-27507 until 1794662811633ms`. The same occurred after a rejected `shortcuts.json` and after SIGKILL.
- **Suggested fix:** Close or release the journal on every exit path (a guard that releases in `Drop`), and treat a lease whose owner PID is no longer running on this host as stale.
- **Related:** R1-S11-01, R1-S06-03 (a different cause of the same startup refusal), R1-S06-08.

### R1-S11-03 · S2 · The lease is never renewed: a second instance steals it after 5 minutes, and whichever instance quits last overwrites the other's recovery snapshot

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft/src/main.rs:20`, `:171`, `:193`, `:242-248`; `crates/format/src/recovery.rs:605` (`renew_lease`, never called from `apps/`), `:613-618` (`close_cleanly` writes the snapshot before `release_lease`)
- **Category:** data-loss
- **Defect:** The app takes a 300 s lease once and never renews it, so a running instance's lease becomes "stale" after 5 minutes; a later instance evicts it and both then write `snapshot.lumencraft` on exit (`close_cleanly` writes before checking ownership), so the last writer wins.
- **Failure scenario:** Instance A runs a control session (no files) for an hour. Instance B is launched more than 5 minutes after A: it steals the lease and loads the *old* snapshot. A quits: it writes A's snapshot, then fails to release (exit code 1, "failed to close crash-recovery journal cleanly"). B quits: it overwrites the snapshot with B's document. The next launch shows only B's work; A's unsaved work is gone. Launched within 5 minutes, B instead refuses to start; `--new-instance` is parsed (`main.rs:114-117`) but has no effect.
- **Evidence:** Probe crate using `Session::open_dir_with_recovery` with TTL 300 000 (A at t0, B at t0+360 000, as `main.rs` would with real time): `B started; stole lease from: Some("lumencraft-pid-A")`, `A close: Err("… cannot release journal lock owned by lumencraft-pid-B from lumencraft-pid-A")`, `B close: Ok(())`, `next launch sees sheets: ["work-of-B"]` (A had created `work-of-A`).
- **Suggested fix:** Renew the lease on a timer (or on every command) while running, and have `close_cleanly` check ownership before writing the snapshot; give each instance its own recovery slot if concurrent instances are supported.
- **Related:** R1-S06-07 (notes the missing renewal as a side effect of the eviction race), R1-S11-01.

### R1-S11-04 · S2 · Several files on the command line: earlier projects are silently dropped, and a CSV merged into a project is reported as unmodified

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft/src/main.rs:363-421` (`load_startup_session`), specifically `:366-371`, `:394-406`, `:418-420`
- **Category:** wrong-result
- **Defect:** Each `.lumencraft`/`.lctemplate`/`.prism`/`.pzfx` argument replaces `primary_doc`, discarding everything loaded before it without a message, and CSV/TSV arguments after a `.lumencraft` are merged into it while `set_file_path(Some(path), true)` marks the session clean.
- **Failure scenario:** `lumencraft --control 7979 a.lumencraft b.lumencraft` opens only `b` (no warning that `a` was ignored). `plate.csv a.lumencraft` drops the imported CSV. `a.lumencraft plate.csv` shows `a`'s sheets plus `data-2`, while `doc.inspect` reports `dirty: false`, so a client or a quit prompt that checks the dirty flag will not save, and `a.lumencraft` on disk never receives the imported table.
- **Evidence:** Probe (two projects each saved with one sheet, plus a 2-column CSV): `['a.lumencraft', 'b.lumencraft'] -> sheets ['sheet-from-b'] dirty False`; `['plate.csv', 'a.lumencraft'] -> sheets ['sheet-from-a'] dirty False`; `['a.lumencraft', 'plate.csv'] -> sheets ['sheet-from-a', 'data-2'] dirty False`.
- **Suggested fix:** Reject more than one project-type file (or open each in its own session), and mark the session dirty when any CSV/TSV was merged into an opened archive.
- **Related:** none.

### R1-S11-05 · S2 · An unreadable or rejected `shortcuts.json` / `preferences.json` stops the app from starting, including a valid swapped-shortcut file

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft/src/main.rs:174`, `:328-345`; `crates/ui-egui/src/menus/shortcuts.rs:206-215` (`import_overrides_json` applies overrides one at a time on top of defaults), `:139-146` (`set_shortcut` rejects unknown ids and conflicts)
- **Category:** data-loss
- **Defect:** `load_shortcut_preferences` errors propagate with `?`, so malformed JSON, an override for a command ID this build does not know, or an override that collides with a not-yet-overridden default aborts the whole launch.
- **Failure scenario:** (a) A swap: `{"ui.palette.open":"F6","ui.pane.cycle":"Cmd+K"}` describes a valid end state, but import applies `ui.palette.open = F6` while `ui.pane.cycle` still has its default `F6`, so it fails and the app exits with "shortcut `F6` conflicts with command `ui.pane.cycle`". (b) A portable stick used by a newer build that has an extra command, then by an older build: "unknown command". (c) A truncated `preferences.json` after a disk-full write. In each case the user has no UI path to fix it, and R1-S11-02 then also blocks relaunch for 5 minutes.
- **Evidence:** Probe with `--portable-dir P --headless-once`: swap file → `error: shortcut F6 conflicts with command ui.pane.cycle`, rc 1; `{"ui.removed.command":"Ctrl+J"}` → `error: unknown command ui.removed.command`, rc 1; `NOTJSON` → `error: invalid shortcut overrides JSON`, rc 1; `preferences.json` = `{"theme":` → rc 1.
- **Suggested fix:** Treat preference load failures as warnings (log, ignore the file or the bad entries, continue with defaults), and make `import_overrides_json` clear all overridden bindings before checking conflicts.
- **Related:** S10 (`shortcuts.rs`), R1-S11-02.

### R1-S11-06 · S2 · `LUMENCRAFT_NO_PREFS` and `LUMENCRAFT_CONFIG_DIR` are documented but never read, so "isolated" automation runs share the user's real recovery directory

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `docs/development.md:64-65`; `apps/lumencraft/src/main.rs:250-273`, `:288-320` (only `HOME`, `XDG_*`, `APPDATA`, `LOCALAPPDATA`, `USERPROFILE` are consulted)
- **Category:** contract-drift
- **Defect:** The guide says `LUMENCRAFT_NO_PREFS` disables reading and writing preferences "for isolated CLI/agent test runs" and `LUMENCRAFT_CONFIG_DIR` overrides the configuration and recovery directory, but no code in the repository reads either variable.
- **Failure scenario:** An agent runs `LUMENCRAFT_NO_PREFS=1 lumencraft --control 7979` as documented. The app opens the user's real `…/LumenCraft/recovery` directory, loads the user's recovered workspace into the agent session, applies the user's shortcuts, and on `app.quit` writes the agent-modified document over the user's recovery snapshot (`main.rs:193`). If the user's own instance started within the last 5 minutes, the agent run fails to start instead (R1-S11-03).
- **Evidence:** `grep -rn LUMENCRAFT_NO_PREFS` and `grep -rn LUMENCRAFT_CONFIG_DIR` over the worktree match only `docs/development.md`.
- **Suggested fix:** Implement both variables in `resolve_app_paths` (and skip the journal and preference load under `NO_PREFS`), or remove them from the guide.
- **Related:** S12 (the guide also names `lumencraft-cli`).

### R1-S11-08 · S3 · OS clipboard adapter waits for EOF on `xclip`/`wl-copy` stdout, which the backgrounded clipboard owner keeps open (latent hang)

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/control_io.rs:1655-1683` (`spawn_candidate_with_stdin`: `stdout(Stdio::piped())` then `wait_with_output`), `:1698-1708` (X11/Wayland write candidates), no timeout anywhere in the adapter
- **Category:** resources
- **Defect:** On X11, `xclip -selection clipboard` forks a child that keeps serving the selection and inherits the piped stdout/stderr, so `wait_with_output` does not return until another program takes the clipboard; the print path likewise has no timeout if `lp`/`lpr` blocks on a hung spooler.
- **Failure scenario:** Once `write_os_pasteboard` is wired to a copy command (it is exported from `lumencraft_ui_egui` at `crates/ui-egui/src/lib.rs:28-29` but has no caller at this base), a copy on Linux or FreeBSD under X11 blocks the single-threaded control loop, freezing the app until the user copies something in another application.
- **Evidence:** Code trace only; not run on X11. The fork-and-inherit-stdout behaviour of `xclip` and the resulting hang in callers that capture its stdout is widely reported, for example in the xclip patch tracker ([daemonize properly](https://sourceforge.net/p/xclip/patches/9)) and a [Stack Overflow question](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/44553539/python-script-using-subprocess-and-xclip-hangs-if-piped-in-bash) about the same hang. No command injection: candidates use fixed argument vectors without a shell, and the printer name is checked for a leading `-` (`control_io.rs:1570-1582`).
- **Suggested fix:** Send stdout/stderr of clipboard writers to `Stdio::null()` (or use `xclip -f`/`wl-copy --foreground` semantics deliberately), write stdin from a separate thread, and bound every adapter with a timeout.
- **Related:** S10 (owner of `control_io.rs`).

### R1-S11-09 · S3 · With `HOME` unset, config and recovery fall back to fixed, shared paths under `/tmp`

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft/src/main.rs:293-295` (macOS), `:309-317` (Linux/FreeBSD)
- **Category:** security
- **Defect:** When `HOME` (and `XDG_*`) are unset, the app uses `std::env::temp_dir().join("lumencraft-config" | "lumencraft-data" | "lumencraft")`, a predictable path in a world-writable directory, for preferences and the recovery snapshot.
- **Failure scenario:** On a multi-user Linux host, another local user pre-creates `/tmp/lumencraft-data/recovery` (or makes it a symlink to a directory they can read). The victim runs `env -i lumencraft --control 7979` (or from a systemd unit or cron job without `HOME`). The app loads the planted `snapshot.lumencraft` as the victim's session and, on exit, writes the victim's document into the attacker-controlled directory.
- **Evidence:** Code trace; `create_dir_all` at `main.rs:228` and the directory backend follow the path as given, and no ownership or permission check exists.
- **Suggested fix:** Refuse to enable recovery or preferences without a per-user directory (or use a per-user, 0700 directory and verify ownership), rather than falling back to a shared fixed name.
- **Related:** none.

### R1-S11-10 · S3 · `GridToolState::emit_exclude_selection_intent` sends reading-order bounds that the engine reads as a 3-D box (latent over- and under-exclusion)

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c

### R1-S11-12 · S3 · Drag-to-place comparison brackets guess the compared groups from `x / 48 pt` (latent wrong annotation)

## Checked, no finding

- **Grid index math from scroll and selection coordinates.** `compute_visible_axis_range` (`crates/tools/src/grid.rs:1331-1357`) rejects non-finite or non-positive values, saturates float-to-usize casts and clamps the window to `total_items`; `navigate` clamps stale `active` coordinates (`grid.rs:819-821`) and every `step_*` helper subtracts only after a bounds check (`grid.rs:1359-1394`, `1427-1434`); `normalized_flat_rect` clamps rows and columns to the sheet (`grid.rs:1115-1165`); all cell reads go through `sheet.cell(..)` returning `Option`. In the UI, viewport geometry is not settable from control input (no writer of `viewport_*`/`scroll_*` outside `crates/tools`), so `format_visible_window`'s `Vec::with_capacity` (`grid.rs:748`) stays at about 20×8 cells.
- **Clipboard TSV parse size.** `parse_tsv_clipboard` caps total cells at `MAX_ROWS` before building cells (`grid.rs:1041-1051`); the record splitter allocates in proportion to the input only.
- **Begin/Preview/Commit on canvas tools.** `set_mode` clears the pending bracket and drag (`canvas.rs:208-215`); `end_drag` without `begin_drag` returns `None` (`canvas.rs:355`); `commit_layout_panel_bounds` rejects an out-of-range item index (`canvas.rs:439-441`); `apply_axis_break_resize` rejects out-of-range segments and non-finite shares (`canvas.rs:653-657`). The `f64::clamp(0.05, pair_total - 0.05)` at `canvas.rs:668` would panic on a NaN share, but `length_share` can only enter through JSON (`crates/engine/src/cmd_sci.rs:1563-1564`, `as_f64`), which cannot carry NaN, and `pair_total <= 0.1` is rejected first.
- **Pan/zoom and rulers.** All zoom paths sanitise and clamp (`canvas.rs:270-285`, `621-623`, `986-1007`); `build_ruler_ticks` bounds the span, the major-tick count and the total tick count (`canvas.rs:1200-1256`), and `subdivisions` is never 0 (`canvas.rs:1259-1302`), so `step_idx % subdivisions` cannot divide by zero.
- **Control port parsing and loopback.** `parse_control_port` rejects 0 and out-of-range values (`crates/ui-egui/src/control_io.rs:247-254`); the app binds `127.0.0.1` only (`apps/lumencraft/src/main.rs:189`) and the server re-checks loopback (`control_io.rs:261-281`).
- **`--portable-dir` and `portable.txt`.** An empty value is rejected (`main.rs:124-126`); `portable.txt` contents are ignored, only `is_file()` matters (`main.rs:258-261`); `portable_app_paths` avoids double-nesting `lumencraft-data` (`main.rs:275-286`).
- **Unreadable startup files.** Every read and import error is returned as a message before any session is built (`main.rs:367`, `373-375`, `381-382`, `388-389`, `395`, `400-402`), and unknown extensions are rejected (`main.rs:407-412`); there is no panic path.
- **OS adapter command injection and PATH.** No shell is used; programs and arguments are fixed vectors (`control_io.rs:1686-1752`), and the only user value, the printer name, follows `-d`/`-P` and is checked for a leading `-` (`control_io.rs:1570-1582`). A missing binary returns `Unavailable` (`control_io.rs:1664-1667`). Stdin is written before stdout is read (`control_io.rs:1670-1676`), but `lp`/`lpr` and the clipboard tools read all input before printing short output, so no pipe deadlock was found beyond R1-S11-08.
- **`cursors.toml` consistency.** The five `Cursor` variants (`crates/tools/src/lib.rs:23-34`) match the five `[[cursor]]` entries one to one, with hotspots inside a 16×16 cursor and plain behavioural wording (`crates/tools/src/cursors.toml:4-27`).
- **Web entry point.** `init_web_app` makes no OS, filesystem or socket call and has no fallible step that could panic (`apps/lumencraft-web/src/main.rs:9-16`).
- **`build.rs`.** It only prints `rerun-if-*` directives (`apps/lumencraft/build.rs:5-11`).
