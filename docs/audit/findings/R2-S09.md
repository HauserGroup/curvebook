### R2-S09-01 · S2 · EMF path encoder emits `EMR_POLYBEZIER` and `EMR_MOVETOEX` inside path brackets, breaking curved fills and leaking open `EMR_BEGINPATH` on move-only paths

- **Base:** fda1cc0106092834d97b53289ec2a99c1bf0439c
- **Location:** `crates/render/src/emf.rs:430-493` and `crates/render/src/emf.rs:507-532` at that base (introduced in `97fd998`)
- **Category:** wrong-result
- **Defect:** Inside an `EMR_BEGINPATH`..`EMR_ENDPATH` bracket, `flush_polybezier` emits `EMR_POLYBEZIER` (`iType = 2`, which starts a standalone figure without using or updating current position per MS-EMF §2.3.5.17) instead of `EMR_POLYBEZIERTO` (`iType = 5`), `LineTo` after a curve emits `EMR_MOVETOEX` (`crates/render/src/emf.rs:434`, starting a new open subpath), and move-only `Path2D`s return `Ok(None)` at `:490-492` after emitting `EMR_BEGINPATH` (`:419`) without `EMR_ENDPATH` or `EMR_ABORTPATH`.
- **Failure scenario:**
  1. **Broken curved fills & joins:** Exporting or copying to `.emf` any **Pie/Donut** chart (`crates/chart/src/survival_cat.rs:790-832`: `MoveTo(center) -> LineTo(arc_start) -> CubicTo.. -> Close`), **spline area-under-curve** XY graph (`crates/chart/src/xy.rs:2039-2046`), or **rounded-rectangle** annotation/callout (`crates/chart/src/xy.rs:1366-1382`, `crates/chart/src/scales.rs:2812-2825`) splits the boundary into disconnected subpaths and closes `EMR_CLOSEFIGURE` back to the post-curve `EMR_MOVETOEX`, leaving pie wedges and rounded rectangles hollow (only thin chord slivers filled) and spline area fills diagonally mis-closed.
  2. **Unclosed `EMR_BEGINPATH`:** Exporting a single-step survival cohort (`crates/chart/src/survival_cat.rs:1568-1595`) or 1-point ROC curve (`crates/chart/src/multivariate_layout.rs:2009-2027`) emits a `Path2D` containing only `MoveTo(x0, y0)`, leaving an unclosed `EMR_BEGINPATH` in the `.emf` stream that corrupts subsequent drawing state on GDI playback.
- **Evidence:**
  ```rust
  if !pending_beziers.is_empty() {
      ensure_begun(self, &mut began)?;
      self.flush_polybezier(&mut pending_beziers, &mut dev_bounds)?;
      let (px, py) = point_to_logical(prev);
      self.emit_i32_pair_record(EMR_MOVETOEX, px, py)?;
  }
  ...
  if !began || !has_segments {
      return Ok(None);
  }
  self.emit_empty_record(EMR_ENDPATH)?;
  ```
- **Suggested fix:** Defer `EMR_BEGINPATH` + initial `EMR_MOVETOEX` until the first actual `LineTo`/`QuadTo`/`CubicTo` segment is emitted (eliminating dangling `EMR_BEGINPATH` on move-only paths), and emit `EMR_POLYBEZIERTO` (`0x0000_0005`, passing only the `3 * k` `[c1, c2, to]` points without `p0`) with no subsequent `EMR_MOVETOEX` so mixed line/curve contours remain a single continuous figure.
- **Related:** none.

### R2-S09-02 · S2 · EMF `emit_text_span` fails to rotate ascender/descender offsets in `EMR_EXTTEXTOUTW.Bounds`, emitting zero-width bounds on vertical axis titles, and emits raw `U+000A` on multi-line text

- **Base:** fda1cc0106092834d97b53289ec2a99c1bf0439c
- **Location:** `crates/render/src/emf.rs:568-625` (bounds calculation at `crates/render/src/emf.rs:598-608`) at that base (introduced in `97fd998`)
- **Category:** wrong-result
- **Defect:** `emit_text_span` rotates `total_adv_pt` along `(cos(rad), sin(rad))` when computing `span_bounds`, but applies `-size_pt` (ascent) and `+0.25 * size_pt` (descent) along the unrotated Y axis instead of perpendicular `(-v * sin(rad), v * cos(rad))`, and encodes `'\n'` (`:573-586`) as a literal `U+000A` code unit on a single line.
- **Failure scenario:** On every standard graph with a `-90°` Y-axis title (or `+90°` Y2-axis title), `rad.cos() == 0.0`, so all four corners at `crates/render/src/emf.rs:601-604` produce identical `px = origin_pt.x` — writing a zero-width `EMR_EXTTEXTOUTW` `Bounds` rectangle (`left == right`) and omitting the glyph height to the left of the baseline from `EMR_HEADER.rclBounds`, causing bounds-culling EMF playback engines to clip or drop vertical axis titles. Multi-line `GraphAnnotation::TextBox` labels (`crates/chart/src/xy.rs:1335`, `crates/chart/src/survival_cat.rs:967`) also render on a single line with `.notdef` `U+000A` boxes in `.emf` exports.
- **Evidence:**
  ```rust
  let rad = (-f64::from(escapement_tenths) / 10.0).to_radians();
  let mut span_bounds = BoundsRect::empty();
  for (px, py) in [
      (origin_pt.x, origin_pt.y - size_pt),
      (origin_pt.x + total_adv_pt * rad.cos(), origin_pt.y + total_adv_pt * rad.sin() - size_pt),
      (origin_pt.x, origin_pt.y + 0.25 * size_pt),
      (origin_pt.x + total_adv_pt * rad.cos(), origin_pt.y + total_adv_pt * rad.sin() + 0.25 * size_pt),
  ] {
      span_bounds.include_pt(pt_to_dev_px(px), pt_to_dev_px(py));
  }
  ```
- **Suggested fix:** Transform local glyph-box corners `(u, v) ∈ {0.0, total_adv_pt} × {-size_pt, 0.3 * size_pt}` via `(origin_pt.x + u * cos(rad) - v * sin(rad), origin_pt.y + u * sin(rad) + v * cos(rad))` when building `span_bounds`, and split `PositionedText` on `'\n'` advancing perpendicular to the baseline by `line_height_pt` per line.
- **Related:** `R1-S09-06` (multi-line `PositionedText` handling across other render backends).

### R2-S09-03 · S2 · `parse_equation_segments` drops math-mode context (`in_math: false`), corrupting `*` multiplication into italics, leaving literal `{...}` braces, and misparsing `^\frac` / `_\frac`

- **Base:** fda1cc0106092834d97b53289ec2a99c1bf0439c
- **Location:** `crates/text/src/markup.rs:1156-1231` and `crates/text/src/markup.rs:1233-1247` at that base (introduced in `f145a16`)
- **Category:** wrong-result
- **Defect:** `parse_equation_segments` unwraps `$...$` / `$$...$$` delimiters and splits `\frac{num}{den}` segments, then passes each stripped slice to `parse_markup(...)` with `in_math: false` instead of math mode (`in_math: true`).
- **Failure scenario:** Three concrete equation inputs render wrongly in chart `ModelEquation` boxes and equation layout:
  1. **Asterisks inside `$...$` math equations (`$a * b + c * d$`):** `parse_markup("$a * b + c * d$")` preserves literal `*` because `parse_segment` disables Markdown emphasis when `state.in_math` is `true` (`crates/text/src/markup.rs:286`). `parse_equation_segments("$a * b + c * d$")` strips the outer `$` at line 1159 and calls `parse_markup("a * b + c * d")` with `in_math: false`, swallowing both `*` characters and italicizing `" b + c "` as Markdown emphasis (`"a"`, italic `" b + c "`, `"d"`).
  2. **Braced sub-expressions inside equations containing `\frac` (`$\frac{1 + \frac{a}{b}}{c + {d + e}}$`):** Inside the denominator, `{d + e}` has no `\frac`, so `parse_markup("c + {d + e}")` (with `in_math: false`) leaves literal `{d + e}` curly braces in the rendered output (`crates/text/src/markup.rs:277` only unwraps `{...}` groups when `state.in_math` is `true`).
  3. **Scripted fractions (`$e^\frac{1}{2}$` or `$x_\frac{1}{2}$`):** Because `brace_depth == 0` at `\frac`, `parse_equation_segments_inner` splits right after `^`, passing `"e^"` to `parse_markup` (which renders a literal caret `"e^"`) followed by a full-size baseline fraction `1/2`.
- **Evidence:**
  ```rust
  pub fn parse_equation_segments(input: &str) -> Vec<EquationSegment> {
      let mut out = Vec::new();
      let trimmed = input.trim();
      let source = unwrap_outer_math_delimiters(trimmed).unwrap_or(input);
      parse_equation_segments_inner(source, &mut out, 0);
      out
  }
  ...
  if brace_depth == 0
      && let Some((frac_seg, consumed)) = try_parse_frac_segment(rest, depth)
  {
      push_inline_segment(out, parse_markup(&input[inline_start..idx]));
  ```
- **Suggested fix:** Track `in_math: bool` through `parse_equation_segments_inner` (setting `in_math = true` when outer `$...$` / `$$...$$` delimiters are unwrapped, inside inline `$...$` blocks, and inside `\frac{...}{...}` numerators/denominators) and parse math slices with a `parse_math_markup` helper initialized with `StyleState { in_math: true, .. }`; also avoid splitting top-level `\frac` immediately after an unbraced `^` or `_`.
- **Related:** `R2-S03-08`.
