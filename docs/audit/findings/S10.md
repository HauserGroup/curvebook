### R1-S10-01 · S1 · `ui.screenshot` with a small viewport and any open dialog panics in `Ord::clamp` and kills the control server

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/dialogs_canvas.rs:2716` and `:2717` (`compute_workspace_layout`), reached from `crates/ui-egui/src/control_io.rs:1107-1114` (`dispatch_ui_screenshot`)
- **Category:** no-panic
- **Defect:** The modal-overlay size is computed with `u32::clamp(min, max)` where `max` can be smaller than `min`, and `Ord::clamp` asserts `min <= max` in every build profile.
- **Failure scenario:** Any control client sends `{"op":"ui.palette.open"}` (or opens any other dialog) and then `{"op":"ui.screenshot","params":{"width_px":64,"height_px":64}}`. `dispatch_ui_screenshot` accepts every width/height in `64..=4096` (`control_io.rs:36-37`, `:1107-1109`), but with a dialog open `compute_workspace_layout` evaluates `(width_px * 3 / 5).clamp(180, width_px.saturating_sub(24).max(1))`, which panics for any `width_px < 204`, and the height line panics for any `height_px < 144`. Nothing between the socket and the compositor catches the unwind (see R1-S10-03), so the panic leaves `serve_control_listener` on the desktop app's main thread (`apps/lumencraft/src/main.rs:188-191`) and the process exits with the researcher's unsaved session. In the browser build the panic aborts the wasm instance.
- **Evidence:** Code:
  ```rust
  let mw = (width_px * 3 / 5).clamp(180, width_px.saturating_sub(24).max(1));
  let mh = (height_px * 3 / 5).clamp(120, height_px.saturating_sub(24).max(1));
  ```
  Probe test in a scratch crate depending on `lumencraft-ui-egui` by path (`cargo test --offline`): after `ui.palette.open`, `ui.screenshot` at 64x64 → `panicked at crates/ui-egui/src/dialogs_canvas.rs:2716:37: min > max. min = 180, max = 40`; 200x400 → `min = 180, max = 176`; 400x140 → panic at `:2717:38` `min = 120, max = 116`; 204x144 → ok. Feeding the same three lines through `serve_control_stream` unwinds out of the stream loop after writing only the first response.
- **Suggested fix:** Compute `mw = (width_px * 3 / 5).max(180).min(width_px.saturating_sub(24).max(1))` (and the same for `mh`), or raise `MIN_SCREENSHOT_DIM_PX`; add a `ui.screenshot` test at 64x64 with a dialog open.
- **Related:** R1-S10-03 (no panic boundary on the control path); X1.

### R1-S10-02 · S1 · The control socket accepts unauthenticated requests from any local process and from browser HTTP POSTs, and several of them write to arbitrary host paths

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/control_io.rs:292-355` (accept and line loop), `:846-848` (`render.pdf` `path`), `:1116-1119` (`ui.screenshot` `path`), `:1136-1139` (`write_host_file`)
- **Category:** security
- **Defect:** Loopback binding is the only access control: there is no token, no check that the peer speaks the protocol (an HTTP request line is answered with an error and the connection stays open), and file-writing parameters take any absolute path with no `--workdir`-style containment.
- **Failure scenario:** While `lumencraft --control 7979` runs, a web page the user visits issues `fetch("http://127.0.0.1:7979/", {method:"POST", mode:"no-cors", body:'{"op":"ui.screenshot","params":{"path":"/Users/<user>/.zshrc"}}\n'})` (a `text/plain` POST needs no CORS preflight; only browsers that enforce local-network-access blocking stop it). The server answers each HTTP header line with `invalid control JSON` and keeps reading, then executes the body line and overwrites the target file with PNG bytes. The same channel can run `render.pdf` with `path`, every engine command (including exports that take `path`, e.g. the CSV export writer at `crates/engine/src/cmd_data.rs:2212-2214` and `write_output_file` at `crates/engine/src/cmd_sci.rs:2377-2385`, which also creates parent directories), and `app.quit`. On a multi-user host any other local account can do the same over plain TCP. The headless CLI/MCP path confines path parameters to `--workdir` (`apps/lumencraft-cli/src/error.rs:19-29`); the control channel, which runs the same commands, has no equivalent.
- **Evidence:** Probe test: an HTTP/1.1 POST byte stream (`POST / HTTP/1.1`, `Host`, `Origin`, `Content-Type: text/plain`, `Content-Length`, blank line, then the JSON body line with `"path":"<tmp>/lc_s10_probe_written.png"`) fed to `serve_control_stream` produced five `{"ok":false,...,"error":"invalid control JSON: expected value at line 1 column 1"}` replies followed by `{"id":7,"ok":true,...}`, and the file existed afterwards (465 bytes). `write_host_file` is `std::fs::write(path, bytes)` with no path check. `docs/control-protocol.md` lists only "loopback only" and "disabled by default" as security invariants.
- **Suggested fix:** Require a per-launch random token (printed to the launching terminal or written to a 0600 file) in every request, close the connection on the first line that is not a JSON object (rejects HTTP), and apply the CLI's workdir containment to every path parameter reachable from the socket (`path` in `render.pdf`/`ui.screenshot` and engine path keys).
- **Related:** S12 (`--workdir` sandbox and its path-key list), X1, R1-S10-04.

### R1-S10-03 · S2 · Control requests outside `Session::execute` run with no panic boundary; one concrete overflow in the layout badge compositor

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/control_io.rs:336-355` and `:432-460` (no `catch_unwind` around dispatch); `crates/ui-egui/src/dialogs_canvas.rs:3334-3337` (`draw_layout_summary_badges`)
- **Category:** no-panic
- **Defect:** Only engine commands are wrapped by `lumencraft_engine::guard::run_guarded` (inside `Session::execute`); `ui.*` commands, `ui.screenshot`, `render.svg`, `render.pdf` (which call `Session::render_sheet_scene`, itself unguarded at `crates/engine/src/lib.rs:375-377`) and `doc.inspect` run directly in the serve loop, so any panic there ends the control server and, on desktop, the process.
- **Failure scenario:** R1-S10-01 is one release-build instance. A second: `layout.create` then `layout.addPanel {"kind":"text","markdown":"x","bounds_pt":[1e12,10,50,50]}` (accepted: `parse_rect_pt` at `crates/engine/src/cmd_sci.rs:2579-2593` takes any finite f64), `sheet.select` the layout, then `ui.screenshot`. `draw_layout_summary_badges` computes `paper.x + ((bounds.x * sx).round().max(0.0) as u32)`; the cast saturates to `u32::MAX` and the `+` overflows. In dev/test builds (overflow checks on) this panics out of `handle_control_line`; in release it wraps and the badge is drawn at a wrapped coordinate. (Whether project loading also accepts such bounds was not checked.)
- **Evidence:** Probe test: the four requests above → `panicked at crates/ui-egui/src/dialogs_canvas.rs:3334:18: attempt to add with overflow`, caught only by the probe's own `catch_unwind` around `dispatch_control_line`. `grep catch_unwind` over `crates/ui-egui/src` and `apps/lumencraft/src` finds none; the only one is `crates/engine/src/guard.rs:26`. `AGENTS.md` describes `guard` as "the last line of defence at entry points".
- **Suggested fix:** Wrap `dispatch_request` (or each line in `serve_control_stream_with_quit`) in `guard::run_guarded`/`catch_unwind` and roll the `UiApp` back to a snapshot on panic, like the engine does; separately use `saturating_add` and clamp the casts at `dialogs_canvas.rs:3334-3337`.
- **Related:** R1-S10-01; S07 (engine `render_sheet_scene` unguarded); S09 (renderer).

### R1-S10-04 · S2 · One idle or slow client blocks the control server for every other client, with no timeout

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/control_io.rs:292-309` (`serve_control_listener`, `serve_control_connection`), `:1384-1407` (`read_bounded_control_line`)
- **Category:** resources
- **Defect:** Connections are served one at a time on the calling thread, and no read or write timeout is set on the accepted `TcpStream`, so a connection that sends nothing, sends a partial line, or stops reading responses holds the server indefinitely.
- **Failure scenario:** A client connects and sends `{"id":1` without a newline (or a half-open connection left by a crashed automation script, or a port scanner that connects and idles). Every later client's requests, including `app.quit`, go unanswered for as long as that socket stays open. A client that sends many `ui.screenshot` requests and never reads blocks the server in `write_all` once the socket buffers fill. On desktop the server runs on the main thread (`apps/lumencraft/src/main.rs:188-191`), so the app stays hung until killed.
- **Evidence:** Probe test: listener bound on `127.0.0.1:0`, server on a thread; client A wrote `{"id":1` and stayed open; client B wrote `{"id":2,"op":"ping"}\n` with a 3 s read timeout → `client B got NO reply within 3 s: Resource temporarily unavailable (os error 35)`.
- **Suggested fix:** Set `set_read_timeout`/`set_write_timeout` on each accepted stream (idle timeout of a few seconds, closing only that connection), and either serve connections on worker threads that send requests to the owner of `UiApp` over a channel, or limit per-connection idle time.
- **Related:** R1-S10-02, X1.

### R1-S10-05 · S2 · `command.batch` has no step limit and responses are not bounded, so one request can run for hours and build a response of tens of GB

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/control_io.rs:567-602` (`handle_command_batch`), `:347-350` (response written without a size check), `:30-31` (`MAX_CONTROL_LINE_BYTES` doc)
- **Category:** resources
- **Defect:** A batch may contain as many steps as fit in the 16 MiB request line, every step's full result (including base64 PNG/PDF payloads) is accumulated in memory, and the response line is never checked against `MAX_CONTROL_LINE_BYTES` even though that constant is documented as the "hard bound per JSON-lines control request/response frame".
- **Failure scenario:** One 16 MiB request `{"op":"command.batch","params":{"commands":[{"command":"ui.screenshot","params":{"width_px":4096,"height_px":4096}}, ...]}}` holds about 233,000 steps (72 bytes each). Each step renders a 4096x4096 frame and keeps its base64 PNG (about 133 KB for an empty project, more with content) in `results`, then `serialize_response` builds one string from all of them: roughly 31 GB before anything is written, so the process aborts on allocation failure (losing the session) or the main thread is busy for hours.
- **Evidence:** Probe test (dev profile): an 8-step batch of 4096x4096 `ui.screenshot` on an empty project → request 629 bytes, reply 1,066,303 bytes, 43.5 s. No length check on `items` at `:568-575`; `serialize_response(&response)` at `:375` and `writer.write_all` at `:348` have no bound.
- **Suggested fix:** Cap batch length (for example 1,000 steps) and the cumulative response size, returning an error past either, and enforce `MAX_CONTROL_LINE_BYTES` on outgoing frames (or document that only requests are bounded).
- **Related:** R1-S10-04, X1.

### R1-S10-06 · S3 · Every atomic `command.batch` deep-clones the whole `UiApp`, including the session undo history

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/control_io.rs:571-572`
- **Category:** resources
- **Defect:** `rollback_snapshot = atomic.then(|| app.clone())` copies the full `UiApp` (document, undo stack up to the engine's `MAX_UNDO_CELL_BUDGET`, navigator and dialog state) before the first step, even when every step is a read-only or UI-only command.
- **Failure scenario:** With a table created as `rows: 2000, data_sets: 50` followed by 50 `table.setCell` commands, an atomic batch containing only `ui.navigator.toggle` takes about 585 ms versus 63 µs non-atomic, and peak memory doubles for the duration; with a large document near the undo budget the clone can be hundreds of MB per request. This reintroduces, at the control layer, the per-request full-document copy that Known defect `G12` removed from `Session::execute`.
- **Evidence:** Probe test (dev profile): `Q5 atomic 1-step UI-only batch elapsed=584.766125ms`, `Q5 non-atomic same batch elapsed=62.792µs`.
- **Suggested fix:** Snapshot only the document (and UI fields the steps can touch), or use the session's own undo/transaction mechanism to roll back engine steps, and skip the snapshot when every step is read-only.
- **Related:** G12 (engine-side fix), R1-S10-05.

### R1-S10-07 · S3 · `ui.locale.set` reports a comma decimal separator but the grid keeps displaying and parsing with `.`

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/lib.rs:90-95` (`UiApp::set_locale`), `crates/ui-egui/src/control_io.rs:1066-1086`, `crates/ui-egui/src/grid_view.rs:796-806`, `:858`, `crates/ui-egui/src/dialogs_canvas.rs:3357`
- **Category:** contract-drift
- **Defect:** `set_locale` updates only `app.locale` and `app.locale_preset`; the separators the grid actually uses (`app.grid.tool.decimal_separator`, read by `format_visible_window` and TSV paste; `app.grid.decimal_separator`, read by `GridViewState::visible_frame`; `app.grid.import_wizard.decimal_separator`) are never synchronised, so they stay `.` (or `'\0'`, treated as `.`).
- **Failure scenario:** `ui.locale.set {"locale":"de"}` returns `"decimal_separator":","` and `ui.state` reports `","`, yet a cell holding 1.5 is still rendered `1.5` in the grid and in `ui.screenshot`, and a German user's pasted `1,5` goes through `Cell::parse_import_token(.., '.', ..)` and is stored as the text `"1,5"` instead of the number 1.5 (flagged later as "numeric observation expected"). `docs/localization-parity.md:10-12` marks the configurable decimal separator and the European clipboard-import preset as done.
- **Evidence:** Probe test: after `table.setCell` 1.5 and `ui.locale.set de` → `ui.state decimal_separator=","`, `grid.tool.decimal_separator='.' grid.decimal_separator='\0' import_wizard='.'`, `format_visible_window` texts `["1.5"]`, `visible_frame` texts `["1.5"]`. `Cell::parse_import_token` at `crates/doc/src/cell.rs:136` replaces `,` only when the separator argument is `,`.
- **Suggested fix:** In `UiApp::set_locale`, copy `locale_preset.decimal_separator` into `grid.tool`, `grid` and `grid.import_wizard` (unless the user has overridden them), and add a test that switches locale and checks the grid frame text.
- **Related:** S05 (cell parsing), X2.

### R1-S10-08 · S3 · Wrong-typed `ui.*` parameters are silently ignored and trigger a different action, including resetting every custom shortcut

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/ui-egui/src/control_io.rs:1048-1063` (`dispatch_ui_shortcut_reset`), `:1012-1025` (`dispatch_ui_rulers_toggle`)
- **Category:** wrong-result
- **Defect:** These handlers read parameters with `.and_then(Value::as_str)` / `.and_then(Value::as_bool)`, so a value of the wrong JSON type is treated as absent and the "absent" branch runs, unlike `ui.gallery.toggle` and `ui.pane.cycle`, which reject wrong types (`:973-990`, `:1000-1004`).
- **Failure scenario:** A script sends `{"op":"ui.shortcut.reset","command_id":5}` (or `null`, or an id with a typo in type such as `["ui.gallery.toggle"]`): instead of an error, `reset_all()` runs and every customized shortcut is discarded, reported as `{"reset_all":true}`. `{"op":"ui.rulers.toggle","visible":"true"}` toggles instead of setting, so sending it twice hides the rulers; `{"unit":5}` is ignored without error.
- **Evidence:** Probe test: after `ui.shortcut.set ui.gallery.toggle Ctrl+Shift+G`, `ui.shortcut.reset {"command_id":5}` → `{"ok":true,"result":{"reset_all":true}}` and `active_combo("ui.gallery.toggle") == Some("")`; two `ui.rulers.toggle {"visible":"true"}` calls returned `rulers_visible: true` then `false`.
- **Suggested fix:** Distinguish "key absent" from "key present with the wrong type" in these handlers and return an error for the latter, as `dispatch_ui_gallery_toggle` already does.
- **Related:** none.

### R1-S10-09 · S4 · Control-protocol docs and `UI_COMMANDS` parameter docs disagree with what the handlers accept and do

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `docs/control-protocol.md` (Framing and error paragraphs), `crates/ui-egui/src/menus/ui_commands.rs:5-23`, `crates/ui-egui/src/control_io.rs:341-342`, `:846`, `:983-991`, `:1021`, `:1084`; `crates/ui-egui/src/dialogs_canvas.rs:2382-2398`
- **Category:** contract-drift
- **Defect:** Several documented contracts do not match the code that reads them.
- **Failure scenario:** (a) `docs/control-protocol.md` says errors return `ok:false` "without disconnecting the socket", but a non-UTF-8 or over-16-MiB line closes the connection with no response (`control_io.rs:341-342`, `:1393-1401`), so a client waiting for a reply hangs or sees EOF. (b) The `UI_COMMANDS` params docs omit keys the handlers read: `open` for `ui.gallery.toggle` (`:983-991`), `visible` for `ui.rulers.toggle` (`:1021`), and the accepted bounds for `ui.screenshot` (`width_px`/`height_px` 64..=4096, `dpi` 72..=600). `render.pdf` reads `path` and `all` (`:830`, `:846`), neither documented, which hides the file-write surface of R1-S10-02 from reviewers. (c) `ui.locale.set` returns `preset_applied`, computed as `app.locale_preset == LocalePreset::for_locale(&app.locale)` right after `set_locale` assigned exactly that, so it is always `true`. (d) The command palette lists `cmd.shortcut`/the static `UI_COMMANDS` shortcut, not the customized binding from `ShortcutRegistry`, so after `ui.shortcut.set` the palette shows a stale shortcut while `command.list` shows the new one (`control_io.rs:530`, `:541`).
- **Evidence:** Read the cited lines; Q1 probe: a stream with a valid `ping`, then a line containing byte `0xFF`, then another `ping` returned one reply and `Err(InvalidData "control line is not valid UTF-8")`, never answering the third line.
- **Suggested fix:** Document the disconnect cases (or reply with an error before closing), add the missing keys and bounds to the params docs (and through `cargo xtask ui-commands` to the MCP catalog), drop or fix `preset_applied`, and read active shortcuts from the registry in the palette.
- **Related:** R1-S10-02, R1-S10-05.

## Checked, no finding

- **Line length limit:** `read_bounded_control_line` (`control_io.rs:1384-1407`) caps a line at 16 MiB before buffering more, including a client that never sends a newline (the cap is reached and only that connection closes; the remaining problem is the blocking in R1-S10-04).
- **JSON depth:** `serde_json::from_str` enforces its 128-level recursion limit; a 100,000-deep `[` nest returns `invalid control JSON: recursion limit exceeded` (probe Q1) instead of overflowing the stack.
- **Non-UTF-8 input:** rejected with `InvalidData` at `control_io.rs:341-342`; only that connection closes and `serve_control_listener` keeps accepting (`:295-298`). The silent disconnect is listed under R1-S10-09.
- **Loopback-only binding (IPv4, IPv6, wildcard):** both `validate_loopback_addr` (`:261-266`) and `bind_control_tcp_listener` (`:273-281`) use `IpAddr::is_loopback`, which rejects `0.0.0.0`, `::` and LAN addresses and accepts `127.0.0.0/8` and `::1`; the desktop app always binds `127.0.0.1` (`apps/lumencraft/src/main.rs:189`). `::ffff:127.0.0.1` is rejected by `is_loopback` (fails closed). Port 0 is rejected by `parse_control_port` (`:247-254`).
- **`ui.screenshot` and compositor size limits:** width/height bounded to `64..=4096` and dpi to `72..=600` (`:1107-1111`); `render_workspace_rgba` allocates through `RasterImage::new` before any layout arithmetic (`dialogs_canvas.rs:2739`), so the G11 pixel cap applies; `fill_rect`, `blit_image` and `draw_glyph_5x7` clip to the image and `blend_pixel` bounds-checks (`dialogs_canvas.rs:3786-3882`, `crates/render/src/rasterizer.rs:65-73`). Only the modal clamp (R1-S10-01) and layout badge offset (R1-S10-03) fail.
- **Clipboard bundle and print spool sizes:** `ClipboardBundle::from_scene` checks DPI `72..=1200` and finite positive scene size and clamps raster size to 8192x8192 (`:101-111`); `PrintJobSpec::spool_pdf` bounds `scale_percent` `1..=1000` and `bleed_pt` `0..=144` and rejects non-finite values (`:201-207`). Printer names starting with `-` are rejected (`:1570-1582`). The xclip/wl-copy no-timeout issue was already reported as R1-S11-08 and is not repeated.
- **RTL mirroring arithmetic:** `mirror_x_for_rtl` uses saturating subtraction (`i18n.rs:3083-3085`), and compositor callers that offset the result do so with `saturating_add` (for example `dialogs_canvas.rs:2820`, `:2858`, `:3152`).
- **Missing locale keys:** `tr` falls back to English and then `""` (`i18n.rs:3181-3184`), `try_tr` uses `.get(idx)` on the 16-entry array (`:3171-3176`); `ui.locale.set` rejects unsupported primary tags (`control_io.rs:1070-1076`). `is_rtl_locale` accepting `fa`/`ur` cannot be reached via `ui.locale.set` because those tags are rejected first.
- **Theme switching:** `ui.theme.set` only accepts `light`/`dark`/`high_contrast` and replaces the theme with a constant preset (`control_io.rs:1088-1104`).
- **Grid indexing from selection and stale coordinates:** `GridQuickStats::from_data_sheet`, `selection_cell_count`, `navigate` and `emit_toggle_exclude_intents` clamp row and flat-column indices to the current table and return early on empty tables (`grid_view.rs:161-212`, `:916-978`, `:1074-1095`); `flat_index_for_coord` saturates and `resolve_flat_coord` checks `col >= column_count` (`:1033-1071`). Quick stats above `MAX_QUICK_STATS_CELLS_FOR_CLONE_PASS` skip the per-cell pass (`:828-835`). Scroll-window clamping itself lives in `lumencraft-tools` (S11) and was not re-audited here.
- **Localized number parsing:** `parse_localized_number_input` slices only after ASCII `e`/`E` and filters non-finite results (`grid_view.rs:1433-1466`); `active_token_span` clamps the cursor to a char boundary before slicing (`:1734-1762`).
- **Navigator recursion:** `append_nested_results` recursion is bounded by the number of result sheets, itself capped by `MAX_SHEETS_PER_PROJECT = 500` (`workspace_nav.rs:1348`, `crates/doc/src/error.rs:25`).
- **Shortcut registry:** `set_shortcut` rejects unknown command ids and conflicting combos; `import_overrides_json` is all-or-nothing (`menus/shortcuts.rs:139-220`).
- **Batch recursion / quit inside batch:** `command.batch` steps go through `dispatch_command_by_id`, which does not route `command.batch` or `app.quit`, so batches cannot nest or quit (`control_io.rs:462-468`, `:561-563`).
