## Severity note

The playbook's severity table is written for runtime defects. For build guards this report uses: **S2** when a guard reports success on ordinary input that its documented contract says it rejects (its "all clear" message misleads the reviewer relying on it); **S3** when the gap needs an unusual input, a deliberate change, or is latent today.

### R1-S13-01 · S2 · `repo_files` silently drops every path that `git ls-files` quotes, so `assets`, `brands` and `cleanroom` never scan non-ASCII file names

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `xtask/src/main.rs:98`, `xtask/src/main.rs:105`
- **Category:** security
- **Defect:** `git ls-files` is run without `-z`, so with Git's default `core.quotePath=true` any path containing non-ASCII bytes, `"`, `\` or control characters is printed C-quoted (`"assets/log\303\263.png"`); `root.join(quoted).is_file()` is then false and the file is filtered out without a message.
- **Failure scenario:** Commit `assets/logó.png` (no `ASSETS.md` row), `crates/format/tests/fixtures/données.pzfx` (a vendor-created fixture) or `packaging/linux/résumé.desktop` (with a competitor name). `cargo xtask assets`, `cleanroom` and `brands` all pass and print their "all clear" summaries, because the file never reaches any of the three scanners (`assets.rs:51`, `cleanroom.rs:26`, `brands.rs:49` all call `crate::repo_files`).
- **Evidence:** In a scratch repo, `git ls-files --cached --others --exclude-standard` printed `"assets/a\"b.png"` and `"assets/log\303\263.png"`. The probe's copy of `repo_files` returned a list without `assets/logó.png`, and `assets::run` listed only `assets/unattributed.png`, `fixtures/sample.prism` and `fixtures/utf16.pzfx` as missing, not the unattributed `assets/logó.png`. Line 105: `text.lines().filter(|l| !l.is_empty()).filter(|l| root.join(l).is_file())`.
- **Suggested fix:** Run `git ls-files -z ...` and split on `\0` (or pass `-c core.quotePath=false` and still use `-z` for `"`/`\`/newline), and make a listed path that is not a regular file an error rather than a silent skip.
- **Related:** R1-S13-02, R1-S13-03, R1-S13-05 (all three scanners inherit this).

### R1-S13-02 · S2 · `cleanroom` misses the standard vendor copyright-notice forms and cannot see inside UTF-16 or compressed project files

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `xtask/src/cleanroom.rs:7-14`, `xtask/src/cleanroom.rs:46-50`
- **Category:** security
- **Defect:** The signatures are fixed substrings with no year, symbol or suffix tolerance (`"copyright (c) graphpad"`, `"copyright graphpad software"`, `"dotmatics limited. all rights reserved"`), matching runs on `from_utf8_lossy` text of the raw bytes, and nothing decodes UTF-16 or decompresses archives.
- **Failure scenario:** Each of these committed files passes `cargo xtask cleanroom`, although `docs/development.md:78` says the command "scans all tracked files for vendor copyright notices and vendor-authored XML/project signatures":
  - a fixture with `Copyright (c) 2024 GraphPad Software, LLC. All rights reserved.` (the year breaks `copyright (c) graphpad`);
  - a fixture with `© 2024 Dotmatics. All rights reserved.`;
  - a `.pzfx` saved as UTF-16 (valid XML, `encoding="UTF-16"`) containing `<GraphPadPrismFile` — lossy decoding yields `<\0G\0r\0…`;
  - a `.prism` file, which is a ZIP archive (`docs/gaps.md:109`, "`.prism` (ZIP/JSON/CSV)"), whose deflated entries contain any signature.
- **Evidence:** Probe run of the unchanged `cleanroom::run` over a scratch repo containing `fixtures/vendor_notice.xml` (both notices above), `fixtures/utf16.pzfx` (UTF-16LE `<GraphPadPrismFile …/>`), `fixtures/sample.prism` (zip of an XML with `<GraphPadPrismFile`) and a control file `fixtures/control.xml` (`copyright (c) graphpad control`): output `1 clean-room violation(s) found: fixtures/control.xml:1: matched 'copyright (c) graphpad'` — only the control was caught.
- **Suggested fix:** Match vendor names (`graphpad`, `dotmatics`) near `copyright`/`©`/`all rights reserved` on case-folded text rather than exact phrases; decode UTF-16 when a BOM or NUL pattern is present; and either open `.prism`/`.pzf` ZIPs (bounded) or reject committed `.prism`/`.pzfx`/`.pzf` files outside an explicit allowlist of testkit-generated paths.
- **Related:** R1-S13-01.

### R1-S13-03 · S3 · `brands` skips most of a Rust file after any `#[cfg(test)]`, misses multi-line string literals, and silently skips non-UTF-8 files

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `xtask/src/brands.rs:145-150`, `xtask/src/brands.rs:132-142`, `xtask/src/brands.rs:70-72`
- **Category:** security
- **Defect:** `strip_cfg_test_tail` truncates the file at the first `#[cfg(test)]` text anywhere, even on a single helper function; literals are extracted line by line, so the continuation line of a `"…\` string is never treated as a literal; and `read_to_string` failure (`let Ok(text) = … else { continue }`) drops the whole file.
- **Failure scenario:**
  - At base, `apps/lumencraft/src/main.rs:78` puts `#[cfg(test)]` on `fn run`. Everything after it, including the shipped `parse_args` and `launch_application` error strings (about 360 production lines before the test module at line 447), is never scanned. Changing the user-visible error at line 143 to `"GraphPad-compatible: unknown option …"` still gives `brands: 0 unapproved brand or suite mentions`.
  - `pub const M: &str = "Import from \` + newline + `    GraphPad table";` passes.
  - A packaging file in UTF-16 (common for Windows `.rc`/installer sources) or one Latin-1 byte (`\xa9`) in a `.desktop` file makes the whole file unscanned for both `BRANDS` and `SUITE_BRANDS`.
- **Evidence:** Probe: a scratch repo holding a copy of `apps/lumencraft/src/main.rs` with that one-line change produced `brands::run = Ok(())`. A second scratch repo with the multi-line literal (`crates/a`), a file that opens with `#[cfg(test)] fn helper() {}` and then has `"Open GraphPad file"` (`crates/b`), a UTF-16LE `packaging/windows/app.rc` and a Latin-1 `packaging/linux/latin1.desktop` (both containing `GraphPad`), plus a control literal (`crates/e`), reported only `crates/e/src/lib.rs:1: 'graphpad'`.
- **Suggested fix:** Cut only `#[cfg(test)]` followed by `mod … {` and resume after its matching brace (or use a tokenizer such as `syn`/`proc-macro2` over the file); carry string state across lines; on non-UTF-8 input either decode UTF-16 with a BOM or fail with "cannot scan <path>".
- **Related:** R1-S13-01, R1-S13-04.

### R1-S13-08 · S3 · NIST ANOVA parser allocates `df_between + 1` bools taken from the file header, so a 247-byte `.dat` aborts or panics `cargo xtask corpus`

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/testkit/src/nist_strd/parser.rs:361`, `crates/testkit/src/nist_strd/parser.rs:408`; reached from `xtask/src/corpus.rs:354-367`
- **Category:** resources
- **Defect:** `anova_groups_cover_range` does `vec![false; expected_groups]` with `expected_groups = df_between.saturating_add(1)` parsed unbounded from the "Between Treatments" header row, bypassing the parser's own `MAX_STRD_BYTES`/`MAX_STRD_ROWS` bounds (`parser.rs:13-17`).
- **Failure scenario:** With `Between Treatments  18446744073709551615 …`, `vec!` panics with `capacity overflow`. With `100000000000000`, the process aborts with `memory allocation of 100000000000001 bytes failed`. `cargo xtask corpus` structurally parses every `.dat` under `corpus/nist-strd/` that is not in the manifest (`corpus.rs:354-367`, before the pinned check at `:371-373`), so a stray or corrupted `corpus/nist-strd/anova/*.dat` aborts the xtask. Pinned loaders are not affected, because they verify the SHA-256 before parsing.
- **Evidence:** The probe `<scratchpad>/probe-S13/tk` called `lumencraft_testkit::nist_strd::parse_anova_dat` on a 252-byte input and got `panicked at …raw_vec/mod.rs:28:5: capacity overflow`. A 247-byte input got `memory allocation of 100000000000001 bytes failed` (abort).
- **Suggested fix:** Reject `df_between` larger than the number of data rows (or `MAX_STRD_ROWS`) before allocating, and use a `BTreeSet` of seen groups.
- **Related:** R1-S13-09.

### R1-S13-09 · S3 · `corpus --fetch` overwrites the cached files before checking the pinned hashes, and records a manifest built from whatever was downloaded

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `xtask/src/corpus.rs:187-192`, `xtask/src/corpus.rs:396-438`, `xtask/src/corpus.rs:364-365`
- **Category:** data-loss
- **Defect:** `fetch_nist_strd` accepts any response containing `Dataset Name:` from any of three candidate URLs (`curl -fsSL` follows redirects to any scheme or host). It `fs::rename`s that response over the existing `.dat` file and writes `sha256sums.txt` from the downloaded bytes, without comparing against `PINNED_NIST_STRD_CORPUS`. `--fetch-only` then returns success. For `.dat` files not listed in the manifest, `verify_corpus_dir` hashes the bytes and checks them against that same hash (`verify_blob(&bytes, bytes.len(), &digest)`), which always passes.
- **Failure scenario:** NIST republishes one file with different bytes (line endings or a header edit), or a redirect returns a different `.dat`. `cargo xtask corpus --fetch-only` prints `fetched and recorded 58 NIST StRD .dat files` and replaces the previously verified cached copy. - **Evidence:** Code trace. `corpus.rs:436` renames before any pin comparison, `:437-438` writes the manifest from `sha256_hex(&bytes)`, and `:190-191` returns `Ok` for `--fetch-only` before `verify_corpus_dir`. - **Suggested fix:** Before the rename, verify each download with `verify_blob` against its `PinnedStrdSpec`, keeping the old file on mismatch. Write `sha256sums.txt` from the pinned table rather than from the downloads, add `--proto =https --max-filesize`, and drop or replace the tautological check at `:364-365` (treat unpinned `.dat` files as an error or a warning).
- **Related:** R1-S13-08.
