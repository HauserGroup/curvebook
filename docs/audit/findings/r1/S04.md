### R1-S04-01 · S1 · Ragged tables panic the formula evaluator and Transpose

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/formula/eval.rs:1002`, `:1008`, `:1014`, `:1026`, `:1041`, `:1061`; `crates/transform/src/ops/reshape_select.rs:177`, `:218`
- **Category:** no-panic
- **Defect:** The evaluator and Transpose index columns with `[row]` up to `row_count()`, which is the length of the first data set or variable only. Nothing guarantees that the other columns are that long.
- **Failure scenario:**
  1. A `.lumencraft` archive has a MultipleVariables sheet where variable B has 2 cells and variable A has 3. `validate_data_sheet` checks only per-column caps (`crates/format/src/archive.rs:564-575`, `:602-611`) and accepts it.
  2. A calculated variable `abs(B)` (or `min(B, 1)`, `not(B)`, `clamp(B,0,1)`, `and(B,1)`) evaluates. `n = ctx.row_count()` is 3, but `eval_scalar_row` indexes `cols[0][row]` with `row = 2` and panics.
  3. Transposing a Grouped sheet whose second data set is longer than the first panics at `grid[r][c]` (`reshape_select.rs:218`). The MultipleVariables equivalent panics at `reshape_select.rs:177`.
  4. Natively, the engine guard turns the panic into an internal error. On `wasm32` it aborts.
  5. Binary operators do not panic but `zip` silently (`eval.rs:386-388`), and `dag.rs:99-109` then stores the shorter vector. In the probe, the calculated column shrank from 3 cells to 2. If that column is variable 0, the table's `row_count()` shrinks.
- **Evidence:** Probe output: `validate_project_document on ragged MV: Ok(())`, then `panicked at crates/transform/src/formula/eval.rs:1008:26: index out of bounds: the len is 2 but the index is 2`. The ragged Grouped sheet also passes `validate_project_document`, then `panicked at .../reshape_select.rs:218:25`. The MultipleVariables transpose `panicked at .../reshape_select.rs:177:17`. The `B + 1` probe returned `Ok([2]) C len = 2`.
- **Suggested fix:**
  - In the evaluator, read rows with `.get(row)` and treat a missing row as `Missing`. Pad every `column_values` result to `ctx.row_count()`.
  - In the transposes, use `get_mut` the way `transpose_single_columns` does.
  - Separately, have `S05`/`S06` reject or pad ragged tables on load.
- **Related:** S05 (rectangular invariant not enforced), S06 (archive validation), X2.

### R1-S04-02 · S1 · Long left-associative formula chains overflow the stack in the recursive evaluator

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/formula/parser.rs:351-362`; `crates/transform/src/formula/eval.rs:375-392`
- **Category:** no-panic
- **Defect:** `MAX_PARSE_DEPTH = 128` (`parser.rs:5`) limits only parser recursion. The Pratt loop at `parser.rs:353-360` builds `a+b+c+…` iteratively into a left-deep tree whose depth can approach `MAX_TOKENS / 2 ≈ 8192`. `eval_column_expr` then recurses once per level.
- **Failure scenario:**
  1. `table.setCalculatedVariable` (`crates/engine/src/cmd_data.rs:2375-2408`) is sent a roughly 32 KB formula `1+1+…+1` with 8000 terms, or a project containing one is opened and recalculated.
  2. Evaluation overflows the stack. This is a `SIGABRT` that no guard catches.
  3. Measured thresholds: a release build overflows a 2 MiB thread stack (the Rust default for spawned threads) and a 1 MiB stack at 4000 terms. A debug build overflows even an 8 MiB stack. The `wasm32` default stack is 1 MiB. Frame sizes on wasm were not measured, but the risk is the same class.
- **Evidence:** Probe `p3b`. The AST was confirmed at depth 7999. Release: `eval` and `calc` overflow at 1024 and 2048 KiB and succeed at 4096 KiB. At 1024 KiB, 2000 terms succeed and 4000 terms overflow. Debug: `eval` and `calc` overflow at 8192 KiB, while `parse`, `drop` and `extract_dependencies` succeed.
- **Suggested fix:** In the parser, cap the AST depth or node count, and count binary-chain length toward `MAX_PARSE_DEPTH`. Alternatively, rebalance associative chains or make `eval_column_expr` iterative.
- **Related:** Known defect `G9` (the same pattern in `crates/fit/src/dsl.rs`; this is a separate parser in a different crate).

### R1-S04-03 · S1 · Import placement grows tables without a row cap before validating

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/import.rs:452-453`, `:490-497`, `:503-506`, `:529-534`, `:548-567`
- **Category:** resources
- **Defect:** `place_grid` computes `needed_rows = start_row + grid.len()` with unchecked addition from a caller-supplied anchor. `ensure_sheet_rows` then resizes vectors to that size before any `validate_rows` check:
  - XY: `x_cells` and `row_titles`.
  - Column, Grouped, Contingency and PartsOfWhole: `row_titles`.
  - Survival: `times` and `row_titles`.
  - MultipleVariables and Nested: every column, with no check at all.
- **Failure scenario:**
  1. The anchor comes straight from `table.paste`: `parse_anchor_coord` at `crates/engine/src/cmd_data.rs:2872-2880` is passed to the pipeline at `cmd_data.rs:1854-1880`.
  2. With `{"sheet_id": <MV sheet>, "text": "1", "row": 1000005}`, the MultipleVariables sheet grows to 1,000,006 rows and the call returns `Ok`. That exceeds `MAX_ROWS`, so the document then fails `validate_project_document`, which the save path runs.
  3. With `"row": 5000000000`, `row_titles.resize_with` requests about 120 GB and aborts on allocation failure. This was traced, not run.
  4. With `"row": 18446744073709551615`, line 452 overflows. Debug builds panic. Release builds wrap, and the cell lands at row 0 (line 458).
- **Evidence:** Probe `p5`: `P5 MV: Ok(1); rows now 1000006 (MAX_ROWS 1000000)` and `P5 MV validate: false`. For XY: `Err(Doc(TooManyRows …)); x_cells 1000006 row_titles 1000006 ds rows 3`, which shows the XY vectors were grown before the error.
- **Suggested fix:** Use `checked_add` and run `validate_rows(needed_rows)` once at the top of `ensure_sheet_rows`, before any `resize`. Apply the same cap to the column offsets in `resolve_target_coord`.
- **Related:** S07 (engine `table.paste` parameter checks).

### R1-S04-04 · S1 · Bare built-in constants such as `e` silently resolve to default-labelled columns

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/formula/eval.rs:447-469`, `:237-246`; `crates/transform/src/formula/dag.rs:151-158`
- **Category:** wrong-result
- **Defect:** `resolve_ident_var` tries column names, including the default letter labels (`resolve_mv_column` → `default_column_label(i)`, case-insensitive, `eval.rs:245`), before `builtin_constant` (`eval.rs:465`). So `e` resolves to column E (index 4) whenever the table has 5 or more columns. `pi` likewise resolves to column `PI` (index 424) when the table has 425 or more columns.
- **Failure scenario:**
  1. A MultipleVariables table has 6 variables. The column at index 4 is titled `Weight` and holds 70 and 80.
  2. A calculated variable `2*e` silently yields `140` and `160` instead of `5.4366`. The same formula in a 3-variable table gives `5.4366`.
  3. If column E itself is calculated with `exp(1)*e`, the DAG reports a spurious self-cycle (`CircularDependency ["Variable E", "Variable E"]`).
  4. The guide (§4.1) says bare identifiers resolve "when unambiguous". Here the reference is ambiguous and resolves without a diagnostic.
- **Evidence:** Probe `p4`: `2*e -> [Number(140.0), Number(160.0)]`. With 3 variables: `5.43656365691809`. For the calculated column E: `Err(CircularDependency { cycle: ["Variable E", "Variable E"] })`.
- **Suggested fix:** Either give built-in constants precedence over default letter labels, so only explicit titles shadow them, or reject the ambiguous identifier with a message telling the user to write `[E]` or `exp(1)`. Apply the same rule in `resolve_col_deps`.
- **Related:** none.

### R1-S04-05 · S2 · Import placement never adds columns: AppendColumns and wide pastes silently drop data

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/import.rs:447-450`, `:457-468`, `:164-165`
- **Category:** data-loss
- **Defect:** `place_grid` grows rows but never data sets or variables. Each cell is written only if `data_cell_mut` finds the column (line 462), and other cells are skipped without a trace. The report still returns `cols_placed` as the grid width.
- **Failure scenario:**
  1. `table.paste` with mode `appendcolumns` (`cmd_data.rs:3079`) sets `start_col = column_count()`, so every cell is discarded. The command reports `rows_placed=1, cols_placed=2` and a target range one column past the table.
  2. With `overwrite`, pasting a 3-column clipboard into a 1-column sheet keeps only the first column.
  3. The format-crate path does grow columns (`crates/format/src/csv.rs:1298-1330`, `grow_datasets`), so behaviour differs by entry point.
  4. Link refreshes rewrite AppendColumns to Overwrite at the old start column (`crates/engine/src/dag.rs:290-293`), so a refresh writes nothing either.
- **Evidence:** Probe `p6`: `AppendColumns: report rows=1 cols=2 range=…start col 1…; columns now 1 -> [[1.0, 2.0, 3.0]]`. The pasted `9\t8` is absent.
- **Suggested fix:** Grow columns (data sets or variables) up to `start_col + width` under the existing caps, as `ensure_sheet_capacity` does in `format`. Otherwise return an error, and in every case report what was actually placed.
- **Related:** S07, X2.

### R1-S04-06 · S2 · `InsertRows` placement overwrites existing rows instead of inserting

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/import.rs:442-446`
- **Category:** data-loss
- **Defect:** `PlacementMode::Overwrite | PlacementMode::InsertRows => anchor.row`. No rows are shifted, so InsertRows behaves exactly like Overwrite.
- **Failure scenario:** `table.paste` with `"mode": "insert"` (`cmd_data.rs:3077`) at row 0 of a column holding `[1, 2, 3]` produces `[9, 2, 3]`. The user's value 1 is lost instead of the column becoming `[9, 1, 2, 3]`. Undo can recover it, but the command reports success.
- **Evidence:** Probe `p7`: `InsertRows: … columns now 1 -> [["Number(9.0)", "Number(2.0)", "Number(3.0)"]]`.
- **Suggested fix:** Shift existing rows of every column (and row titles, X and times) down by the grid height before writing. Otherwise reject `InsertRows` until it is implemented.
- **Related:** R1-S04-05.

### R1-S04-07 · S2 · Prune with averaging averages SD and N subcolumns and wipes text variables

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/ops/reshape_select.rs:434-445`, `:478-484`, `:499-511`
- **Category:** wrong-result
- **Defect:** `average_cell_grid_bins` takes a plain mean of `active_number()` for every subcolumn, so averaging is wrong for both pre-summarized and text data:
  - In pre-summarized modes (Mean/SD/N, Mean/SEM/N, Mean/CV/N and others), the SD and N subcolumns are averaged like the means.
  - Text and categorical cells have no numeric value, so they come out `Empty`.

  No warning is emitted in either case.
- **Failure scenario:**
  1. The `prune_rows` analysis is called with `average_window: true` (`crates/engine/src/cmd_sci.rs:500-503`).
  2. On an XY Mean/SD/N sheet, rows `(10, 1, 3)` and `(20, 1, 5)` become `(15, 1, 4)`. The pooled values for those 8 observations are mean 16.25, N 8 and SD about 5.26.
  3. On a MultipleVariables sheet, a categorical variable `ctrl, ctrl` becomes `Empty`.
  4. Downstream analyses then use the wrong N and SD.
- **Evidence:** Probe `p12`: `MeanSdN bin: [[15.0, 1.0, 4.0]]`, `MV text bin: [Empty] / [2.0]`, warnings `[] []`.
- **Suggested fix:** Pool pre-summarized rows properly (N-weighted mean, summed N, pooled SD including between-row spread) or reject AverageBins for those modes. Keep text cells when every cell in the bin agrees, otherwise blank them with a warning.
- **Related:** S02 (consumers of summarized N/SD).

### R1-S04-08 · S2 · Simulate allocates up to 512 M cells from user parameters with no total budget

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/simulate.rs:98-113`, `:126-129`
- **Category:** resources
- **Defect:** The only limits are the per-axis caps `row_count <= MAX_ROWS` (1,000,000) and `replicates <= MAX_SUBCOLUMNS` (512). The table is then allocated eagerly through `XyTable::new_with_x_mode` (`crates/doc/src/archetypes.rs:149-171`, which has no total-cell check).
- **Failure scenario:**
  1. `table.simulateXy` with `rows: 1000000, replicates: 512` (`crates/engine/src/cmd_data.rs:2417-2429`), or a stored `Transform::Simulate` analysis with the same values (`cmd_sci.rs:508-517`, recomputed by `dag.rs:432-443`).
  2. This requests 512 M × 32 B ≈ 16 GiB of `Cell`s, plus 1 M row vectors.
  3. The process aborts on allocation failure, which is certain on `wasm32` (4 GiB address space). Before allocation can fail, the loop also runs 512 M normal draws.
- **Evidence:** Probe `p8`: `size_of::<Cell>() = 32`. `simulate 2 x 512: ok=true` shows the replicate cap is accepted. The 1 M × 512 case was not run.
- **Suggested fix:** Check `row_count * replicates` against a total cell budget (for example the import `MAX_IMPORT_CELLS`) before allocating, and return `InvalidSpec`.
- **Related:** Known defect `G11` (same pattern for raster buffers), S05 (no total-cell budget in constructors).

### R1-S04-09 · S2 · XY Transpose and Select→XY projection silently keep only subcolumn 0

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/ops/reshape_select.rs:128-140`, `:248-277`, `:857-889` (line 884)
- **Category:** wrong-result
- **Defect:** `transpose_single_columns` copies `row_cells.first()` only, and `transpose_xy` does not check `y_subcolumn_mode`. Column tables are rejected unless the mode is Single (`:59-62`), but XY tables with replicates or Mean/SD/N are not, so replicates 2..n, SD and N are dropped. `flatten_primary_columns` likewise reads `CellCoord::new(r, c, 0)`, so `SelectAndTransform`, which the engine always projects to XY (`cmd_sci.rs:504-507`), drops every replicate after the first of a Grouped or Column source.
- **Failure scenario:**
  1. Transposing an XY table with 3 replicates (`1, 2, 3` per row) yields a Single Column table holding only `1` per cell, with no warning.
  2. Select on a Grouped table with 3 replicates per cell yields X = 1 and Y = 4. Replicates 2 and 3 (2, 3, 5, 6) are gone.
- **Evidence:** Probe `p13`: `XY(rep3) transpose -> Column subcols [1, 1], mode Single, cells [[[1.0]], [[1.0]]]`, warnings `[]`. Also `Grouped(rep3) select->XY: x=[[1.0]] y=[[[4.0]]]`.
- **Suggested fix:** Reject multi-subcolumn XY sources in Transpose (as for Column) or carry subcolumns through. In projection, either reject replicate sources or carry the replicates into the target's subcolumn mode, and add a warning whenever data is dropped.
- **Related:** none.

### R1-S04-10 · S3 · Curve calculus pairs each data set's compacted series with data set A's X values

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/curve.rs:547-563`, `:576-598`
- **Category:** wrong-result
- **Defect:** `extract_xy_mean_series` skips rows with missing or excluded Y independently per data set and sorts by X. `apply_curve_calculus_to_sheet` then writes X only from data set 0's result (`if ds_idx == 0`) and every other data set's values by compacted index.
- **Failure scenario:**
  1. X is `1..4`, A is `1..4` and B is `10, _, 30, 40`.
  2. `Differentiate(First)` gives B's values at x = 1, 3 and 4, but they are written against X = 1, 2 and 3, and row 4 of B is left empty.
  3. Smoothing and integration misalign the same way.
  4. The function is public but has no engine caller at this base, which is why the severity is S3.
- **Evidence:** Probe `p9`: rows show `x=2 … B=9.999…`, `x=3 … B=9.999…`, `x=4 … B=Empty`. Computed alone, B is `[(1,10),(3,9.99…),(4,9.99…)]`.
- **Suggested fix:** Write each data set's own X per point, keyed by its source row, or build the output on the union of X values with gaps.
- **Related:** none.

### R1-S04-11 · S3 · Remove Baseline blanks cells for missing or zero baselines without a warning

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/ops/normalize_baseline.rs:563-570`, `:513-523`, `:539-552`
- **Category:** wrong-result
- **Defect:** When a row's baseline is missing (empty, excluded or non-numeric), `apply_baseline_cell` sets the data cell to `Empty` and pushes no warning. The pre-summarized branches (Mean/SD/N, Mean/CV/N and Mean/Low/High) also blank cells on a zero baseline (Ratio, PercentChange or FractionalChange) without warning. Only the replicate and single-cell path warns, and only for an undefined operation.
- **Failure scenario:** The baseline column is `[1, 2*, empty]` (row 1 excluded) and data `[10, 11, 12]`. The output is `[9, Empty, Empty]` with `warnings: []`, so the summary tab reports "Warnings 0" while two of the three observations vanished from downstream analyses.
- **Evidence:** Probe `p10`: `B after: [Number(9.0), Empty, Empty]; warnings []`.
- **Suggested fix:** Push a per-row warning, or one aggregated count, whenever a non-excluded data value is blanked because its baseline is missing or zero, in every subcolumn mode.
- **Related:** AGENTS.md "never silently drop missing values".

### R1-S04-12 · S3 · The simulation seed in the summary tab loses precision above 2^53

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/ops/mod.rs:166`
- **Category:** contract-drift
- **Defect:** The summary reports `ResultCell::Number { value: *seed as f64 }`, so seeds above 2^53 are shown rounded.

- **Related:** none.

### R1-S04-13 · S3 · A non-ASCII, non-alphanumeric character produces a "token limit" parse error

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/formula/parser.rs:306-307`, `:235-251`, `:296-298`
- **Category:** contract-drift
- **Defect:** Any non-ASCII byte is routed to `lex_ident`. If the character is not alphanumeric (for example `€` or a no-break space U+00A0 pasted from a spreadsheet), `lex_ident` returns an empty `Ident("")` without advancing. The loop then pushes 16,384 empty tokens until `MAX_TOKENS` trips.
- **Failure scenario:** `[A]\u{a0}+ 1` fails with `"formula exceeds maximum token limit"` at the position of the no-break space, instead of "unexpected character". This misleads a user whose formula is only a few characters long.
- **Evidence:** Probe `p11`: both `[A] + €` and `[A]\u{a0}+ 1` return `ParseError { message: "formula exceeds maximum token limit" }`.
- **Suggested fix:** In `lex_ident`, return an "unexpected character" error when no character was consumed. Consider treating Unicode whitespace as whitespace.
- **Related:** none.

## Checked, no finding

- **DAG cycles:**
  - Self-references are rejected (`formula/dag.rs:137-140`).
  - Multi-column cycles are found by Kahn's algorithm with deterministic ordering (`dag.rs:171-201`).
  - The cycle-naming DFS recurses at most once per variable, which is capped at `MAX_DATA_SETS = 1024` on load (`crates/format/src/archive.rs:566`).
  - Static dependency resolution (`dag.rs:151-169`) uses the same `resolve_mv_column` as runtime, so the evaluation order is consistent. See R1-S04-04 for the constant-shadowing exception.
- **Parser bounds:**
  - Parentheses, calls, unary chains and `^` are bounded by `MAX_PARSE_DEPTH` (`parser.rs:341-349`, `:392-411`).
  - Token count is capped (`:296-298`).
  - Overflowing literals are rejected (`:181-183`).
  - Lexer slicing stays on character boundaries: it advances by bytes only over ASCII and by `len_utf8` otherwise.
  - `col(n)` with a huge `n` saturates and resolves through `get` (`parser.rs:481-484`, `eval.rs:407`).
- **Window and aggregate functions:**
  - `lag`, `lead` and `diff` use `checked_sub`/`checked_add` (`eval.rs:862-886`).
  - `rolling_*` rejects `w = 0` (`:843-845`).
  - An out-of-range percentile returns `Missing` (`:639`).
  - `zscore` with SD 0 returns `Missing` (`:917`).
  - Division and modulo by zero map to `Missing` through `from_f64` (`:521`).
- **Excluded and missing cells in formulas:**
  - `FormulaValue::from_cell` maps excluded, empty and whitespace-only cells to `Missing` (`eval.rs:29-38`).
  - Aggregates skip them.
  - Calculated output keeps the target column's exclusion mask (`dag.rs:98-106`).
  - Replicate rows average only active numbers (`eval.rs:293-306`).
- **Normalize with a zero or missing reference:**
  - A zero span is rejected (`normalize_baseline.rs:58`, `:68`).
  - An anchor with no active values is an error (`:161`, `:166-179`, `:197-198`).
  - `FixedValue` must be finite (`:150`).
  - Hooked constants and result scalars must be finite (`ops/mod.rs:54-57`, `:81-86`; `crates/doc/src/result.rs:206`).
- **Baseline and selection indices:**
  - Baseline columns, row ranges and first/last-k windows are bounds-checked (`normalize_baseline.rs:388-393`, `:405-410`, `:420-430`).
  - Selected data-set indices are validated (`ops/mod.rs:97-107`).
  - All subcolumn writes in Normalize, Baseline and Math are guarded by `get` or length checks (`normalize_baseline.rs:309-349`, `math.rs:474`, `:543`, `:603`).
- **Reshape and select with out-of-range input:**
  - Prune `k = 0` is rejected (`reshape_select.rs:292`, `:308`, `:314`).
  - `retain_rows` uses `get` (`:513-571`).
  - `RowRange` with start > end is rejected (`:615`).
  - The TopN column is bounds-checked (`:648`).
  - Projection grids are rectangular by construction (`:880-888`).
  - `transpose_single_columns` writes through `get_mut` (`:135`).
  - Import row and column windows, unstack bounds and result-tab slicing are clamped (`import.rs:266-303`, `:327-329`, `:211-217`).
- **Simulation seeds and noise:**
