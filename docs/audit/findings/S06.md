### R1-S06-01 · S1 · `.prism` import has no project-wide cell budget: a 6 KB file allocates 1.5 GiB and scales to hundreds of GiB

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/prism.rs:127` (CSV loop), `crates/format/src/prism.rs:150` (embedded `.pzfx` loop); budget checks at `crates/format/src/csv.rs:636`, `csv.rs:653`, `csv.rs:871` and `crates/format/src/pzfx.rs:128`
- **Category:** no-panic (allocation abort) / resources
- **Defect:** `MAX_IMPORT_CELLS` (10M, `csv.rs:16`) is enforced per CSV entry by `import_csv_to_datasheet` (`validate_csv_cell_budget`, `csv.rs:636/653/665/674/688/708/721/754`) and per `.pzfx` payload (`remaining_cells` is a local in `import_table_sections`, `pzfx.rs:128`), but `import_prism_bytes_with_limits` calls these once per ZIP entry (`prism.rs:127-147`, `prism.rs:150-156`) with no shared remaining budget, so the total is up to `MAX_SHEETS_PER_PROJECT` (500) × 10M dense cells.
- **Failure scenario:** A `.prism` ZIP with N stored/deflated CSV entries, each a 1,024-column header line followed by 9,000 lines of `1`. Each 23 KB entry is under the per-table cap (9.2M cells) and deflates to about 2 KB. The dense `Vec<Vec<Cell>>` layout costs about 56 bytes per cell (`DataSetColumn::new`, `vec![vec![Cell::empty(); subs]; rows]`, `Cell` is 32 bytes), so each entry allocates about 490 MiB. With 3 entries (6.4 KB file) peak heap is 1.48 GiB; with a few dozen entries the native process aborts on allocation failure, and `wasm32` aborts much earlier. Entries: `file.import` (`crates/engine/src/cmd_data.rs:2231`), desktop open (`apps/lumencraft/src/main.rs:382`), MCP import (`crates/mcp/src/tools.rs:675`).
- **Evidence:** Probe built the archive with `ZipWriter` and called `import_prism_bytes`:
  ```
  prism: 1 tables, archive bytes = 2159  -> Ok, total dense cells = 9216000,  peak heap = 494 MiB
  prism: 3 tables, archive bytes = 6433  -> Ok, total dense cells = 27648000 (MAX_IMPORT_CELLS = 10000000), peak heap = 1479 MiB
  ```
  The import succeeds with 2.76× the documented cap. The ZIP limits (`zip.rs:13-19`, 128 MiB decompressed) do not help because the amplification is in table construction, not decompression.
- **Suggested fix:** Thread one `remaining_cells` budget through `import_prism_bytes_with_limits` into every CSV and embedded-`.pzfx` import (for example an `import_csv_to_datasheet_with_budget` variant and a `pzfx` entry point taking `&mut usize`), and reject the archive once the project total exceeds `MAX_IMPORT_CELLS`.
- **Related:** Known defect `G10` (pzfx `estimate_table_cells` duplication) is a different defect; `X1` (untrusted input end to end).

### R1-S06-02 · S2 · Checkpoint writes the snapshot before truncating the journal and records no covered sequence, so recovery replays commands already in the snapshot

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/recovery.rs:598` (`checkpoint`), `recovery.rs:613` (`close_cleanly`), `recovery.rs:654` (`recover_journal_contents`)
- **Category:** data-loss / wrong-result
- **Defect:** `checkpoint` does `write_snapshot_atomic` then `clear_journal` as two independent steps (`recovery.rs:599-600`), and neither the snapshot nor the journal records which `seq` the snapshot already contains, so after a crash or a `clear_journal` error between the two steps, `open_or_recover` returns the new snapshot together with the old commands and the engine replays them on top (`crates/engine/src/lib.rs:169-182`).
- **Failure scenario:** (a) Process is killed or loses power after the snapshot rename and before `ops.journal` is removed. (b) `clear_journal` fails (`remove_file` error, for example a Windows indexer or antivirus holding `ops.journal` open): `checkpoint` returns `Err` but the snapshot is already replaced, the session keeps running, and further commands are appended after the stale ones; a later crash replays all of them. In both cases non-idempotent commands (add rows, append data, add sheet) are applied twice and the recovered project is silently wrong, with no diagnostic.
- **Evidence:** Probe with a backend wrapping `MemoryJournalBackend` whose `clear_journal` returns `Err`:
  ```
  checkpoint result = Err(Io("simulated: journal file in use"))
  after crash: snapshot = Some("SNAPSHOT-THAT-ALREADY-CONTAINS-THE-5-ROWS"),
               commands to replay on top = [{"command_id":"table.addRows","params":{"count":5}}]
  ```
  And a plain crash between the two steps (`write_snapshot_atomic` called, then `abandon`): `snapshot = Some("S2"), replay = 1`. `RecoveryReport` (`recovery.rs:119-132`) has no field linking the snapshot to a sequence number.
- **Suggested fix:** Store the last applied `seq` with the snapshot (for example a small header or sidecar written in the same atomic rename) and have `recover_journal_contents` skip records with `seq <=` that value; then the order of snapshot write and journal truncation no longer matters.
- **Related:** `S07` (`Session::open_with_recovery` replays blindly); `S11` (desktop app entry point).

### R1-S06-03 · S2 · One malformed interior journal line aborts all recovery, and the desktop app then refuses to start

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/recovery.rs:665-673` (`is_tail` only for the last line; `verify_crc()?`), `recovery.rs:704-720` (`parse_journal_line`), `recovery.rs:511-519` (`append_journal_line`)
- **Category:** data-loss
- **Defect:** Only the last non-empty line may be torn; any earlier line that fails UTF-8, JSON or CRC makes `open_or_recover` return `Err` and discards every valid record before it, yet `append_journal_line` can leave exactly such a line behind: a short `write_all` (ENOSPC, EIO) leaves partial bytes without a newline, and the next successful append is glued onto them.
- **Failure scenario:** The disk fills during `record_command` for seq 2 (partial line written, error returned); space is freed and seq 2 (retry) and seq 3 append normally; the app later crashes. On restart, line 2 is `{"seq":2,"{"seq":2,...}` and is not the tail, so recovery fails with `malformed entry in ops.journal line 2`. Seq 1 and seq 3 are lost. Because `apps/lumencraft/src/main.rs:223-224` maps that error into `launch_application`'s `?` (`main.rs:171`), the desktop app with no file arguments exits with an error on every launch until the user deletes the recovery directory by hand.
- **Evidence:** Probe on `MemoryJournalBackend`: record seq 1, `append_raw_journal_bytes` with the first 10 bytes of a seq-2 line, then two more `record_command` calls, then `open_or_recover`:
  ```
  journal = "{\"seq\":1,...}\n{\"seq\":2,\"{\"seq\":2,\"crc32\":...,\"command_json\":{\"command_id\":\"c2-retry\"}}\n{\"seq\":3,...}\n"
  recovery = Err(Json("malformed entry in ops.journal line 2: expected `:` at line 1 column 13"))
  ```
  A CRC mismatch on the tail line is also fatal, since `verify_crc()?` (`recovery.rs:673`) runs after the tail tolerance.
- **Suggested fix:** On an append error, truncate the file back to its pre-append length (or write a newline before the next append); in recovery, stop at the first bad record and report it as discarded (as for the tail) rather than failing the whole replay.
- **Related:** `S11` (desktop startup treats recovery failure as fatal).

### R1-S06-04 · S2 · PZFX import silently drops subcolumns beyond the resolved subcolumn mode

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/pzfx.rs:420-424` (`fill_datasets` `break`), `pzfx.rs:286-292` (XY X subcolumns), `pzfx.rs:354-361` (Multiple Variables uses only the first subcolumn), `pzfx.rs:321-325` (Survival uses only the first X subcolumn), `pzfx.rs:521-528` (mode resolution ignores how many subcolumns are present)
- **Category:** data-loss
- **Defect:** The subcolumn mode comes only from the `YFormat`/`Replicates` attributes; every `<Subcolumn>` the file actually contains beyond that count is discarded without an `ImportWarning`, although the importer emits warnings for other coercions.
- **Failure scenario:** A `OneWay` table with no `YFormat` and a `YColumn` holding two `<Subcolumn>`s (values 1, 2 and 30, 40) imports as `Single` with only 1, 2; 30 and 40 vanish and `warnings` is empty. Likewise an XY table with two X subcolumns and no `XFormat` keeps only the first X subcolumn. The user analyses an incomplete table with no signal.
- **Evidence:** Probe with `import_pzfx_str`:
  ```
  pzfx subcol: subcolumns kept = 1, cells = [[Number(1.0)], [Number(2.0)]], warnings = []
  pzfx xy: x_cells = [[Number(1.0)]], warnings = []
  ```
- **Suggested fix:** When a column has more subcolumns than the mode allows, push an `ImportWarningKind::CoercedValue` naming the table, column and dropped count (or widen to `RawReplicates(n)` where the table kind allows it).
- **Related:** none.

### R1-S06-05 · S2 · `.lumencraft` open parses `document.json` into a `serde_json::Value` tree first: a 61 KB archive drives 1.1 GiB of heap

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/archive.rs:137` (`serde_json::from_slice::<Value>`), `archive.rs:143-145`
- **Category:** resources
- **Defect:** The only size bound on `document.json` is the 64 MiB ZIP entry cap (`zip.rs:19`); the whole entry is materialised as a generic `Value` tree (about 32 bytes per JSON value plus container overhead) before typed deserialisation or `validate_project_document` can reject it, so peak memory is roughly 17× the entry size and about 18,000× the compressed file.
- **Failure scenario:** `document.json` of about 60 MiB consisting of `[[],[],[],…]` with a matching CRC in `manifest.json`; the archive deflates to 61 KB. Opening it (`project.open`, desktop open, MCP open, or a crash-recovery snapshot) allocates about 1.1 GiB before failing with a type error. On `wasm32` or a low-memory host this risks an allocation abort; on desktop it is a large, avoidable spike from a tiny untrusted file.
- **Evidence:** Probe:
  ```
  lumencraft: archive bytes = 32947 -> Err(Json("invalid type: sequence, expected u32")), peak heap during open = 576 MiB
  lumencraft: archive bytes = 61464 -> Err(Json("invalid type: sequence, expected u32")), peak heap during open = 1088 MiB
  ```
- **Suggested fix:** Read `schema_version` with a small typed peek (for example a struct with only that field) and deserialise straight into `ProjectDocument` when no migration is needed; or cap `document.json` well below 64 MiB relative to the cell budget.
- **Related:** R1-S06-11 (same amplification class in the XML DOM).

### R1-S06-06 · S3 · Save validates finiteness only for cells, constants and results; a non-finite `f64` elsewhere writes a file that cannot be reopened

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/archive.rs:175-180` (`save_archive_bytes`), `archive.rs:490-492` (graph sheets only call `graph.spec.validate()`), `archive.rs:494-497` (layouts only check the title); `crates/doc/src/graph.rs:157-168`, `graph.rs:639-647`
- **Category:** data-loss (latent)
- **Defect:** `validate_project_document` rejects non-finite values in data cells, info constants and result payloads, but not in graph specs (axis `stroke_width_pt`, `tick_angle_deg`, segment `min`/`max`, error-bar widths, annotation positions) or analysis specs other than the fit bounds; `serde_json` writes such values as `null`, which then fails to deserialise into `f64` (or silently becomes `None` for `Option<f64>`).
- **Failure scenario:** Any code path that leaves `NaN` in, say, `spec.y_axis.stroke_width_pt` lets `save_project_bytes` succeed and produces an archive that `open_project_bytes` rejects; an `Option<f64>` axis bound instead silently reopens as auto-range. I found no command that stores `NaN` there today (engine float params pass through `opt_f64`'s `is_finite` filter, `crates/engine/src/cmd_data.rs:2828-2835`), so this is a latent hazard for computed values.
- **Evidence:** Probe: column table plus `GraphSheet::new_uninitialized_for_data`, `y_axis.stroke_width_pt = NaN`:
  ```
  save with NaN stroke width = Ok(1588)
  reopen = Err(Json("invalid type: null, expected f64"))
  ```
- **Suggested fix:** Make the save path reject (or the serializer error on) every non-finite `f64`, for example a `serialize_with` finite check on the doc types or a post-serialisation scan for `null` where a number is required; at minimum extend `validate_project_document` to graph, layout and analysis specs.
- **Related:** `S05` (validate methods on `GraphSpec`/`AxisSpec`); `X2`.

### R1-S06-07 · S3 · Stale-lock eviction is unlink-then-create: two concurrent recoverers can both acquire the lease

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/recovery.rs:425-455` (`DirectoryJournalBackend::acquire_lease`)
- **Category:** data-loss (race)
- **Defect:** After reading a stale lease, the backend unconditionally removes `lumencraft.lock` (`recovery.rs:446`) and then exclusively creates a new one (`recovery.rs:451`); nothing checks that the file it removes is still the stale lease it read, so a second contender can delete the first contender's fresh lock.
- **Failure scenario:** After a crash, two app instances start within the same moment (double launch, session restore). Both read the same stale lease X. B removes X and creates lock L_B (returns success). C then removes L_B and creates L_C (also returns success). Both sessions run `recover_journal_contents` and append to the same `ops.journal` with overlapping sequence numbers; the next recovery fails with `non-monotonic journal sequence` (`recovery.rs:674-677`), which with R1-S06-03 blocks startup. The same eviction also fires against a live instance after `ttl_ms`, because liveness is time-only and the desktop app never calls `renew_lease` (`RECOVERY_LOCK_TTL_MS = 300_000`, `apps/lumencraft/src/main.rs:20`).
- **Evidence:** Code trace only (interleaving not reproduced): `read_lease` at `recovery.rs:425`, `remove_file(self.lock_path())` at `recovery.rs:446`, `try_create_lock_exclusively` at `recovery.rs:451`.
- **Suggested fix:** Evict by renaming the stale lock to a unique name and re-reading it to confirm it is still lease X before deleting (or compare file identity or contents just before unlinking); have the app renew the lease periodically.
- **Related:** `S11` (no lease renewal in the desktop app).

### R1-S06-08 · S3 · An unparsable `lumencraft.lock` is a permanent acquire error rather than a stale lease

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/recovery.rs:390-404` (non-hard-link fallback), `recovery.rs:488-493` (`read_lease` propagates the JSON error), `recovery.rs:425-435`
- **Category:** data-loss / availability
- **Defect:** On filesystems without hard links (for example exFAT/FAT USB sticks used with `--portable-dir`), the fallback creates `lumencraft.lock` and then writes it in a second step; a crash in between leaves an empty or partial lock, and `acquire_lease` then fails forever because `read_lease` returns a `Json` error instead of treating the unreadable lease as stale.
- **Failure scenario:** Portable install on exFAT; power loss right after `create_new` and before the data reaches disk. Every later launch hits `try_create_lock_exclusively` → `AlreadyExists` → `read_lease` → `serde_json` error → `open_or_recover` fails → the app refuses to start (`apps/lumencraft/src/main.rs:223-224`) until the user deletes the hidden lock file.
- **Evidence:** Code trace: `create_new(true)` at `recovery.rs:393`, `write_all` + `sync_all` at `recovery.rs:395`, `serde_json::from_slice(&bytes)?` at `recovery.rs:491`, `Err(err) => return Err(err)` at `recovery.rs:434`.
- **Suggested fix:** Treat a lock that fails to parse as stale once its file modification time is older than the TTL (or immediately, with a warning in `RecoveryReport`), and write the fallback lock through the temp-file path where possible.
- **Related:** R1-S06-03.

### R1-S06-09 · S3 · `MemoryJournalBackend` writes web-storage JSON it later refuses to read back

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/recovery.rs:31`, `recovery.rs:170-178`, `recovery.rs:188-199`
- **Category:** data-loss (latent; browser binding not yet wired, per `docs/gaps.md` `G2`)
- **Defect:** `to_web_storage_json` has no size limit, and `snapshot`/`journal_bytes` are `Vec<u8>` serialised as JSON number arrays (about 3.6 bytes per byte), while `from_web_storage_json` rejects anything over 64 MiB, so any project archive above about 18 MB is stored but can never be recovered.
- **Failure scenario:** A 20 MB project snapshot is checkpointed into web storage; after a tab crash, restore fails with `web-storage journal payload exceeds budget`, losing the recovery state.
- **Evidence:** Probe: 20,000,000-byte snapshot → `web storage json bytes = 71406302 … restore = Err(Io("web-storage journal payload exceeds budget of 67108864 bytes"))`.
- **Suggested fix:** Apply the same limit on export (return an error at checkpoint time, when the session is still alive), and encode the byte buffers compactly (base64) so the limit covers realistic projects.
- **Related:** `G6` (`wasm32` hosting).

### R1-S06-10 · S3 · One overlong PZFX row title rejects the whole import, while other titles are truncated with a warning

### R1-S06-11 · S3 · XML node cap counts elements only; text nodes and attributes give about 10× memory amplification

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/xml.rs:177-180` (counts elements), `xml.rs:243-246` (text nodes uncounted), `xml.rs:263-301` (attributes uncounted, duplicates allowed)
- **Category:** resources
- **Defect:** `MAX_XML_NODES` bounds elements, but every text run between comments and every attribute allocates its own `String`/`XmlNode` without counting toward any cap, so the 64 MiB `MAX_XML_BYTES` input can become several hundred MiB of DOM.
- **Failure scenario:** `<PrismFile>` followed by `a<!---->` repeated, or one element with millions of `aN=""` attributes. 16 MiB of input produces 168 MiB (text) or 142 MiB (attributes) of heap; at the 64 MiB cap this extrapolates to about 650 MiB, before any table budget applies.
- **Evidence:** Probe with `parse_xml`: `xml text nodes: input 16777239 bytes -> Ok(2097152), peak 168 MiB`; `xml attrs: input 12582924 bytes -> Ok(2097152), peak 142 MiB`.
- **Suggested fix:** Count text nodes and attributes toward `max_nodes` (or a separate cap), and reject duplicate attribute names as XML requires.
- **Related:** R1-S06-05.

### R1-S06-12 · S3 · `PlacementMode::InsertRows` overwrites the rows at the anchor instead of inserting

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/csv.rs:1201-1204` (`place_grid_in_datasheet`)
- **Category:** contract-drift / data-loss
- **Defect:** `InsertRows` is handled exactly like `Overwrite` (start at `anchor.row` and write over existing cells); nothing shifts existing rows down, contrary to the documented "Overwrite, insert, or append" placement (`docs/data-tables-and-transforms.md:128`).
- **Failure scenario:** Applying an import link with `mode = InsertRows` at row 0 into a sheet with 10 rows of data overwrites rows 0..k with the imported grid; the user expected the data to move down and loses the overwritten cells (recoverable only through undo).
- **Evidence:** `PlacementMode::Overwrite | PlacementMode::InsertRows | PlacementMode::AppendColumns => placement.anchor.row` (`csv.rs:1202`). `apply_csv_import_link` has no caller outside `crates/format`; the live engine path uses the copy in `crates/transform/src/import.rs:443`, which has the same mapping (`PlacementMode::Overwrite | PlacementMode::InsertRows => anchor.row`) and is reached from the `insert`/`insertrows` param (`crates/engine/src/cmd_data.rs:3077`).
- **Suggested fix:** Implement row insertion (shift existing rows down by the grid height) in the live `transform` pipeline, and either delete the unused `format` copy or make it delegate, so the two cannot drift.
- **Related:** `S04` (live copy in `crates/transform`); R1-S06-13.

### R1-S06-13 · S3 · `apply_csv_import_link` header promotion maps header index to data-set index, ignoring subcolumns

### R1-S06-14 · S3 · Journal replay is unbounded in size and record count

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/recovery.rs:521-527` (`read_journal_bytes` reads the whole file), `recovery.rs:654-661`, `recovery.rs:588-595` (`record_command` has no size check)
- **Category:** resources
- **Defect:** There is no limit on `ops.journal` size, line length or record count; recovery holds the raw bytes, the line index, the parsed `Value` for every record and a cleaned copy at once, and the engine then replays every record (`crates/engine/src/lib.rs:174-182`).
- **Failure scenario:** A long session using `execute_and_record` with large-parameter commands (pastes, imports) and no checkpoint leaves a journal of hundreds of MiB; startup recovery then needs several times that in memory, can abort, and with R1-S06-03 the app cannot start. The web backend has a 64 MiB cap (`recovery.rs:31`); the directory backend has none.
- **Evidence:** Code trace of the cited lines; not run.
- **Suggested fix:** Cap journal bytes and record count on append (force a checkpoint when exceeded) and on read (fail cleanly with a structured error), streaming lines instead of reading the whole file.
- **Related:** `S07` (checkpoint policy).

## Checked, no finding
