### R1-S09-01 · S1 · Raster dashing has no length budget: one long dashed annotation line allocates without bound and aborts the app

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/render/src/rasterizer.rs:882` (`emit_dashed_subpath_pieces`, loop at `:894-921`), pieces vector at `:726`
- **Category:** no-panic (allocation abort) / resources
- **Defect:** `emit_dashed_subpath_pieces` walks every segment in full, unclipped pixel space and pushes a quad plus caps for every dash, so the number of `StrokePiece`s is proportional to path length / dash length with no cap and no clipping to the canvas before dashing.
- **Failure scenario:** `graph.addAnnotation {sheet_id, kind:"line", start_pt:[40,40], end_pt:[1e9,40], dash:"dotted"}` is accepted (`cmd_sci.rs:1910-1917` only parses two `f64`s; `GraphSpec::validate`, `graph.rs:639-647`, does not look at annotations). The chart emits it as a plain dashed `Path` with `clip: None` (`xy.rs:1309-1318`, `scales.rs:2699-2715` checks only finiteness). Any raster of that graph then dashes a ~4·10⁹ px line: at 300 dpi each dotted dash (round caps, `width_pt 1.25`) costs three pieces, about 170 MiB of heap per 10⁶ pt of line, so 10⁹ pt asks for ~170 GiB and the process aborts. The desktop canvas rasterizes the active scene on every frame (`dialogs_canvas.rs:3290-3291`), so a project file carrying this annotation aborts the app on open and loses unsaved work; `graph.exportPng`/`exportTiff` (`cmd_sci.rs:2308-2312`) and the MCP raster tools take the same path. Above about 2·10¹⁵ px `pos + take == pos` (`:901`) so the loop also never terminates. A `Shape` annotation with huge `bounds_pt` and a dash style hits the same code.
- **Evidence:** Probe: one `ScenePrimitive::Path` line from (40,40) to (40+L,40), `StrokePaint { width_pt: 1.25, dash: Dotted, cap: Round, join: Round }`, `render_scene` at 2500×1667 px (300 dpi):
  ```
  dotted line length 1e4 pt: 0.05 s, peak heap  18 MiB (image 15 MiB)
  dotted line length 1e5 pt: 0.07 s, peak heap  38 MiB
  dotted line length 1e6 pt: 0.29 s, peak heap 184 MiB
  dotted line length 4e6 pt: 1.23 s, peak heap 688 MiB
  ```
  Growth is linear in L; nothing in `render_scene` (`:146-196`) or `stroke_subpaths` (`:723-738`) bounds it. SVG and PDF are unaffected (they emit `stroke-dasharray` / `d`).
- **Suggested fix:** Clip each segment to the (stroke-radius-inflated) clip rectangle before dashing, advancing the dash phase analytically across the skipped part, and cap total pieces per path (return early or fall back to a solid stroke past the cap). Separately, bound annotation coordinates in `GraphSpec::validate`.
- **Related:** S08 (chart emits unclipped annotation paths), S07 (`graph.addAnnotation` accepts any finite coordinate), X1. Different from Known defect `G11` (image buffer size).

### R1-S09-02 · S2 · `parse_markup` is quadratic on unmatched `*`: a large text-box annotation hangs every render

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/text/src/markup.rs:375` (`handle_asterisk_run` → `find_closing_star_run`, `:382-410`), called per `*` from `parse_segment` `:202-208`
- **Category:** resources
- **Defect:** Every `*` that is followed by a non-space character scans the whole remainder of the input for a closing run; when none qualifies (closing `*` must follow a non-space character), the scan fails and the next `*` repeats it, so `k` unmatched stars cost O(k·n).
- **Failure scenario:** A graph text-box annotation (no length cap: `GraphSpec::validate` ignores annotations; MCP accepts requests up to 16 MiB, `mcp/src/protocol.rs:21`; a `.lumencraft` file has no cap) whose markdown is `"*a "` repeated. The XY compiler parses the whole markdown in one call (`xy.rs:335-338`, `:1322-1333`) on every compile, so each repaint and export stalls. Measured: 120 KB → 4.8 s per parse; extrapolating the measured n² growth, 1 MB ≈ 5 min and 16 MB ≈ 1 day, i.e. a hang. Titles are safe only because of `MAX_TITLE_BYTES = 4096` (`doc/src/error.rs:22`).
- **Evidence:** Probe, `parse_markup(&"*a ".repeat(n))`, release build:
  ```
  15000 bytes: 0.042 s   30000 bytes: 0.183 s   60000 bytes: 1.264 s   120000 bytes: 4.849 s
  ```
- **Suggested fix:** Precompute, in one pass, the positions of valid closing runs (or remember the last failed search end and skip re-scanning), making emphasis matching linear; also cap annotation text length at the document layer.
- **Related:** S08 (`expand_doc_text`), S05/S07 (annotation size limits), X1.

### R1-S09-03 · S2 · Default (selectable-text) PDF export replaces every non-WinAnsi, non-Symbol character with `?`, even with an embedded TrueType font

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/pdf/src/writer.rs:1204` (`winansi_font_byte` fallback `_ => b'?'`), used by `split_span_into_pdf_runs` `:1031-1045`; embedded font dictionary `:314-317`
- **Category:** wrong-result
- **Defect:** Selectable text is always encoded as single-byte WinAnsi (or Adobe Symbol); any other code point is silently replaced by `?`. The embedded `/FontFile2` font is also declared `/Encoding /WinAnsiEncoding` (`:315`), so it cannot carry CJK, Cyrillic, Hebrew or Arabic either, and no per-glyph outline fallback exists despite the guide promising one (`docs/graphing-and-layouts.md:100`, "selectable text + outlined vector glyph-path fallback"). The PDF writer's BiDi reordering (`:666-667`) therefore only reorders `?` characters.
- **Failure scenario:** A graph with axis title `濃度 (nM)`, legend `Концентрация` or an RTL label `שלום`, exported with `graph.exportPdf` (default `outline_text: false`, `cmd_sci.rs:2249-2265`). The PDF shows `?? (nM)`, `????????????`, `????`; export reports success with no warning. Localized users (ja, ko, zh, ru, ar, he are registered locales) get unusable figures by default.
- **Evidence:** Probe, `render_pdf` with `compress_streams: false`, text at 10 pt:
  ```
  "濃度 (nM)"     -> ["(?? \\(nM\\)) Tj"]
  "שלום"          -> ["(????) Tj"]
  "Концентрация"  -> ["(????????????) Tj"]
  with embedded TTF (build_minimal_truetype_font): /FontFile2 present, ["/F6 10.00 Tf", "(?? ) Tj", "(????) Tj"]
  ```
- **Suggested fix:** For runs containing characters outside WinAnsi/Symbol, either emit those glyphs as outlines (reuse `emit_single_outlined_glyph`) or embed the TrueType font as a `Type0`/`CIDFontType2` with `Identity-H` and a `ToUnicode` CMap; at minimum add a scene warning when a `?` substitution occurs.
- **Related:** R1-S09-08 (BiDi), S10 (localization claims in `docs/gaps.md` G13).

### R1-S09-04 · S2 · SVG export writes XML-forbidden control characters from labels, producing a file no XML parser accepts, while `validate_svg_structure` passes it

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/svg/src/writer.rs:601-614` (`escape_xml`), used for text at `:420-421`, font family `:409`, `<title>` `:174-176`
- **Category:** wrong-result
- **Defect:** `escape_xml` escapes only `& < > " '` and copies every other character, but XML 1.0 forbids C0 controls other than TAB/LF/CR (and U+FFFE/U+FFFF) even as content, so any such character in a label makes the whole document not well-formed.
- **Failure scenario:** A graph title, axis title, group or column name containing U+000B (vertical tab, as produced by some word-processor line breaks), U+0001 or similar; nothing upstream strips them (`validate_title` only checks length, `doc/src/error.rs:31-36`). `graph.exportSvg` succeeds and writes the file; browsers and editors show an XML parse error instead of the figure. The crate's own validator reports `Ok`, so the CI structural check does not catch it.
- **Evidence:** Probe rendered a scene with text `"Group\u{0B}A"` using default `SvgExportOptions`:
  ```
  validate_svg_structure: Ok(())
  contains raw U+000B: true
  xml.parsers.expat.ExpatError: not well-formed (invalid token): line 4, column 162
  ```
- **Suggested fix:** In `escape_xml`, drop or replace (for example with U+FFFD or a space) characters not in the XML `Char` production, and make `validate_svg_structure` reject them.
- **Related:** none.

### R1-S09-05 · S3 · PDF writer measures text with its own approximate Helvetica/Symbol width table, so centred and right-aligned PDF text is misplaced

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/pdf/src/writer.rs:1288-1315` (`helvetica_advance_thousandths`), `:1318-1332` (`symbol_advance_thousandths`), used by `measure_span_width_pt` `:1263-1281` and the anchor offset `:668-669`, and to re-open text blocks after colour/alpha changes `:711`, `:758`
- **Category:** contract-drift / wrong-result
- **Defect:** The PDF writer duplicates width tables that disagree with the Core-14 metrics the viewer actually uses (for example regular `i`/`j`/`l` = 278 vs 222, `@` = 556 vs 1015, bold computed as `base + base/18` so bold `n` = 586 vs 611, most Symbol Greek = 600), while `lumencraft-text` already holds the per-glyph AFM tables (`crates/text/src/metrics.rs:195-213`, `215-299`) that the chart layout uses.
- **Failure scenario:** End- or Middle-anchored labels (right-aligned category labels, centred titles) are offset from where the chart laid them out. Probe, End anchor at x = 300, 10 pt: `"Vehicle + inhibitor"` is placed 2.8 pt too far left, `"Lipid (mg/dl) @ 4 °C"` 2.9 pt too far right, `"\delta\sigma\tau\theta"` 3.4 pt (17 % of its width) too far left, so labels no longer line up with their ticks and differ from the PNG/SVG of the same scene.
- **Evidence:** Probe compared the `Tm` x-offset written for an End-anchored label with `lumencraft_text::measure_text_pt` on the same markup:
  ```
  "<b>Concentration (nM)</b>": PDF writer width 90.660 pt, AFM width 91.660 pt
  "Vehicle + inhibitor":       PDF writer width 82.000 pt, AFM width 79.200 pt
  "Lipid (mg/dl) @ 4 °C":      PDF writer width 87.370 pt, AFM width 90.280 pt
  "\delta\sigma\tau\theta":    PDF writer width 24.000 pt, AFM width 20.570 pt
  ```
- **Suggested fix:** Expose `core14_advance_em` (or a byte-level helper) from `lumencraft-text` and use it in `measure_span_width_pt`, deleting the local tables.
- **Related:** none.

### R1-S09-06 · S3 · Multi-line text is broken into lines only by the raster/outline paths; selectable PDF and editable SVG put all lines on one baseline

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/pdf/src/writer.rs:1174` (`'\n'` → space) in `emit_selectable_span` `:745-757`; `crates/svg/src/writer.rs:420-421` (whole span in one `<tspan>`, `xml:space="preserve"` from `:549-572`)
- **Category:** wrong-result
- **Defect:** `measure_text_pt` (`metrics.rs:92-96`) and `outline_rich_text` (`glyph_paths.rs:83-95`) treat `\n` as a line break, and the XY compiler passes a whole multi-line text box as one `PositionedText` (`xy.rs:1322-1333`), but the PDF writer turns `\n` into a space and the SVG writer keeps it inside one `<tspan>`, which SVG renders as a space.
- **Failure scenario:** A two-line text-box annotation on an XY graph: PNG shows two lines inside the box; the PDF and SVG exports show `Line one Line two` on one line running out of the box.
- **Evidence:** Probe, text `"Line one\nLine two"`: PDF ops `["... 300.000 200.000 Tm", "(Line one Line two) Tj"]`; SVG `<tspan>Line one\nLine two</tspan>`; text crate measures 22.0 pt (two lines) and places the second line's glyphs at y = 12.0 pt.
- **Suggested fix:** Split spans at `\n` in both writers and start a new line (`T*`/`Td` with the same 1.2 em leading in PDF; a new `<tspan x=… dy=…>` in SVG).
- **Related:** S08 (`render_annotation` text box layout).

### R1-S09-07 · S3 · With `BUNDLED_FONTS` empty, raster and outlined text draw every accented Latin letter as an empty box

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/text/src/glyph_paths.rs:730` (fallback box in `build_glyph_strokes`, `:710-731`), reached from `crates/render/src/rasterizer.rs:1039`
- **Category:** contract-drift
- **Defect:** The clean-room stroke tables cover ASCII, Greek, a math set and a few Latin-1 symbols (`°`, `²`, `Å`…), but no accented letters (`é`, `ü`, `ö`, `ñ`, `ç`, `ß`…); everything else gets a rectangle, although the doc comment promises "seamless clean-room fallback" (`glyph_paths.rs:42-46`) and AGENTS.md requires everything to run with `BUNDLED_FONTS` empty.
- **Failure scenario:** Default build (no `LUMENCRAFT_FONTS_DIR`), axis title `Größe (µm)` or legend `Protéine`: PNG/TIFF exports and the desktop canvas show `Gr□□e`, `Prot□ine`, while the selectable PDF and editable SVG of the same graph show the correct text. Users of the registered de/fr/es/pt-BR locales hit this with ordinary labels.
- **Evidence:** `grep` finds no Latin-1 letter (`00E0`–`00FF`) in `glyph_paths.rs`; `build_glyph_strokes` returns the box for any character not matched by the six tables (`:711-730`). Probe output for the same label in PDF: `(Gr\366\337e \() Tj` (correct WinAnsi), confirming the backends disagree.
- **Suggested fix:** Compose Latin-1 and Latin Extended-A letters from the base letter strokes plus accent strokes (acute, grave, diaeresis, tilde, cedilla, ring, caron), and add a warning to the scene when the box fallback is used.
- **Related:** R1-S09-03.

### R1-S09-08 · S3 · BiDi reordering is applied only by the PDF writer; PNG/TIFF and outlined SVG draw RTL text in logical order

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/render/src/rasterizer.rs:1039` (`render_text` calls `outline_rich_text` directly), `crates/svg/src/writer.rs:430` (`write_outlined_text`); compare `crates/pdf/src/writer.rs:666-667`, `:769-771`

- **Failure scenario:** Label `IC50 שלום` (or any Hebrew/Arabic title) with a bundled font that has the glyphs: the PNG shows the Hebrew word reversed and the run order wrong, while the outlined PDF of the same scene is correct. With `BUNDLED_FONTS` empty the boxes still appear in the wrong run order.

- **Suggested fix:** Move the `reorder_rich_text_bidi` helper into `lumencraft-text` and apply it in `outline_rich_text` callers (rasterizer and SVG outline mode), or inside `outline_rich_text` itself.
- **Related:** R1-S09-03.

### R1-S09-09 · S3 · cmap format 4 collection iterates every code of every segment even when nothing is kept: a 262 KB font takes 3.2 s to validate

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/text/src/metrics.rs:1226-1260` (`collect_cmap_format4`); the only guard is `MAX_CMAP_COLLECT` on pushed entries (`:696`, `:1239`)
- **Category:** resources
- **Defect:** The loop bound is the number of codes covered by segments (up to 32,767 × 65,535 ≈ 2.1·10⁹), but the cap only counts accepted mappings, so a table whose mappings are all rejected (`gid == 0 || gid >= num_glyphs`) runs to completion.
- **Failure scenario:** A user-supplied `--ttf-font` (`cmd_convert.rs:185-187`, desktop `main.rs:324`) with `numGlyphs = 1` and 32,767 format-4 segments each spanning `0x0000..=0xFFFE` blocks the CLI or app start for seconds (longer in debug builds, and scales with segment count).
- **Evidence:** Probe built a 262,360-byte SFNT (`head`, `hhea`, `maxp numGlyphs=1`, `hmtx`, `cmap` (3,1) format 4 with 32,767 such segments): `parse_truetype_font_info -> ok=true in 3.185 s`.
- **Suggested fix:** Count iterations, not pushes (for example a total budget of 65,536 or 2¹⁷ codes across segments), or skip a segment whose `idDelta`/`idRangeOffset` cannot produce an in-range glyph.
- **Related:** S11/S12 (font loading entry points).

### R1-S09-10 · S3 · Compound-glyph decoding has a depth cap but no total budget: 64 components per level × 8 levels is exponential (latent, bundled fonts only)

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/text/src/glyph_paths.rs:395` (`for _ in 0..64`), recursion `:442`, depth cap `:19`, `:225-227`
- **Category:** resources
- **Defect:** Each compound glyph may reference up to 64 components, each of which may itself be compound, down to `MAX_TTF_COMPONENT_DEPTH = 8`, so one glyph can trigger 64⁷ simple-glyph decodes and unbounded growth of `out`; `MAX_TTF_POINTS` limits only each simple glyph.
- **Failure scenario:** Not reachable from user files today, because only `BUNDLED_FONTS` (build time) reach `TrueTypeFont`/`outline_ttf_glyph`; user `--ttf-font` files go through `parse_truetype_font_info` only. A malformed or hostile face placed in `LUMENCRAFT_FONTS_DIR` would hang every text render of the affected glyph.
- **Evidence:** Code read of `decode_compound_ttf_glyph` (`:383-448`) and `decode_ttf_glyph_recursive` (`:214-244`).
- **Suggested fix:** Thread a total component/point budget through the recursion and return `None` when it is exhausted.
- **Related:** none.

- **Raster indexing:** pixel writes are bounds-checked (`rasterizer.rs:66-73`); scanline spans are clamped to clip and canvas (`:588-613`, `:616-637`); Bézier flattening depth-capped (`:14`, `:435`, `:455`); non-finite points dropped (`:341-350`).
- **Font fallback with `BUNDLED_FONTS` empty:** `select_bundled_font` returns `None` (`metrics.rs:497-503`) and metrics fall back to Core-14 tables (`:136-167`); PDF always declares the Core-14 fonts (`writer.rs:253-257`); SVG skips `@font-face` (`svg/src/writer.rs:192`). Gaps: R1-S09-03, R1-S09-07.
- **Markup recursion and BiDi indexing:** recursion capped by `MAX_MARKUP_DEPTH` (`markup.rs:6`, `:164`, `:488`); paragraph splitting slices after single-byte `\r` (`:893`); W4 neighbour indexing stays in range (`:1023-1026`); bracket stack capped at 63 (`:1134-1145`).
- **User `--ttf-font` validation:** malformed or CFF fonts are rejected before reaching the PDF writer (`apps/lumencraft-cli/src/cmd_convert.rs:185-193`), so the PDF writer's `.ok()` at `writer.rs:147` does not hide a user error on that path.
