### R1-S12-01 · S1 · `--workdir` sandbox is bypassed by external-link paths stored inside a project or template

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/engine/src/cmd_data.rs:193` (read of `LinkSource::ExternalDelimitedFile.path`), reached from `crates/engine/src/cmd_data.rs:525` (`project.recalculate`); sandbox only rewrites command params at `apps/lumencraft-cli/src/sandbox.rs:107`; archives loaded unscanned at `apps/lumencraft-cli/src/cmd_run_batch.rs:386-397`
- **Category:** security
- **Defect:** The sandbox resolves path *parameters*, but a `.lumencraft`/`.lctemplate` document carries `linked_regions[].spec.source.ExternalDelimitedFile.path` strings that `project.recalculate` passes straight to `std::fs::read_to_string`, with no workdir check.
- **Failure scenario:** `lumencraft-cli batch manifest.json --workdir .` where the manifest names `"project": "evil.lumencraft"` (inside the workdir) and runs `project.recalculate` then `table.exportCsv {path: "out.csv"}`. `evil.lumencraft` holds an external link to any absolute path (for example a file in the user's home directory). The run reads that file outside the workdir into sheet `d1` and writes its contents to `out.csv` inside the workdir, exit code 0. The same works with no file at all in the workdir: a `run` script can call `project.open {bytes_base64: …}` (`bytes_base64` is not a path key) with an archive carrying the link. Templates keep the links too: `strip_project_data_for_template` copies `linked_regions` unchanged (`crates/format/src/archive.rs:272`, `:284`).
- **Evidence:** Ran at the base with the debug CLI. Setup (unsandboxed `run`): import CSV into `d1`, re-import with `path=<abs>/outside/secret.csv, link=true`, `project.save` into `wd/evil.lumencraft`. Then changed `outside/secret.csv` to `x,y\n777,888\n999,111`. Sandboxed run: `batch manifest.json --workdir .` printed `batch completed: 0 input(s), 2 command(s), 0 export(s)`, exit 0, and `wd/out.csv` contained `777` and `999`, the bytes only present in the file outside the workdir. `resolve_link_source_payload` (`cmd_data.rs:193-198`) reads `path` whenever `include_external_links` is true, which `cmd_project_recalculate` sets (`cmd_data.rs:525`).
- **Suggested fix:** Give the engine a path policy (a resolver callback or allowed root on `Session`) that every filesystem access goes through, including stored link paths, and have the CLI install the `WorkdirGuard` there; until then, reject or drop `ExternalDelimitedFile` links from documents loaded under `--workdir`.
- **Related:** R1-S07-02 (engine side: `project.recalculate` reads the stored path), S06 (archive and template keep it), X1.

### R1-S12-02 · S1 · JSON project input skips `validate_project_document`; a 0.8 KB file panics `convert`

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft-cli/src/cmd_convert.rs:307` (`load_project_json`), reached from `:229` (`.json` extension) and `:334` (any input whose first non-blank byte is `{`); used by `convert`, `info`, `bench` and the batch manifest `project` key (`apps/lumencraft-cli/src/cmd_run_batch.rs:394`)
- **Category:** no-panic
- **Defect:** `load_project_json` deserializes a `ProjectDocument` with `serde_json::from_slice` and returns it without the checks the archive path runs (`validate_project_document`, `crates/format/src/archive.rs:144`, `:470-500`: title, sheet-count, unique-ID, row/subcolumn caps and dependency-cycle checks).
- **Failure scenario:** A JSON project whose XY table has `"y_subcolumn_mode": {"RawReplicates": 400000000000000000}` (793 bytes). `lumencraft-cli convert evil.json out.csv` reaches `push_dataset_headers` (`crates/format/src/csv.rs:575`), whose `SubcolumnMode::subcolumn_labels` collects `1..=n` labels (`crates/doc/src/cell.rs:208`) and the process panics with `capacity overflow`. With `RawReplicates: 20000000` the same 793-byte file drives the process to 1.4 GB RSS and writes a 229 MB CSV. The archive loader rejects these values (`validate_subcolumns`, `archive.rs:520`). The same file works as `"project": "evil.json"` in a sandboxed batch manifest.
- **Evidence:** Ran at the base: exported a valid project to JSON with `convert ok.lumencraft ok.json`, patched `y_subcolumn_mode`, then `convert evil2.json evil2_out.csv` printed `panicked at …/raw_vec/mod.rs:28:5: capacity overflow`. With `20000000`, `/usr/bin/time -l` reported `1403027456 maximum resident set size` and `csv, 228888906 bytes`.
- **Suggested fix:** Call `lumencraft_format::validate_project_document` (and the circular-hook sanitizer) on every document loaded from JSON, or route JSON input through the same migrate-and-validate path as `open_archive_bytes`.
- **Related:** S05 (`subcolumn_labels` allocates from an unchecked count), S06 (validation lives there), X1.

### R1-S12-03 · S1 · MCP `save_file` without `path` overwrites the previously opened file after a command replaced the document

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/mcp/src/tools.rs:766` (falls back to `state.session.file_path()`); `crates/mcp/src/tools.rs:957` (`command_run`/`command_batch` execute document-replacing commands without touching `file_path`); `crates/engine/src/lib.rs:294-342` (`Session::execute` never updates `file_path`)
- **Category:** data-loss
- **Defect:** `open_file` binds the session to a file path (`tools.rs:633`), but engine commands that replace the whole document (`project.new` at `crates/engine/src/cmd_data.rs:298`, `project.open` at `:304`, `project.instantiateTemplate` at `:376`, non-merge `table.importPrism` at `:2236`, non-merge `table.importPzfx` at `:2263`) leave that binding in place, and `save_file {}` then writes the new document over the old file.
- **Failure scenario:** An MCP client calls `open_file {path: "A.lumencraft"}`, then `command_run {command_id: "project.new", params: {title: "Scratch"}}`, then `save_file {}` (the schema says the path "defaults to current project path when available", `tools.rs:239`). `A.lumencraft` is replaced by an empty project titled `Scratch`. No warning or error is returned.
- **Evidence:** Ran at the base through `lumencraft-cli mcp` with newline JSON-RPC on stdin. Before: `info A.lumencraft` showed `Sheets (1 total): 1 tables`. The `save_file` reply reported `"path": ".../A.lumencraft"`. After: `info A.lumencraft` showed `Title: Scratch` and `Sheets (0 total)`.
- **Suggested fix:** Clear `file_path` (or mark it stale) whenever a command replaces the document: in `execute_single_command` for the document-replacing command IDs, or in `Session::execute` itself so the desktop shares the rule; require an explicit `path` once the binding is stale.
- **Related:** S07 (`Session` file-path ownership), S11 (desktop may share the pattern).

### R1-S12-04 · S1 · MCP `render_preview` and `export` compile and render outside the engine panic guard; one bad graph ends the server and loses the session

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/mcp/src/tools.rs:1003` (`render_preview` → `compile_visual_sheet`), `:1042-1057` (`export` → `export_*_tool`), `:1350-1385` (`compile_visual_sheet` calls `compile_graph`/`compile_layout` directly), `:1105`/`:1112` (`all_graphs` PDF); dispatch at `crates/mcp/src/protocol.rs:326` has no `catch_unwind`. Only `Session::execute` is guarded (`crates/engine/src/lib.rs:318`, `guard::run_guarded`). CLI equivalent: `apps/lumencraft-cli/src/cmd_convert.rs:339-351`, reached from batch exports at `apps/lumencraft-cli/src/cmd_run_batch.rs:110`.
- **Category:** no-panic
- **Defect:** The MCP tools that render (`render_preview`, `export` for svg/pdf/png/tiff) call the chart compiler, rasterizer and encoders on the live document without `lumencraft_engine::guard::run_guarded`, so any panic in S08/S09 code unwinds through `call_tool` and `serve` and ends the `lumencraft-cli mcp` process.
- **Failure scenario:** An MCP client creates a Contingency table, `graph.create`, then `graph.setSpec {spec: {canvas_size_pt: {width: 30, height: 200}, y_axis: {title: "Count"}}}` (accepted), then calls `render_preview {sheet_id: "g1"}`. The server panics in the chart compiler (the R1-S08-02 `clamp`), exits with status 101, never answers that request or the following ones, and every unsaved edit in the in-memory session is gone. The same graph exported through the engine command `command_run graph.exportSvg` returns `recovered from internal panic` and the session survives. In the CLI, a batch manifest whose `exports` entry renders such a graph exits 101 with a Rust panic message instead of the documented exit code 1.
- **Evidence:** Ran at the base. MCP newline stream: requests 1-3 (`table.importCsv` kind `contingency`, `graph.create`, `graph.setSpec`) answered; request 4 `render_preview` produced on stderr `panicked at …/core/src/num/f64.rs:1585:9: min > max, or either was NaN. min = 11.0, max = 6.399999999999999`; exit status `101`; request 5 `doc_inspect` got no reply. Same requests 1-3 then `command_run graph.exportSvg` gave `isError: true`, text `graph.exportSvg: recovered from internal panic: min > max…`, and request 5 `doc_inspect` answered with `"dirty": true`.
- **Suggested fix:** Wrap every MCP tool handler (or `call_tool` as a whole) in `guard::run_guarded` and map the error to `isError: true`; do the same around `export_from_document` in the CLI so panics surface as exit code 1.
- **Related:** R1-S08-02 (the panic used here; any other compiler or rasterizer panic has the same effect), S09, X1.

### R1-S12-05 · S2 · MCP `open_file {append: true}` reports the session clean and drops its undo history

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/mcp/src/tools.rs:731-739`; `crates/engine/src/lib.rs:258-260` (`Session::from_document` sets `dirty: false` and empty undo/redo stacks); `crates/engine/src/lib.rs:276-281` (`set_file_path(_, false)` leaves `dirty` as is)
- **Category:** data-loss
- **Defect:** Append rebuilds the session with `Session::from_document`, which resets `dirty` to `false` and empties the undo stack, and then calls `set_file_path(existing_path, !is_dirty)`, which can only clear `dirty`, never restore it; so after an append the session always reports `dirty: false`, even though it now holds a new sheet and possibly earlier unsaved edits.
- **Failure scenario:** `open_file {path: "a.csv"}`, `command_run table.setCell {sheet_id: "a", row: 0, col: 0, value: 99}` (`dirty: true`), then `open_file {path: "b.csv", append: true}`. `doc_inspect` now reports `"dirty": false` with two sheets, and `command_run edit.undo` answers `nothing to undo`. A client that saves only when `dirty` is true (the flag exists for that) skips saving, and the cell edit and the appended sheet are lost when the server exits; the edit can no longer be undone either. The non-append import paths (`tools.rs:683`, `:749`) likewise present a never-saved imported document as `dirty: false`.
- **Evidence:** Ran at the base through `lumencraft-cli mcp`: replies were `2 {'dirty': True, 'mutated': True, 'message': 'updated cell'}`, `3 {'dirty': True, 'total_sheet_count': 1}`, `5 {'dirty': False, 'total_sheet_count': 2}`, `6 {'dirty': False, 'mutated': False, 'message': 'nothing to undo'}`.
- **Suggested fix:** Append through the engine (`Session::execute` of an import command, so undo and dirty tracking apply), or add a `Session` method that adds a sheet as an undoable mutation; mark freshly imported, never-saved documents dirty.
- **Related:** S07 (`Session` dirty and undo ownership), R1-S12-03 (same pattern of session metadata going stale).

### R1-S12-06 · S2 · An over-limit `Content-Length` frame ends the MCP server instead of being skipped, losing the session

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/mcp/src/protocol.rs:436-441` (`parse_headers_content_length` failure → `NextFrame::FatalError`), `:470-479` (limit check), `:151-155` (`FatalError` writes one reply and returns from `serve`)
- **Category:** data-loss
- **Defect:** When a well-formed `Content-Length` header exceeds `MAX_REQUEST_BYTES` (16 MiB), the stream is still in sync (the length is known), but the server reports a fatal error with `id: null` and stops serving; an over-long newline-framed line, by contrast, is drained and answered as a recoverable error (`protocol.rs:379-385`).
- **Failure scenario:** A client using `Content-Length` framing imports data, then sends `command_run table.importCsv` with a 17 MiB inline `csv`. The server replies `Content-Length 22282435 exceeds maximum 16777216 bytes` with `"id": null`, exits with status 0, and the earlier unsaved import is lost; the following `doc_inspect` request is never answered. The client cannot tell which request failed, because the error has no id.
- **Evidence:** Ran at the base: three `Content-Length` frames (small `table.importCsv`, 22 MB `table.importCsv`, `doc_inspect`) piped into `lumencraft-cli mcp`. Output: reply to id 1, then `{"jsonrpc":"2.0","id":null,"error":{"code":-32600,"message":"Content-Length 22282435 exceeds maximum 16777216 bytes"}}`, then end of output with exit 0.
- **Suggested fix:** For a parsed length above the cap, consume and discard exactly that many bytes in bounded chunks (no buffering), reply with a recoverable `-32600`, and keep serving; keep `FatalError` for headers that leave the stream unsynchronized.
- **Related:** X1.

### R1-S12-07 · S3 · MCP `export {format: "csv", tab_id}` ignores `tab_id` unless `tidy: false` is also passed

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c

- **Category:** contract-drift
- **Defect:** The result-sheet branch checks `tidy` before `tab_id`, and `tidy` defaults to `true`, so a request that names a tab but leaves `tidy` unset gets the tidy export of every tab instead of the named tab, with no warning; the schema lists `tidy` and `tab_id` as independent options.

- **Evidence:** Traced by reading `tools.rs:1248` and `:1268-1279`; not run.
- **Suggested fix:** Treat an explicit `tab_id` as `tidy: false` (or reject the combination `tidy: true` + `tab_id` with `InvalidParams`), and document the rule in the schema.
- **Related:** none.

### R1-S12-08 · S3 · `lumencraft-cli info` prints sheet titles raw, so an archive can send terminal escape sequences

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft-cli/src/cmd_info.rs:237-238`, `:257-295` (titles, IDs and warnings printed with `println!` and no escaping), `:249-253` (import warnings)
- **Category:** security
- **Defect:** The human-readable `info` output writes document-controlled strings (project, sheet, graph and layout titles, import warning text) to the terminal unescaped; neither `doc` nor `format` rejects control characters in titles (no `is_control` check in `crates/doc/src` or `crates/format/src`).
- **Failure scenario:** A received `evil.lumencraft` whose table title is `ok\x1b[1A\x1b[2K\x1b]52;c;<base64>\x07`. Running `lumencraft-cli info evil.lumencraft` (the command meant for inspecting files) erases the previous output line and sends an OSC 52 clipboard write; terminals that honour OSC 52 replace the clipboard with attacker text, and cursor sequences can hide or rewrite the rest of the report (for example the warnings). `--json` output is escaped and is not affected.
- **Evidence:** Ran at the base: `run` script `project.open`, `sheet.rename {title: "ok\u001b[1A\u001b[2K\u001b]52;c;ZWNobyBwd25lZA==\u0007"}`, `project.save`; then `info esc.lumencraft | od -c` showed `o k 033 [ 1 A 033 [ 2 K 033 ] 5 2 ; c ; … \a` in the `Tables:` line.
- **Suggested fix:** Escape or replace C0/C1 control characters (and U+007F) when printing untrusted strings in human-readable CLI output, for example with `char::escape_debug` on control characters only.
- **Related:** S05 (titles accept control characters), R1-S09-04 (same characters break SVG export).

## Checked, no finding

- **Engine path keys vs `PATH_PARAM_KEYS`:** every engine filesystem access driven by a parameter reads one of `path`, `file_path`, `filePath`, `source_path`, `sourcePath`, `template_path`, `templatePath` (`crates/engine/src/cmd_data.rs:305`, `:331`, `:354`, `:378`, `:2038`, `:2106`, `:2150`, `:2212`, `:2221`, `:2249`; `crates/engine/src/cmd_sci.rs:217`, `:241`, `:2230`, `:2287`, `:2315`, `:2348`), and all are in `apps/lumencraft-cli/src/sandbox.rs:15-44`. `opt_str` matches keys exactly (`cmd_data.rs:2792`, `cmd_sci.rs:2414`), so no case or alias variant slips past. The extra keys in the list (`input`, `output`, `file`, `project`, `template`, …) are read by no engine command, so rewriting them corrupts nothing. The only path not reached by the sandbox is the one stored inside documents (R1-S12-01).
- **Nested params:** `sanitize_params` recurses through objects and arrays (`sandbox.rs:107-127`), so `table.pasteLink {link_spec: {source: {ExternalDelimitedFile: {path}}}}` is rewritten; recursion depth is bounded by `serde_json`'s 128-level parse limit.
- **`..`, absolute paths, symlinks:** `..` is rejected before joining (`sandbox.rs:146-156`); absolute paths pass only if the canonical result starts with the canonical root (`sandbox.rs:72-78`); the deepest existing ancestor is canonicalized, so symlinks to outside are caught, and dangling symlinks are rejected (`sandbox.rs:160-190`). Windows drive-relative and UNC inputs replace the joined root and then fail the `starts_with` check (reasoned from `Path::join` semantics; not run on Windows).
- **Batch implicit recalculation:** `Session::recalculate_all` (`crates/engine/src/lib.rs:367-372` → `dag.rs:51-57`) does not refresh external links, so the recalculation `batch` always runs (`cmd_run_batch.rs:105`) does not widen R1-S12-01; only an explicit `project.recalculate` does.
- **Manifest parsing:** schema tag check, `template`/`project` exclusivity, and type and range checks for `dpi`, `tab_index`, `pdf_version`, `ttf_font` (`cmd_run_batch.rs:216-384`); every manifest path (inputs, exports, font, template, project) goes through the resolver.
- **JSON-RPC framing and limits:** header line cap 8 KiB and 32 headers (`protocol.rs:399-426`); `Content-Length` digits only, overflow-safe parse and cap check (`:470-480`); body read in 8 KiB chunks without preallocating the declared length (`:482-504`); over-long newline lines are drained and answered (`:506-551`); empty and over-256 batches rejected (`:187-196`); non-scalar `id` rejected (`:237-245`); non-object `params`/`arguments` rejected (`:226-232`, `:318-324`).
- **MCP argument bounds:** raster edges ≤ 8192, DPI 18-2400, `svg_precision` 1-8 (`tools.rs:1000-1001`, `:1440-1445`, `:1066`); `command_batch` ≤ 1024 items (`:860`); replicate count 1-256 (`:1488-1495`); single-character delimiters (`:708-717`, `:1251-1259`).
- **Live control client:** loopback `127.0.0.1` only, 2 s connect and 5 s I/O timeouts, 16 MiB response cap and request-id check (`tools.rs:1638-1709`).
- **Indexing in CLI and MCP code:** every `[0]` follows a length check (`cmd_convert.rs:364-365`, `:466-467`; `cmd_run_batch.rs:470-471`); `encode_base64` indexes non-empty chunks only (`tools.rs:1594-1595`); framing slices stay within `fill_buf` lengths (`protocol.rs:499`, `:520`).
- **Known defects, not re-reported:** CLI `convert`/`bench` clamp each raster edge to 16384 px (`cmd_convert.rs:484-486`, `cmd_bench_perf.rs:394-396`) with no total-pixel cap; that is Known defect `G11` (no `MAX_RASTER_PIXELS` in `crates/render/src` at this base). Every MCP and CLI command clones the whole document and pushes undo without bound (`crates/engine/src/lib.rs:317`, `:331`); that is Known defect `G12`, also unfixed at this base.
