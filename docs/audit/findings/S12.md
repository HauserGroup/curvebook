### R1-S12-01 · S1 · `--workdir` sandbox is bypassed by external-link paths stored inside a project or template

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/engine/src/cmd_data.rs:193` (read of `LinkSource::ExternalDelimitedFile.path`), reached from `crates/engine/src/cmd_data.rs:525` (`project.recalculate`); sandbox only rewrites command params at `apps/lumencraft-cli/src/sandbox.rs:107`; archives loaded unscanned at `apps/lumencraft-cli/src/cmd_run_batch.rs:386-397`
- **Category:** security
- **Defect:** The sandbox resolves path *parameters*, but a `.lumencraft`/`.lctemplate` document carries `linked_regions[].spec.source.ExternalDelimitedFile.path` strings that `project.recalculate` passes straight to `std::fs::read_to_string`, with no workdir check.
- **Failure scenario:** `lumencraft-cli batch manifest.json --workdir .` where the manifest names `"project": "evil.lumencraft"` (inside the workdir) and runs `project.recalculate` then `table.exportCsv {path: "out.csv"}`. `evil.lumencraft` holds an external link to any absolute path (for example a file in the user's home directory). The run reads that file outside the workdir into sheet `d1` and writes its contents to `out.csv` inside the workdir, exit code 0. The same works with no file at all in the workdir: a `run` script can call `project.open {bytes_base64: …}` (`bytes_base64` is not a path key) with an archive carrying the link. Templates keep the links too: `strip_project_data_for_template` copies `linked_regions` unchanged (`crates/format/src/archive.rs:272`, `:284`).
- **Evidence:** Ran at the base with the debug CLI. Setup (unsandboxed `run`): import CSV into `d1`, re-import with `path=<abs>/outside/secret.csv, link=true`, `project.save` into `wd/evil.lumencraft`. Then changed `outside/secret.csv` to `x,y\n777,888\n999,111`. Sandboxed run: `batch manifest.json --workdir .` printed `batch completed: 0 input(s), 2 command(s), 0 export(s)`, exit 0, and `wd/out.csv` contained `777` and `999`, the bytes only present in the file outside the workdir. `resolve_link_source_payload` (`cmd_data.rs:193-198`) reads `path` whenever `include_external_links` is true, which `cmd_project_recalculate` sets (`cmd_data.rs:525`).
- **Suggested fix:** Give the engine a path policy (a resolver callback or allowed root on `Session`) that every filesystem access goes through, including stored link paths, and have the CLI install the `WorkdirGuard` there; until then, reject or drop `ExternalDelimitedFile` links from documents loaded under `--workdir`.
- **Related:** S07 (engine reads the stored path), S06 (archive and template keep it), X1.

### R1-S12-02 · S1 · JSON project input skips `validate_project_document`; a 0.8 KB file panics `convert`

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `apps/lumencraft-cli/src/cmd_convert.rs:307` (`load_project_json`), reached from `:229` (`.json` extension) and `:334` (any input whose first non-blank byte is `{`); used by `convert`, `info`, `bench` and the batch manifest `project` key (`apps/lumencraft-cli/src/cmd_run_batch.rs:394`)
- **Category:** no-panic
- **Defect:** `load_project_json` deserializes a `ProjectDocument` with `serde_json::from_slice` and returns it without the checks the archive path runs (`validate_project_document`, `crates/format/src/archive.rs:144`, `:470-500`: title, sheet-count, unique-ID, row/subcolumn caps and dependency-cycle checks).
- **Failure scenario:** A JSON project whose XY table has `"y_subcolumn_mode": {"RawReplicates": 400000000000000000}` (793 bytes). `lumencraft-cli convert evil.json out.csv` reaches `push_dataset_headers` (`crates/format/src/csv.rs:575`), whose `SubcolumnMode::subcolumn_labels` collects `1..=n` labels (`crates/doc/src/cell.rs:208`) and the process panics with `capacity overflow`. With `RawReplicates: 20000000` the same 793-byte file drives the process to 1.4 GB RSS and writes a 229 MB CSV. The archive loader rejects these values (`validate_subcolumns`, `archive.rs:520`). The same file works as `"project": "evil.json"` in a sandboxed batch manifest.
- **Evidence:** Ran at the base: exported a valid project to JSON with `convert ok.lumencraft ok.json`, patched `y_subcolumn_mode`, then `convert evil2.json evil2_out.csv` printed `panicked at …/raw_vec/mod.rs:28:5: capacity overflow`. With `20000000`, `/usr/bin/time -l` reported `1403027456 maximum resident set size` and `csv, 228888906 bytes`.
- **Suggested fix:** Call `lumencraft_format::validate_project_document` (and the circular-hook sanitizer) on every document loaded from JSON, or route JSON input through the same migrate-and-validate path as `open_archive_bytes`.
- **Related:** S05 (`subcolumn_labels` allocates from an unchecked count), S06 (validation lives there), X1.

### R1-S12-03 · S1 · MCP `save_file` without `path` overwrites the previously opened file after a command replaced the document

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/mcp/src/tools.rs:766` (falls back to `state.session.file_path()`); `crates/mcp/src/tools.rs:957` (`command_run`/`command_batch` execute document-replacing commands without touching `file_path`); `crates/engine/src/lib.rs:294-342` (`Session::execute` never updates `file_path`)
- **Category:** data-loss
- **Defect:** `open_file` binds the session to a file path (`tools.rs:633`), but engine commands that replace the whole document (`project.new` at `crates/engine/src/cmd_data.rs:298`, `project.open` at `:304`, `project.instantiateTemplate` at `:376`, non-merge `table.importPrism` at `:2236`, non-merge `table.importPzfx` at `:2263`) leave that binding in place, and `save_file {}` then writes the new document over the old file.
- **Failure scenario:** An MCP client calls `open_file {path: "A.lumencraft"}`, then `command_run {command_id: "project.new", params: {title: "Scratch"}}`, then `save_file {}` (the schema says the path "defaults to current project path when available", `tools.rs:239`). `A.lumencraft` is replaced by an empty project titled `Scratch`. No warning or error is returned.
- **Evidence:** Ran at the base through `lumencraft-cli mcp` with newline JSON-RPC on stdin. Before: `info A.lumencraft` showed `Sheets (1 total): 1 tables`. The `save_file` reply reported `"path": ".../A.lumencraft"`. After: `info A.lumencraft` showed `Title: Scratch` and `Sheets (0 total)`.
- **Suggested fix:** Clear `file_path` (or mark it stale) whenever a command replaces the document: in `execute_single_command` for the document-replacing command IDs, or in `Session::execute` itself so the desktop shares the rule; require an explicit `path` once the binding is stale.
- **Related:** S07 (`Session` file-path ownership), S11 (desktop may share the pattern).
