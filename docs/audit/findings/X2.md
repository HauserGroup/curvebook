### R1-X2-01 · S1 · A result that fails to recompute keeps its old numbers, and hooks, chained analyses and graph overlays keep using them as current

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/engine/src/dag.rs:469` (`recompute_result_sheet`, error branch), consumed by `crates/doc/src/result.rs:200` (`lookup_scalar`), `crates/transform/src/ops/mod.rs:65`, `crates/fit/src/types.rs:145`, `crates/engine/src/dag.rs:370` (`resolve_source_table` → `analyzable_data`) and `crates/chart/src/xy.rs:1688` (`resolve_fitted_overlay`)
- **Category:** wrong-result
- **Defect:** When an analysis fails on recalculation, the engine only overwrites `status` with `Failed`; the previous `scalars`, `tabs`, `fitted_curves`, `pairwise_comparisons` and `analyzable_data` stay in the sheet, and no consumer checks `status` before reading them.
- **Failure scenario:** XY sheet, linear regression `lin`, a Normalize transform `norm` whose 100 % anchor is hooked to `lin`'s `Slope`, and an XY graph with `lin` as regression overlay. The user edits two Y values (slope becomes −32.01) and then excludes two rows, leaving 2 points. `table.excludeCells` returns success (`recalculated_sheets: 1`); `lin` becomes `Failed { "insufficient observations: need at least 3, got 2" }`, but `lin.lookup_scalar("Slope")` still returns −32.01, `norm` is recomputed from it and reported `UpToDate` with `HundredAnchor = −32.01`, and the graph still draws the old regression line over the two remaining points with no chart warning. The same path feeds stale scalars into nonlinear-fit constraints hooked with `ResultScalar` (`fit/src/types.rs:145`), stale `analyzable_data` into any analysis chained on a failed transform (`dag.rs:370`), and stale P values into comparison brackets (brackets read `pairwise_comparisons` live from the result sheet). Saving keeps the stale numbers in the file (`save_project_bytes` succeeded, 8 951 bytes).
- **Evidence:** Read `dag.rs:421-474`: on `Ok` the whole sheet is replaced; on `Err(message)` only `target.status = ResultStatus::Failed { … }` is set. `lookup_scalar` (`result.rs:200-207`) filters by key and finiteness only. Probe `probe-X2/tests/probe.rs::p5_stale_results_after_failure` printed `[after exclusion] lin.status=Failed { … got 2 } slope_scalar=Some(-32.01…) curves=1 ; norm.status=UpToDate norm scalars=[("ZeroAnchor", 0.0), ("HundredAnchor", -32.01…)]`, `scene prims before=35 after=35 warnings_after=[]`, and `30` primitives once the overlay was cleared, i.e. the stale curve was still drawn.
- **Suggested fix:** On failure, clear the computed payload (scalars, tabs except a diagnostic tab, curves, comparisons, `analyzable_data`), or make `lookup_scalar`, `resolve_source_table`, `resolve_fitted_overlay` and bracket resolution refuse a sheet whose status is not `UpToDate` so dependants fail with a "stale upstream" message; report failed dependants in the command payload.
- **Related:** S07 (engine DAG) and S08 (chart) own the files; R1-S07-07 is a different stale-data path (links).

### R1-X2-02 · S1 · Linear and nonlinear regression on Mean/SD/N (or Mean/SEM/N, Mean/%CV/N) data ignore N and the within-point scatter

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/fit/src/types.rs:294-306` (extraction keeps `sd`/`n` on `DataPoint`), `crates/fit/src/solver.rs:414` (`compute_point_weight`) and `:473` (`build_observations`), `crates/fit/src/linear.rs:145-150` (`simple_linear_regression` uses only `x0` and `y`)
- **Category:** wrong-result
- **Defect:** The summarized-Y path turns each row into one `DataPoint { y: mean, sd, n }`, but neither solver uses `n` at all (and `sd` only under the explicit `1/SD²` weighting), so each mean counts as a single unweighted observation; the governing guides say these rows are "expanded from `(Mean_i, SD_i, n_i)`" (`docs/curve-fitting-implementation.md:22`) and that nonlinear regression reconstructs `SS_within = (n_i − 1)·SD_i²` (`docs/data-tables-and-transforms.md` §2.1).
- **Failure scenario:** Five X values with replicate Y data (N = 3, 3, 3, 3, 6) fitted as raw replicates give slope 1.7375, SE 0.160, DF 16, P = 8.6e-9. The same data typed as Mean/SD/N (means, SDs and Ns computed from those replicates) give slope 1.8, SE 0.208, DF 3, P = 0.0033, Sy.x 0.658 vs 1.011, "Number of points analyzed" 5 instead of 18, for both "linear" and the `straight_line` nonlinear model. Unequal N therefore changes the best-fit values, and any N > 1 changes SEs, CIs, DF, P values and model comparisons, with nothing on the result sheet saying the N column was ignored.
- **Evidence:** Read `types.rs:279-333`, `solver.rs:414-484` (no reference to `pt.n`; `pt.sd` only inside `WeightingScheme::ObservedSd`), `linear.rs:137-229`. Probe `probe-X2/tests/probe.rs::p6_mean_sd_n_vs_raw` printed for raw: `Slope 1.7375 … Degrees of Freedom 16 … Number of points analyzed 18`; for Mean/SD/N: `Slope 1.8 … Degrees of Freedom 3 … Number of points analyzed 5` (linear: `P value raw 0.00325` vs `8.56e-9`).
- **Suggested fix:** For parametric summary modes, weight each mean by `n_i` and add `Σ(n_i − 1)·SD_i²` to the residual SS with `Σn_i − K` degrees of freedom (equivalent to expanding the replicates), or refuse with a clear diagnostic until that is implemented.
- **Related:** S03 (fit) owns the code; seam with the S05 summarized-cell model. R1-S02-08 is the analogous problem in ANOVA.

### R1-X2-03 · S2 · Excluding an X value (or every Y in a row) turns that row into an "unknown" to interpolate

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/fit/src/types.rs:292` (`populate_xy_column`), with `crates/doc/src/archetypes.rs:187` (`XyTable::x_value_at`) and `crates/engine/src/cmd_data.rs:1723` (`table.excludeCells` with `target: "x"`)
- **Category:** wrong-result
- **Defect:** The fit extractor decides "standard-curve unknown" from `x_value_at(row) == None` and `had_y == false`, but both helpers return `None`/`false` for *excluded* cells as well as blank ones, so an exclusion is reinterpreted as a request to interpolate.
- **Failure scenario:** XY table X = 1..6, Y = 2.1, 3.9, 6.2, **50**, 10.1, 11.8, linear regression with "interpolate unknowns" on. The user excludes the X cell of the outlier row (`table.excludeCells {target:"x", row:3}`). The fit correctly drops the row, but the result sheet gains a new "Interpolated unknowns" tab reporting `A (X from Y=50.0000)` → X = 25.33, CI 23.93–26.94, an extrapolation four times past the data range, presented as an assay result. The same happens for a 4PL fit (`X from Y=55.5`), and symmetrically a row whose Y replicates are all excluded becomes a `Y from X` unknown (`had_y` stays false, `types.rs:328`). The graph of the same data simply omits the row (`crates/chart/src/xy.rs:1653`), so the graph and the result sheet disagree about what the row is.
- **Evidence:** Read `types.rs:279-333` (`types.rs:324` pushes the unknown): `let x_opt = xy.x_value_at(row);` then `series.unknowns_y.push((row, y))` when `x_opt` is `None`; `x_value_at` uses `Cell::active_number` (`archetypes.rs:187`), which returns `None` for `excluded`. Probe `probe-X2/tests/probe.rs::p1_excluded_x_becomes_unknown_linear` (engine `Session`, `analysis.add` + `table.excludeCells`) printed, after the exclusion, `TAB linear_interpolated … A (X from Y=50.0000): [Number 50.0, Number 25.334317779090373, ConfidenceInterval { Finite(23.93…), Finite(26.94…) }]`; before the exclusion the tab did not exist. `p1b_excluded_x_nonlinear` printed `A (X from Y=55.5000) … -5.9903` for `log_agonist_vs_response_4pl`.
- **Suggested fix:** Classify unknowns from the raw cell state: a row is an X-unknown only when the X cell is blank and not excluded (likewise for Y); an excluded X or an all-excluded Y row is dropped and counted in an "excluded" tally.
- **Related:** R1-S03-12 (interpolation extrapolates without a flag) makes the spurious value look ordinary.

### R1-X2-04 · S2 · Paste and live CSV links split quoted fields and keep quoted numbers as text, while CSV import of the same text does not

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/transform/src/import.rs:248` (`parse_delimited_text`: `line.split(delimiter)` then `Cell::parse_import_token`), reached from `:224` (external-file links, `table.pasteLink`) and `:227` (`table.paste`, `crates/engine/src/cmd_data.rs:1871-1875`); the CSV importer uses the RFC-4180 reader `crates/format/src/csv.rs:148` (`parse_delimited_records`)
- **Category:** wrong-result
- **Defect:** Two different delimited-text parsers feed data tables: `table.importCsv` honours quotes, while paste and live file links split on every delimiter and never strip quotes, so the same text produces different cells and different column alignment depending on the command.
- **Failure scenario:** The text `"Boston, MA",1,12.5` / `Lyon,2,14.0` / `"Oslo","3","15.5"` (typical spreadsheet CSV export: a label with a comma, and a tool that quotes every field). `table.importCsv` gives Site = `Boston, MA`, Dose = 1, Response = 12.5 etc. `table.paste` of the same rows into a 3-column Column table gives row 1 = `"Boston` | `MA"` | **1** (the dose lands in the third column and 12.5 is dropped), and row 3 = `"Oslo"` | `"3"` | `"15.5"` as text, which every analysis then skips as non-numeric (R1-X2-08). The command reports success (`rows_placed: 3`, `cols_placed: 4`); an analysis of the third column now mixes a dose with responses. A live link to a CSV file (`LinkSource::ExternalDelimitedFile`) re-parses with the same splitter on every refresh, so it disagrees with an import of the same file.
- **Evidence:** Read `import.rs:198-258` and `format/src/csv.rs:148-210`, `:273-317`. Probe `probe-X2/tests/probe.rs::p9_paste_vs_import_quotes` printed for importCsv `col 0 'Site': [Text("Boston, MA"), …]`, `col 1 'Dose': [Number(1.0), …]`, `col 2 'Response': [Number(12.5), …]`, and for paste `col 0 'A': [Text("\"Boston"), Text("Lyon"), Text("\"Oslo\"")]`, `col 1 'B': [Text("MA\""), Number(2.0), Text("\"3\"")]`, `col 2 'C': [Number(1.0), Number(14.0), Text("\"15.5\"")]`.
- **Suggested fix:** Route paste and external links through `lumencraft_format::parse_delimited_records` + `parse_cell_token` (one tokenizer, one set of missing sentinels and exclusion rules), or move that reader below both crates.
- **Related:** R1-S04-05 (wide pastes drop columns) hides the overflow; S04 and S06 own the two parsers.

### R1-X2-05 · S2 · Two-way/three-way ANOVA on Grouped tables, nested ANOVA and contingency analyses ignore "data sets to analyze"

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/stats/src/anova.rs:2041` (`run_factorial_anova` → `run_grouped_factorial`, which loops `0..n_cols` at `:2124`/`:2190`), `crates/stats/src/anova.rs:2370` (`run_nested_analysis` → `nested_one_way_anova(nested, …)`), `crates/stats/src/categorical.rs:1332` (`n_cols = table.data_sets.len()`); selection written by `crates/engine/src/cmd_sci.rs:385-389`
- **Category:** wrong-result
- **Defect:** The engine stores the user's column selection in `AnalysisSpec::selected_data_sets` (and `analysis.retargetData` rewrites it), and the one-way, two-group, descriptive, survival and multivariate paths honour it, but these three analysis families never read it and always analyse every data set in the table.
- **Failure scenario:** Grouped table with three column groups (Control, DrugA, DrugB), 2 rows × 3 replicates. The user runs two-way ANOVA with `selected_data_sets = [0, 1]` to compare Control vs DrugA only. The result reports Column Factor df = 2, SS = 25 154, F = 1547, P < 0.0001 and residual df = 12: DrugB (values near 90–99) is included and dominates the column effect, while `analysis.selected_data_sets` still reads `[0, 1]`. Likewise a contingency analysis restricted to two outcome columns runs the full R×C table, and a nested t test restricted to two groups runs nested one-way ANOVA on all groups.
- **Evidence:** Read `anova.rs:2035-2045`, `:2114-2200` (no `spec`/selection parameter reaches `run_grouped_factorial`), `:2362-2370`, `categorical.rs:1318-1338`; `grep selected_data_sets crates/stats/src/*.rs` shows no use in these paths. Probe `probe-X2/tests/probe.rs::p7_selected_data_sets_ignored` printed `selected=[0, 1]` and `Column Factor: [SS 25154.30, df 2.0, MS 12577.15, F 1547.43, P 3.3e-15]`, `Residual: [… df 12.0 …]`.
- **Suggested fix:** Resolve `selected_data_sets` (as the other families do with `resolve_selected_indices`) before building observations or counts, or reject a non-empty selection for kinds that cannot honour it.
- **Related:** S02 (stats) owns the code.

### R1-X2-06 · S2 · A regression overlay on a data set the fit did not analyse draws another data set's curve

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/xy.rs:1694` (`resolve_fitted_overlay`: `.find(|fc| fc.data_set_index == series.data_set_index).or_else(|| res.fitted_curves.first())`)
- **Category:** wrong-result
- **Defect:** When the result sheet has no curve for the series' data set, the chart silently substitutes the first fitted curve in the result instead of drawing nothing or warning.
- **Failure scenario:** XY table with data set A (Y = 2X, rising) and data set B (Y ≈ 50 − 8X, falling). Linear regression is run on A only (`selected_data_sets = [0]`; the result has one curve, for data set 0). On the graph, `graph.setRegressionOverlay {all_series: true}` (or an overlay bound to series B alone) draws A's rising line through B's falling points with no chart warning. The same substitution happens whenever a data set was dropped from the fit (for example all its Y excluded, `crates/fit/src/types.rs:269-271` keeps only non-empty series), so the graph shows a fit for data that was never fitted.
- **Evidence:** Read `xy.rs:1688-1702`. - **Suggested fix:** Drop the `.or_else(|| res.fitted_curves.first())` fallback (keep it only for single-curve results whose source is the same single data set) and emit a `ChartWarning` when the series has no matching curve.
- **Related:** R1-S08-07 is the same fallback pattern for comparison brackets.

### R1-X2-07 · S2 · Heatmaps draw missing and excluded cells as the value 0, which also stretches the colour scale and drives the row clustering

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/multivariate_layout.rs:1194` (Multiple Variables), `:1214` (Column), `:1229` (Grouped), `:1161` (correlation-matrix result tab); consumed at `:1056` (clustering) and `:1063` (`heatmap_min_max`)
- **Category:** wrong-result
- **Defect:** `extract_heatmap_data` substitutes `0.0` for every blank, excluded, text or non-finite cell (`active_number().unwrap_or(0.0)`; empty replicate set → `0.0`; non-`Number` result cell → `0.0`), and the matrix then feeds the colour domain and Ward clustering as if those zeros were measurements.
- **Failure scenario:** A Multiple Variables table of expression values between 100 and 200 with one missing (or one excluded `*`) cell, graphed as a heatmap. That cell is painted the colour of 0; `heatmap_min_max` returns `(0, 200)`, so the Viridis ramp spans 0–200 and every real value is squeezed into its upper half; `hierarchical_clustering` (run automatically for 2–128 rows) treats the row as having a 0 there and splits it into its own branch of the dendrogram, reordering the rows. For a correlation-matrix heatmap, a pair whose r is undefined (constant variable, written as `ResultCell::Empty`) is drawn as r = 0, "no correlation". No warning is emitted, and the analysis on the same table drops those cells, so the graph and the analysis use different data.
- **Evidence:** Read `multivariate_layout.rs:1150-1236` (extraction), `:1038-1075` (`compile_heatmap`: `hierarchical_clustering(&hm.values, …)` at `:1056`, `heatmap_min_max(&hm.values)` at `:1063`), `:1256-1262` (min/max over all finite values, including the substituted zeros). The guide requires graphs to treat excluded cells "as masked observations" (`docs/data-tables-and-transforms.md` §1 item 2).
- **Suggested fix:** Carry `Option<f64>` (or `NaN`) per cell, draw missing cells with a distinct "no data" fill, exclude them from the colour domain, and either skip clustering or use a pairwise-complete distance when any cell is missing.
- **Related:** S08 (chart) owns the file; seam with S05 cell model.

### R1-X2-08 · S3 · Text in a numeric data column is dropped from every analysis without being counted as missing or excluded

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/stats/src/common.rs:227-231` and `:246-250` (`extract_numeric_columns`), reported by `crates/stats/src/column.rs:1537-1538` (`Number of values`, `Excluded values`)
- **Category:** wrong-result
- **Defect:** A non-excluded `CellValue::Text` in a Column or Multiple Variables numeric column falls through both branches (`excluded` → count, `active_number` → value) and is discarded with no count and no checklist note, though `table.setCells` stores any non-numeric string as text (`crates/engine/src/cmd_data.rs:2918`, `Cell::parse_import_token`).
- **Failure scenario:** A Column data set holding `1.2, 3.4, <0.5, <0.5, 2.0` (two results below the detection limit, typed or pasted as text). Descriptive statistics report Number of values 3, Excluded values 0, mean 2.2; a t test or ANOVA uses n = 3. Nothing says two entries were ignored, and the dropped values are systematically the small ones, so the mean is biased upward. The same happens to quoted numbers from a paste (R1-X2-04).
- **Evidence:** Read `common.rs:212-255`: `if cell.excluded { excluded_count += 1; } else if let Some(v) = cell.active_number() { values.push(v); }` with no `else`; `column.rs:1510-1540` shows only `n` and `excluded_count` reach the result. The project rules require that analyses never drop missing values silently (AGENTS.md › Statistical & numerical rigor).
- **Suggested fix:** Count non-numeric cells separately and report them ("Non-numeric values ignored: 2") with a checklist warning, or reject the analysis with the cell coordinates.
- **Related:** S02 owns the code.

### R1-X2-09 · S3 · One non-finite number in any result sheet makes the whole project unsavable; Bland–Altman can produce one from finite data

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/archive.rs:176` (`save_archive_bytes` → `validate_project_document`) and `:651-681` (`validate_result_sheet`); producer `crates/stats/src/two_group.rs:1118-1125` (Bland–Altman overlay stores `out.loa_lower`/`out.loa_upper` unchecked); nothing in `crates/engine/src/dag.rs:457-468` sanitizes a computed sheet
- **Category:** data-loss
- **Defect:** Analyses write raw `f64`s into `fitted_curves`, `scalars`, `pairwise_comparisons` and tab cells, the engine stores them as-is, and save rejects the entire document if any of them is non-finite, so one overflowing analysis blocks saving every data table in the project.
- **Failure scenario:** Column table A = 1e300, 1.1e300, 1.2e300; B = −1e300, 1e300, 1.5e300 (any pair whose differences square past `f64::MAX`, i.e. |A − B| above about 1.3e154). Bland–Altman succeeds (`analysis.add` returns OK and the sheet is `UpToDate`), but every later Save fails with `non-finite floating-point value at r.fitted_curves[0].points[0]` until the user finds and deletes that analysis. Every other analysis family survived the same sweep, so the trigger needs extreme magnitudes today; the hazard is that the engine relies on every producer guarding every field.
- **Evidence:** Probe `probe-X2/tests/probe.rs::p3_fuzz_stats_then_save` (855 analysis runs: one-way ANOVA × 16 multiple-comparison methods, 10 two-group methods, descriptive, Grubbs/ROUT, Bland–Altman, Passing–Bablok over 9 edge datasets, then `save_project_bytes`) printed `big/BA: analysis OK but save failed: non-finite floating-point value at r.fitted_curves[0].points[0]` and no other failure; `p2_fuzz_fit_then_save` (every built-in equation × 3 X sets × 4 Y sets) and `p4_fuzz_survival_then_save` found none.
- **Suggested fix:** Validate a freshly computed `ResultSheet` with the same finiteness rules in `recompute_result_sheet` and turn a violation into `ResultStatus::Failed` (so the analysis fails, not the save); in Bland–Altman, compute the SD with scaling or return an error on overflow.
- **Related:** R1-S06-06 (fields save does not validate) is the opposite gap in the same validator.

## Checked, no finding

- **Excluded cells reach stats as masked, not as values.** `extract_numeric_columns` counts and skips `excluded` (`crates/stats/src/common.rs:227-231`); `Cell::active_number` gates every chart and fit read (`crates/doc/src/cell.rs:94-96`).
- **Paired row alignment.** Paired t, ratio paired t and Wilcoxon use `extract_paired_values`, which keeps a row only when both cells are active (`crates/stats/src/common.rs:285`); multiple-row paired tests pair subcolumns within the row (`crates/stats/src/two_group.rs:1524`).
- **Survival exclusions.** `cohort_observations` skips rows whose status or time is excluded or blank (`crates/doc/src/archetypes.rs:603-611`); the KM graph uses the analysis's curves when a result exists (`crates/chart/src/survival_cat.rs:1356-1358`).
- **Transforms keep exclusion flags and only write finite numbers.** `CompiledOp::eval` returns `None` for non-finite output (`crates/transform/src/ops/math.rs:110`); mean/spread rewrites carry `excluded` (`:489`, `:525`).
- **Calculated variables keep a user's exclusion across recalculation** (`crates/transform/src/formula/dag.rs:98-105`).
