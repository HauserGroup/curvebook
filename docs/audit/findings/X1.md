## Findings

### R1-X1-01 · S1 · Layout `LiveGraph` items have no count limit and each one compiles and keeps its own graph scene: a 44 KB project needs about 10 GB to show or export its layout

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/chart/src/multivariate_layout.rs:2673-2713` (`compile_layout_scene`: `compile_graph` per `LiveGraph` item at `:2679`, every sub-scene kept in `panels` at `:2698`, then copied into the page at `:2711-2713`); `crates/doc/src/layout.rs:135` (`items: Vec<LayoutItem>`, no limit); `crates/engine/src/cmd_sci.rs:1971-1998` (`layout.setSpec` stores any number of items), `:2000-2030` (`layout.addPanel`)
- **Category:** no-panic (allocation abort) / resources
- **Defect:** Nothing bounds the number of layout items, and `compile_layout_scene` compiles the referenced graph once per item and holds every sub-scene at the same time, so the work and memory of one render are (item count) × (graph scene size). Repeated items cost about 5 bytes each in a saved archive.
- **Failure scenario:** A `.lumencraft` file of 44 KB holds one 200-row × 4-column XY graph and a layout with 10 000 `LiveGraph` items that all reference it, and the layout is the active sheet. It opens and validates normally. Rendering it then needs about 1 MB per item, about 10 GB and 20 s, and the process aborts on allocation failure (wasm at 4 GB), which `guard::run_guarded` cannot catch. Every render path reaches it: MCP `open_file` then `render_preview` with no `sheet_id` (compiles the active sheet, `crates/mcp/src/tools.rs:1364-1371`), MCP `export {all_graphs}`, control `render.svg`/`render.pdf`/`ui.screenshot` (active scene, `crates/ui-egui/src/dialogs_canvas.rs:2512-2520`, `:3290`), `lumencraft --headless-once project.lumencraft` (`apps/lumencraft/src/main.rs:180-181`), CLI `convert`/`batch` exports of the layout (`apps/lumencraft-cli/src/cmd_convert.rs:347`), and engine `export.*`. The same item list can also be sent in a 31 KB `layout.setSpec` request over C, M or L. With a larger graph (R1-S07-11 measured about 12 MB per scene for a 20 000-point graph) a few hundred items are enough.
- **Evidence:** Probe (`Session::execute`, release): `sheet.createData` 200 × 4 with `graph_sheet_id`, `layout.create`, `layout.setSpec {spec: {items: [LiveGraph × n]}}`, then `export.svg {sheet_id: layout-1}`:
  ```
  n=1    request 196 B   export 4 ms     SVG 0.18 MB  archive 7 739 B  peak RSS   8 MB
  n=50   request 7.8 KB  export 108 ms   SVG 8.9 MB   archive 8 030 B  peak RSS  58 MB
  n=100                  export 222 ms   SVG 17.8 MB                   peak RSS 109 MB
  n=200  request 31 KB   export 458 ms   SVG 35.6 MB  archive 8 782 B  peak RSS 207 MB
  n=10000: project.save → 44 372 B archive; project.open of those bytes → Ok, 10 000 items back, active sheet layout-1 (not rendered)
  ```
  Memory grows linearly at about 1 MB per item. `LiveTable` items repeat the same pattern with a full result-tab grid per item (`crates/chart/src/survival_cat.rs:1042-1048`, rows not capped for result tabs).
- **Suggested fix:** Limit the number of layout items in `LayoutSpec` validation (on load and in `layout.setSpec`/`layout.addPanel`), and in `compile_layout_scene` compile each referenced graph once and reuse it, emitting panels one at a time against a primitive budget.
- **Related:** R1-S07-11 (same multiplication through `export.pdf {sheet_ids}`), S08 (chart), S07 (layout commands), R1-S12-04 and R1-S10-03 (the same render paths have no panic boundary).

### R1-X1-02 · S2 · CSV import tokenizes the whole input into `Vec<Vec<String>>` before any column or cell limit, about 27 bytes of heap per input byte

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/format/src/csv.rs:608` (`import_csv_to_datasheet` calls `parse_delimited_records` first), `csv.rs:148-250` (tokenizer), `csv.rs:254-268` (`push_field`/`push_record` limits); limits applied afterwards at `csv.rs:635-636`, `:653` (`validate_data_sets`, `validate_csv_cell_budget`); same order in the link pipeline at `csv.rs:967`
- **Category:** resources / no-panic (allocation abort)
- **Defect:** The tokenizer stores every field as its own `String` (24 bytes even when empty) and only limits fields per row to `MAX_DATA_SETS × MAX_SUBCOLUMNS + 4` = 524 292 and rows to `MAX_ROWS + 16`, so up to about 5×10¹¹ fields can be held before `MAX_IMPORT_CELLS` (10 M) and `MAX_DATA_SETS` (1 024) are checked; a one-byte field (`,`) costs about 27 bytes.
- **Failure scenario:** Every CSV entry point goes through this order: `table.importCsv` with inline `csv` over C, M or L (16 MiB line → about 450 MB before the error), with `path`, MCP `open_file` CSV, CLI batch `inputs[]`, desktop file arguments (`apps/lumencraft/src/main.rs:395-400`), linked-file refresh, and each CSV entry of a `.prism` archive (an entry may decompress to 64 MiB, `crates/format/src/zip.rs:19`, so a `.prism` of a few tens of KB holding 64 MiB of commas costs about 1.7 GB before the import is rejected). A user who opens a 1 GB CSV, which should get "exceeds 10 000 000 cells", instead needs about 27 GB and the process aborts (wasm at 4 GB) instead of returning the error.
- **Evidence:** Probe with input that is only commas, 500 000 fields per row:
  ```
  import_csv_to_datasheet, 1 MiB  -> Err("column count 499999 exceeds maximum 1024"), peak RSS  42.5 MB
  import_csv_to_datasheet, 4 MiB  -> same error,                                        peak RSS 123.0 MB
  import_csv_to_datasheet, 6 MiB  -> same error,                                        peak RSS 175.6 MB
  Session::execute("table.importCsv", {csv: <4 MiB>}) -> same error,                    peak RSS 131.9 MB
  ```
  The ~27 bytes per input byte is measured; the `.prism` and 1 GB figures are that rate applied to the stated sizes (not run).
- **Suggested fix:** Count fields in the tokenizer against `MAX_IMPORT_CELLS` (plus header rows) and fail as soon as the count passes it; optionally reject a row as soon as it exceeds `MAX_DATA_SETS × subcolumns + row-title column` once the subcolumn mode is known.
- **Related:** R1-S06-01 (prism multiplies this per entry), R1-S05-02 (transpose after tokenizing), R1-S06-11 (similar amplification in the XML parser), S06.

### R1-X1-03 · S2 · No file read checks size or file type first: every limit applies after the whole file is in memory, a FIFO blocks forever, and a link to `/dev/zero` reads until the process aborts

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/engine/src/cmd_data.rs:197` (linked-file refresh), `:379`, `:2039`, `:2107`, `:2222`, `:2250`; `crates/format/src/archive.rs:158`, `:171`; `crates/mcp/src/tools.rs:644`, `:671`, `:695`; `apps/lumencraft/src/main.rs:373`, `:381`, `:388`, `:395`; `apps/lumencraft-cli/src/cmd_run_batch.rs:388`, `:393`, `:402`
- **Category:** resources / data-loss
- **Defect:** Every file sink is `std::fs::read` or `read_to_string` on the given path with no `metadata().is_file()` check, no length check and no read limit (`Read::take`), so the format limits (`MAX_XML_BYTES` 64 MiB, ZIP caps, CSV caps) only run after the whole file has been read, and device files and FIFOs are read like regular files.
- **Failure scenario:** (a) A project or template carries an external link whose path is `/dev/zero` (or a named pipe). Choosing Analyze ▸ Recalculate All (`project.recalculate`, `cmd_data.rs:524-525`), from the desktop control socket, MCP `command_run`, or a sandboxed CLI batch (the link path is not checked, R1-S12-01), makes `read_to_string` grow its buffer forever until allocation fails and the process aborts, losing the session; with a FIFO the command never returns and the single-threaded server hangs. (b) MCP `open_file {path: "/dev/zero", format: "csv"}` or `table.importCsv {path: "/dev/zero"}` from an MCP client or control peer does the same. (c) Opening a 2 GB `.pzfx` reads 2 GB before the 64 MiB limit rejects it.
- **Evidence:** Probe via `Session::execute`:
  ```
  table.importPzfx {path: big.pzfx (150 000 000 bytes of spaces)}
    -> Err("XML byte length 150000000 exceeds limit 67108864") after 149 ms, peak RSS 152.7 MB
  table.importCsv {path: <mkfifo pipe>}  -> still blocked after 3 s (killed)
  ```
  `/dev/zero` was not run (it would exhaust memory); the trace is `cmd_data.rs:197` `read_to_string` → `std` reads to EOF with a size hint of 0 for character devices.
- **Suggested fix:** Route all file reads through one helper that opens the file, rejects anything that is not a regular file, and reads through `take(limit + 1)` with a per-format limit (ZIP total, `MAX_XML_BYTES`, a CSV byte limit), returning an error past the limit.
- **Related:** R1-S07-02 and R1-S12-01 (the same link read, sandbox side), Known defect G2 (`cmd_data.rs:2039` also swallows errors), R1-S06-14 (journal read), S06, S07, S12.

### R1-X1-04 · S3 · The `--workdir` path guard exists only for CLI `run`/`batch`; MCP reads, writes and creates directories at any path through the same engine commands, and `docs/mcp.md` says nothing about it

- **Base:** ebcc622b32fc526c545aad8439e3e580d04b478c
- **Location:** `crates/mcp/src/tools.rs:619-626` (`open_file` takes `path` as given), `:764-776` (`save_file`), `:1336-1338` (`write_binary_export`), `:956` (`command_run`/`command_batch` pass params to `Session::execute` unchanged); compare `apps/lumencraft-cli/src/sandbox.rs:65-79`, `:107-127`; engine writers `crates/engine/src/cmd_sci.rs:2378-2386` (`create_dir_all` then `fs::write`), `crates/engine/src/cmd_data.rs:2212-2214`, `crates/format/src/archive.rs:152`, `:165`
- **Category:** security
- **Defect:** The CLI rewrites and contains every path parameter (`sandbox.rs`), but the MCP server has no equivalent option or policy, so the same commands (`project.save`, `table.exportCsv`, `export.*`, `analysis.export*`, `project.recalculate` links) read and overwrite any file the user can access and create directory trees anywhere.
- **Failure scenario:** An MCP client that has read untrusted text (a document or web page with injected instructions) calls `command_run {"command_id": "table.exportCsv", "params": {"sheet_id": "data-1", "path": "/Users/<user>/.zshrc"}}` after filling the table with chosen strings, or `export {"format": "svg", "path": "<any file>"}`; the server overwrites the target with no containment, while the same script under `lumencraft-cli run --workdir` would be rejected with `PathEscape`. The control socket has the same gap (R1-S10-02); MCP is the remaining entry point without one.
- **Evidence:** Code read: no path check in `crates/mcp/src` (`grep -i 'workdir|canonical|sandbox'` finds none); `handle_open_file`/`handle_save_file`/`write_binary_export` call `fs::read`, `save_project_file` and `fs::write` on the raw string; `docs/mcp.md` describes the tools but not their file access. Not run.
- **Suggested fix:** Give `lumencraft-cli mcp` a `--workdir` (or allowed-roots) option backed by the CLI's `WorkdirGuard`, enforced through an engine-level path policy that also covers stored link paths (as suggested for R1-S12-01), and document the file-access scope in `docs/mcp.md`.
- **Related:** R1-S10-02 (control socket), R1-S12-01 / R1-S07-02 (engine-level path policy), S12.
